# 聊天室 AI 工作区执行方案

## 目标

聊天室 AI 同时满足四个要求：

1. 用户能实时看到规划、上下文读取、RAG、重排、模型连接和流式生成状态。
2. 简单问题保持低延迟，复杂问题可以拆成多个并行研究任务。
3. AI 可以引用聊天室内有权限访问的消息、图片和文件，并能回到原消息。
4. 用户可以在聊天室右侧持续和 AI 对话，不中断左侧真人聊天。

## 请求流程

```text
用户问题
  -> 规划 Agent（快速模型，最多 8 秒）
  -> 权限校验后的聊天室上下文
  -> 简单任务：单路 RAG
     复杂任务：最多 3 个研究子问题并行 RAG
  -> Embedding -> Qdrant -> 消息权限复核 -> Rerank
  -> 合并文本证据与附件证据
  -> 主模型流式综合回答
  -> 前端渲染引用、附件和原消息定位
```

## 规划策略

规划不再依赖本地关键词表。快速模型输出受约束的 JSON：

- `intent`：总结、待办、结论、事实查找或一般问答。
- `context_scope`：近期上下文或全房间历史。
- `semantic_search`：是否需要补充语义检索。
- `research_questions`：复杂任务的 0 到 3 个独立研究子问题。

规划失败、超时或返回无效枚举时，服务端降级为“近期上下文 + 单路 RAG”。降级不再尝试本地关键词分类，避免规则未命中导致静默跳过检索。

## 自适应并行研究

普通任务只执行一次检索。规划 Agent 只有在问题确实包含多个主题时才生成研究子问题；这些任务使用 `FuturesUnordered` 并发执行，谁先完成就先更新执行过程。

每个研究任务执行：

1. 调用配置的 Embedding API。
2. 查询当前房间的 Qdrant 向量索引。
3. 回查数据库，只保留当前用户仍有权查看且未撤回的消息。
4. 调用配置的 rerank 模型重排候选。
5. 低分无匹配时不注入证据；rerank 超时或失败时降级到向量排序。

边界：

- 最多 3 个并行研究任务。
- 每个任务最多 5 秒。
- 检索任务使用互不冲突的 `S` 引用编号区间。
- 规划和检索失败不会阻止主回答，主模型会基于仍可用的上下文继续工作。
- 不对每个简单问题强制启动多个模型 Agent，避免无意义增加首 token 延迟和费用。

## 实时执行状态

每个 AI run 持久化并实时发布以下信息：

- 当前阶段、阶段开始时间和总耗时。
- 规划 Agent 的上下文范围、检索策略和子问题数量。
- 并行研究任务数、Embedding 模型和 rerank 模型。
- 每个研究 Agent 的具体问题、选中条数和耗时。
- 最终注入的 RAG 证据及分数。
- 发现的可引用附件。
- 请求的 provider、模型、首个响应等待时间和已生成字符数。

前端执行过程默认在生成期间展开，完成后保留紧凑的两列时间线。用户向上滚动时停止自动跟随 token，并显示“回到最新消息”按钮。

## 消息与附件引用

证据标签分两类：

- `[S1]`：RAG 文本证据。
- `[A1]`：聊天室上下文中的图片或文件。

提示词要求模型在描述、比较或建议打开附件时引用对应的 `[A#]`，但禁止模型生成附件 URL。服务端只把经过房间成员权限校验的附件元数据写入来源对象，包括文件名、MIME、大小、敏感标记和授权下载地址。

前端根据来源对象渲染附件：

- 图片显示缩略图并支持图库预览。
- 视频和普通文件沿用聊天室附件组件。
- 敏感附件保留确认查看遮罩。
- 详情页显示引用状态、发送人、时间，并可通过 `?message=<id>#message-<id>` 定位原消息。
- 仅有文件名但没有 `[A#]` 时，精确文件名匹配仍可渲染，兼容旧回答。

## 右侧 AI 工作区

聊天室头部的 Bot 按钮控制右侧 AI 面板：

- 桌面端显示“左侧导航 + 真人聊天室 + AI 助手”三列布局。
- 展开 AI 时左侧导航自动收窄，优先保证两块聊天内容的可读宽度。
- 移动端 AI 面板覆盖当前工作区，通过关闭按钮返回聊天室。
- 面板自动选择当前房间最近使用的 AI 线程；没有线程时自动创建并绑定当前房间。
- 切换房间会重建面板上下文，避免把上一个房间的密码、消息或引用带入新房间。
- 独立 AI 助手页面保持原有多线程管理能力。

## 聊天输入框 AI 建议

旧接口必须等待完整 JSON，前端无法利用模型的首 token。新接口使用 SSE 传输 NDJSON：

```json
{"type":"suggestion","content":"第一条建议"}
{"type":"suggestion","content":"第二条建议"}
{"type":"suggestion","content":"第三条建议"}
{"type":"summary","content":"一句话摘要"}
```

模型先输出最有价值的建议。前端解析到完整第一行后立即填入输入框，同时继续接收其余建议和摘要。旧的一次性 JSON 接口保留用于兼容。

## 性能与可观测性验收

- 点击 AI 后立即出现本地加载状态，不出现无反馈空窗。
- AI 建议以“第一条完整建议”的到达时间衡量，不再以完整响应完成时间衡量。
- 多研究任务并发，总检索等待接近最慢单个任务，而不是各任务耗时之和。
- 模型连接、首响应和流式生成分别计时，慢点可以在前端直接识别。
- 用户离开消息底部后，任何 token 更新都不得强制滚回底部。
- 每条 `[S#]` 和 `[A#]` 都必须对应当前回答保存的来源对象。
- 刷新已加入房间时自动重连，不再显示重复加入操作。

## 后续调优顺序

1. 用真实请求记录规划、Embedding、Qdrant、rerank、首 token 和总生成的 P50/P95。
2. 根据误召回案例调整 rerank 最低分和候选数，而不是重新引入关键词规则。
3. 只有当并行检索仍无法覆盖复杂任务时，再增加带独立上下文的模型研究 Agent，并设置并发、token 和费用预算。
4. 为引用准确率建立离线评测集，分别统计召回率、重排准确率、引用覆盖率和错误引用率。
