## Frozen interface

### Model

- **General topic**: every forum chat has exactly one `forum_topics` row with
  `is_general = true` (Telegram's topic id 1). It is created lazily the first time a forum
  chat's topics are resolved, so forums enabled through `apply_chat_capabilities` directly also
  get one. `messages.topic_id IS NULL` **means General** — every pre-existing message and every
  message of a non-forum chat therefore belongs to General with no backfill. Posting to General
  (by its id or with no `topic_id`) stores `NULL`.
- Palette (`icon_color`, Telegram's six): `0x6FB9F0, 0xFFD67E, 0xCB86DB, 0x8EEE98, 0xFF93B2,
  0xFB6F5F` (decimal 7322096, 16766590, 13338331, 9367192, 16749490, 16478047).
- Roles: **topic admin** = holds `chat.topics` *and* is owner/admin (a member who holds
  `chat.topics` through the default permissions may only create topics). Creator of a topic may
  edit its title/icon and close/reopen it. Pin / hide General / delete / edit others' topics
  need topic admin. Posting into a closed topic needs topic admin.
- Enabling / disabling the forum needs `chat.info` (Telegram's "change info"); enabling
  upgrades a group to a supergroup through `apply_chat_capabilities`.

### HTTP (under `/api/chats/:id`, also on the `/api/rooms` alias)

| Method | Path | Gate | Body → Answer |
| --- | --- | --- | --- |
| PUT | `/forum` | `chat.info` | `{enabled: bool}` → `Chat` descriptor; 409 when the chat type cannot be a forum (private/channel) |
| GET | `/topics` | active member | → `ForumTopicList {chat_id, is_forum, can_create, can_manage, topics: ForumTopic[]}`; 409 when not a forum |
| POST | `/topics` | `chat.topics` | `{title, icon_emoji?, icon_custom_emoji_id?, icon_color?}` → 201 `ForumTopic` |
| GET | `/topics/:topic_id` | active member | → `ForumTopic` |
| PATCH | `/topics/:topic_id` | creator (title/icon/is_closed) or topic admin | `{title?, icon_emoji?, icon_custom_emoji_id? (null clears), icon_color?, is_closed?, is_pinned?, is_hidden? (General only)}` → `ForumTopic` |
| DELETE | `/topics/:topic_id` | topic admin; General → 409 | → 204; the topic's messages are deleted (see Decisions) |
| GET | `/topics/:topic_id/messages?before&limit` | active member | → `StoredMessage[]` — exactly `/messages`' contract: the newest `limit` (1–500, default 100) at or before `before` (inclusive cursor), array in ascending order (pinned by `forum_topics_test`) |
| GET | `/topics/:topic_id/messages/:message_id/context?limit` | active member | → `StoredMessage[]` window around the message within the topic |
| POST | `/topics/:topic_id/read` | active member | `{message_id}` → `{topic_id, unread_count, chat_read_advanced}` |
| PUT | `/topics/:topic_id/notifications` | active member | `{muted: bool, muted_until: RFC3339 \| null}` → `ForumTopic` |

`ForumTopic {id, chat_id, is_general, title, icon_emoji ('' = none), icon_custom_emoji_id
(uuid|null), icon_color, is_pinned, pinned_at, is_closed, is_hidden, creator_id, created_at,
last_message: {message_id, sender, content, created_at} | null, unread_count, muted,
muted_until, can_edit}` — `unread_count`/`muted*`/`can_edit` are the viewer's. Order: pinned
(by `pinned_at`), then General, then by last activity (last message or creation) newest first.
Title 1–128 chars (trimmed), `icon_emoji` ≤ 16 chars, `icon_color` must be in the palette
(default derived from the topic id).

### Send paths (all accept an optional `topic_id`; absent = General)

WS `message` frame `topic_id`; multipart `POST /attachments` field `topic_id`;
`POST /attachments/uploads/:id/complete` body `topic_id`; `POST /sticker-messages` body
`topic_id`; `POST /polls` body `topic_id`. Forwards and favorite shares always land in General.
Rules (`AppState::resolve_post_topic`): non-forum chat + non-General topic → 400; unknown or
other chat's topic → 404; closed topic and sender not topic admin → 403 (the WS frame is dropped,
as for any refused WS send). Every path, General included.

### Wire

- `StoredMessage.topic_id` / `broadcast.topic_id`: optional uuid, omitted when `NULL` (General).
- `topic_updated {topic: TopicSummary}` — TG-007 fields `{id, title, icon_emoji, closed,
  pinned}` plus, additively and omitted at default: `icon_color`, `icon_custom_emoji_id`,
  `hidden`, `is_general`, `deleted`. Emitted on create, edit, close/reopen, pin, hide, delete.
- `chat_updated` on forum enable/disable (from `apply_chat_capabilities`).

### Unread / mute

- Per-topic read cursor in `forum_topic_members(topic_id, user_id, read_created_at,
  read_message_id, muted, muted_until)` — independent of `chat_reads`. A topic read never moves
  the chat cursor **except** when it leaves the viewer with zero unread in every topic: then the
  chat cursor advances to the chat's newest message (so the sidebar badge clears). A chat-level
  `read` frame never touches topic cursors.
- Per-topic mute is independent of the chat's `muted_until`; a muted topic suppresses web push
  for its messages.

## Decisions

- 2026-10-01 `messages.topic_id NULL` = General instead of backfilling General's id into every
  message: pre-existing messages need no rewrite (a table-wide UPDATE on the biggest table), and
  a chat that later enables the forum has its whole history in General for free.
- 2026-10-01 Topic history lives on `/topics/:topic_id/messages` (own handler) instead of a
  `topic_id` query on `/messages`, so the frozen history handler and the Redis history cache stay
  untouched; topic pages bypass the cache. It copies `/messages`' ordering and inclusive cursor
  exactly (the lead asked; `message_history` returns the newest page ascending).
- 2026-10-01 Deleting a topic deletes its messages (Telegram), in one transaction: `DELETE FROM
  messages … RETURNING attachment_id`, then the topic row; afterwards
  `recompute_attachment_orphan_status` runs for each returned attachment, so a file still
  referenced by a forwarded copy / favorite / sticker stays, the last reference orphans it for
  the cleanup job. Dependent rows follow their existing `ON DELETE` rules. `messages.topic_id`
  also cascades from `forum_topics`, which only matters for an insert racing the delete.
- 2026-10-01 A topic's effective read cursor is the later of its own cursor and the chat-level
  cursor, not its own cursor alone: otherwise every existing member would see the whole
  pre-forum history as unread in General the moment the forum is enabled, and a frozen client
  that reads the chat as one stream would never clear topics. The React client therefore never
  sends the chat-level `read` frame in a forum chat (`readCursor: false` in the list view, topic
  reads in topic mode); the chat cursor follows only when a topic read leaves zero unread
  anywhere, so the sidebar badge clears. Independence (tested): a topic read never moves another
  topic or the chat cursor; mutes are separate in both directions.
- 2026-10-01 "Topic admin" (manage others' topics, pin, hide, delete, post when closed) =
  `chat.topics` **and** owner/admin role. `chat.topics` is member-toggleable (TG-201), and
  Telegram's member toggle only allows *creating* topics; granting it through the defaults must
  not let every member write into closed topics.
- 2026-10-01 Enabling the forum requires `chat.info`, not `chat.topics`: `ChatType::permits`
  denies `chat.topics` in a `group`, and enabling a forum is what upgrades a group, so a
  `chat.topics` gate could never be passed before the upgrade.
- 2026-10-01 The General row is created lazily (`ensure_general_topic`, idempotent under the
  partial unique index) rather than in `apply_chat_capabilities`, so a forum enabled by any
  path (TG-201's tests call the domain directly) still gets one, and TG-201's file stays as is.
- 2026-10-01 The attachment send paths take a `MessagePlacement {reply_to, topic_id}` in place of
  their `reply_to` argument instead of a new parameter: `content.rs`, `handlers.rs` and
  `upload_handlers.rs` are at their file-size baselines (growth blocked), and it also keeps
  `insert_poll_message` under clippy's argument limit. To stay at baseline, the multipart UUID
  parsing moved to `upload_validation::multipart_uuid`, and `MAX_MESSAGE_CHARS` of
  `upload_handlers` moved to `upload_validation`.
- 2026-10-01 A refused WebSocket `message` (closed / unknown topic) is dropped with a warning,
  like every other refused WS send; the client prevents it by replacing the composer with
  "话题已关闭" for non-admins. HTTP paths answer 403 / 404 / 400.
- 2026-10-01 Forwards and favorite shares always land in General; a closed General refuses them
  (forward: `skipped_reason: "the target topic is closed"`; favorites: the existing
  "cannot send to the target chat", decided inside `forward_favorite` because the favorites
  handler is at its size baseline). Forwarding into a specific topic is not implemented.
- 2026-10-01 Web push: a muted topic suppresses the push of its messages (mentions/replies
  included, like the chat-level mute); `AppState::message_topic_muted` in `delivery.rs`.
- 2026-10-01 Frontend: the topic view is TG-100's `ChatPane` in topic mode (session drops foreign
  broadcasts, merges the topic's newest page before `historyReady`, reads per topic), keyed by
  chat id like every chat — one open topic per chat at a time. HTTP send paths learn the open
  topic from `features/forum/activeTopic` (a per-chat registry) rather than the composer draft's
  `topicId`, which a remote draft update may overwrite.
