## Frozen interface

### `Composer` (packages/web/src/features/composer/index.ts)

```ts
interface ComposerProps {
  chatId: string
  currentUserId: string
  members: readonly ChatMember[]      // @mention source — pass presence.participants (see below)
  session: ComposerSessionApi
  canSend?: boolean                   // default true; ChatPane passes connection === 'online'
}
interface ComposerSessionApi {
  sendMessage(text: string): boolean  // existing ChatSession.sendMessage
  setDraftText(text: string): void    // existing ChatSession.setDraftText (TG-008 draftSync)
  sendFrame(frame: ClientFrame): boolean  // NEW on ChatSession — see integration patch 1
}
```

The component memoises the three functions itself, so `useChatSession(chatId)`'s return value can be
passed directly even though it is a new object each render.

WS naming trap found here: in `auth_ok`/`presence`, `members` = **currently connected** users and
`participants` = **all** chat participants (`src/realtime/ws.rs::member_connected` /
`chat_participants`). Mentions must use `participants`.

### `composerStore` (packages/core) — additive except one type change

- `editing: Record<chatId, EditLayer>` — was `Record<chatId, messageId>`; now
  `{ messageId, originalText, text }`. Only consumer was `stores.test.ts` (updated, one line).
- `forwarding: Record<chatId, ForwardLayer>` — `{ messageIds, fromChatId }`, new.
- `dispatchMode(chatId, event): ComposerModeState` — runs the state machine. Events:
  `reply{messageId}`, `edit{messageId,text}`, `editText{text}`, `forward{messageIds,fromChatId}`,
  `cancel`, `sent`. **This is how message menus (TG-101/103/…) open the bars**:
  `composerStore.getState().dispatchMode(chatId, { type: 'reply', messageId })`. The composer
  pushes any reply-target change into the cloud draft itself.
- `startEditing(chatId, messageId, text = '')` kept (now routes through `dispatchMode`).
- `selectComposerMode(chatId)` — builds an object; for logic, not a raw `useStore` selector.

## Decisions

- 2026-10-01 Bars are **layers**, not one enum: edit overlays reply/forward and cancelling it restores
  them; edit text lives in `editing`, never in the synced draft — so entering/leaving edit never
  PUTs the draft and the draft comes back untouched (Telegram behaviour). Forward and reply are
  mutually exclusive (Telegram Desktop shows one). Escape peels one layer.
- 2026-10-01 `sendFrame` is required on the session rather than opening a second socket: edit only
  exists as a WS frame (`{type:'edit'}`, no REST), and a second chat socket would double presence.
  `chatSession.ts` belongs to features/chat (TG-101 active), so the addition is an integration patch.
- 2026-10-01 Typing is announced by TG-107's `createChatActionSender` (4 s resend window, keep-alive
  for uploads, one `cancel`). The session's legacy `maybeSendTyping` still fires until patch 2 —
  duplicate frames are harmless (receivers key by user) but wasteful.
- 2026-10-01 Uploads: chunked REST (`/api/chats/:id/attachments/uploads` → PUT chunks → complete)
  over an injected fetch in `features/composer/uploadClient.ts`, **without content hash** — the
  server treats it as optional; hashing first would double the wait on large files and needs
  `@noble/hashes` (not in packages/web). Cost: no dedup and no direct-to-OSS upload. A later task
  can add hashing with `hashFile` from core. `ApiClient` could not be reused (JSON bodies only).
- 2026-10-01 One file = one message; caption + reply ride on the first one (server stores one text
  per message). Albums are TG-409-ish scope. Failed items stay for «重试»; caption is not repeated.
- 2026-10-01 Upload progress is shown in the send dialog, not as a timeline placeholder: there is no
  `appendUpload` in `messageStore` (not my path). The completed message arrives as a normal broadcast.
- 2026-10-01 Underline is `<u>…</u>`: markdown has none and the frozen DOMPurify html profile keeps
  `<u>`. Italic uses `_` so it never collides with bold `**` toggling.
- 2026-10-01 Selection toolbar anchors to the field, not the words: a textarea exposes no selection
  rectangle. Moving to contenteditable was out of proportion for this card.
- 2026-10-01 emoji-picker-element is `import()`ed on first open: 13.4 KB gzip separate chunk.
- 2026-10-01 Voice button is rendered disabled («即将推出») until TG-401, per card.
- 2026-10-01 Extras cheap enough to include: ↑ in an empty input edits your last message; a
  «= 84 · Alt+Enter» hint when the draft is pure arithmetic (quick calculator = core `calculator.ts`).
- 2026-10-01 Root CSS class is `tg-compose`, not `tg-composer`: styles/chat.css still styles the old
  minimal composer under that name until the lead deletes it.

## Residual risk

- No content hash on uploads → no server-side dedup / direct OSS upload (see Decisions).
- Password-protected chats: the new client has no chat-password plumbing; uploads send no
  `x-room-password` (same as the rest of the new client today).
- The selection toolbar is field-anchored; long multi-line selections may sit far from the words.
- Forward uses REST `forwardMessages`; its failure is swallowed silently (no toast system yet).
- Minimal `MessageList` (pre-TG-101) shows raw markdown and no attachment previews — the composer
  sends correct markdown/attachments; rendering is TG-101/103's.
