## Frozen interface

- Schema: `chats_title_active_idx` no longer exists on either adapter after `20271001000001_allow_duplicate_chat_titles`. `chats_username_active_idx` (public @username) stays UNIQUE.
- HTTP: `POST /api/chats` and `PATCH /api/chats/:id` no longer answer 409 for a title another active chat already uses (both now 201 / 200). The `is_unique_violation → 409` arms stay for other unique keys. `GET /api/chats?title=` and `GET /api/chats/discover?title=` already returned every match; unchanged.
- CLI: `client join --room-name <t>` resolves only when exactly one visible chat has title `t`. With several matches it exits with an error naming each candidate (`<uuid>  (<n> members[, joined])`) and pointing at `--room-id`. `ChatSummary` gained optional `member_count` (serde default; older servers still parse).

## Decisions

- 2026-10-01 Drop the unique index without a replacement non-unique index, because every title lookup (`AppState::list_chats(Some(title))`, the `/api/chats?title=` filter) runs against the in-memory chat cache, never SQL. An unused index would only cost writes.
- 2026-10-01 Keep the `is_unique_violation → 409` arms in `create_chat` / `update_chat`, because a chat insert still has other unique keys (id, username) and a 409 there is correct; removing them would turn a real conflict into a 500.
- 2026-10-01 CLI candidates come only from `/api/chats` (caller's active memberships) plus `/api/chats/discover` (public, non-password, non-private). Both are already authorised server-side, so the ambiguity error can list them without leaking a chat the caller may not see. A chat listed by both endpoints counts once (dedupe by id) so joining a chat you're already in by name doesn't become falsely ambiguous.
- 2026-10-01 Ambiguity is an error, never a pick (oldest/most members). Silently joining the wrong one of two same-named chats is exactly the class of bug the card forbids.
- 2026-10-01 Resolution logic sits in its own `src/bin/client_chat_lookup.rs` as a pure function so it's unit-testable without a server, and `client.rs` stays small.
