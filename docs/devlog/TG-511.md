## Frozen interface

- `GET /api/users/:id/avatars` → `[{ id, url, is_current, created_at }]`, newest first (TG-505
  profile-photo rule; 404 when hidden). `GET /api/users/:id/avatars/:avatar_id` → the image.
- `PUT /api/users/me/avatars/:avatar_id/main`, `DELETE /api/users/me/avatars/:avatar_id` → `User`.
- Migration `20270201000008_user_avatar_history` (backfills every current photo).
- Web: 设置 › 我的账号 › «头像» (carousel) and «我的二维码»; route `/add/:username`.
- Token `--tg-scan-surface` (both themes, white) — the QR card's background.

## Decisions

- 2026-10-01 `user_avatar_files` stays the "current photo" pointer every existing reader (and
  the frozen clients) uses; `user_avatar_history` keeps every upload. The storage key is the
  photo id (already unique; downloads still go through the privacy check).
- 2026-10-01 Replacing a photo no longer deletes the old file — it lives in the history; switching
  to an emoji avatar clears the pointer but keeps the photos (Telegram keeps them too). Only
  deleting a photo from the history removes its file. Deleting the main photo promotes the next
  newest, or clears the avatar when none is left, so history order and the pointer stay consistent.
- 2026-10-01 The QR encodes an absolute `/add/<username>` link (Telegram encodes `t.me/<name>`).
  It is drawn in the accent on a card that is white in both themes (`--tg-scan-surface`), so it
  scans on the dark theme too; colours are read from tokens at runtime (no literals).
- 2026-10-01 No history cap: Telegram keeps every photo; the photos are small and user-deletable.
