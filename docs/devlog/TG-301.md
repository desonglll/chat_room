## Frozen interface

`@tg/core/domain` (`packages/core/src/domain/tgs.ts`, pure, no dependencies):

- `decodeTgs(bytes, inflate: TgsInflate, limits?) → DecodedTgs` checks gzip magic, file size,
  bounded inflate, JSON, and the Lottie header.
- `parseLottieText(text, limits?)` and `readLottieHeader(json, limits?) → LottieHeader`.
- `isGzip(bytes)`.
- `tgsSpecViolations(header, fileBytes) → ('file-size'|'dimensions'|'frame-rate'|'duration')[]`
  checks Telegram's upload spec. TG-302 can use this for server parity and the client can use it
  for early errors.
- `TGS_RENDER_LIMITS` holds the lenient limits for rendering: 256 KiB file, 4 MiB JSON, ≤1024 px,
  1–120 fps, ≤10 s, ≤1000 layers. `TGS_SPEC` holds Telegram's spec: 64 KiB, 512², 60 fps, 3 s.
- `TgsError { code: 'empty'|'file-too-large'|'not-gzip'|'inflate-failed'|'json-too-large'|'invalid-json'|'invalid-lottie' }`.
- `type TgsInflate = (gzip: Uint8Array, maxOutputBytes: number) => string` must throw once output
  goes over the bound.

`packages/web/src/features/sticker/renderer` (import from `./index`):

- `<AnimatedSticker src | data [cacheKey] size=160 loop=true autoplay=true poster? label? className? onError? manager?>`
  - `src` and `data` are mutually exclusive (a union type enforces this). `data` is a `Uint8Array | ArrayBuffer`
    holding `.tgs` or raw Lottie `.json`.
  - DOM: `span.tg-sticker[data-phase=loading|static|live|error][role=img][aria-label]`, containing
    `img.tg-sticker__still` (the first-frame snapshot, or `poster` until that exists) and
    `canvas.tg-sticker__canvas`.
  - Tapping a sticker that is not `autoplay && loop` plays it once.
- `stickerRenderManager()` returns the page-wide manager. `createBrowserStickerManager(engine?, policy?)`
  and `createStickerRenderManager(services, policy)` expose the seams used by tests and the bench.
- `StickerRenderManager.attach({ element, canvas, source, size, loop, autoplay, onState, onError }) → { replay(), destroy() }`
  is the format-independent seam for TG-306. Visibility, hidden-tab, reduced-motion and cap
  policy all live here, not in the component.
- `StickerSource = { url } | { bytes, key? }`. URLs are fetched with `credentials: 'same-origin'`,
  so attachment authorization applies. TG-302 owns the wire shape; this module needs only a URL.

## Decisions

- 2026-10-01 Decoding rules live in core, and inflate is injected rather than adding pako to
  `packages/core`. Core keeps zero new dependencies, a React Native host can inject native zlib,
  and tests inject Bun's zlib. The web adapter `tgsCodec.ts` wraps pako's `Inflate` with an
  `onData` byte counter that throws mid-stream, so a gzip bomb is stopped before it fully
  allocates. A 16 MiB bomb is tested.
- 2026-10-01 **Canvas renderer**, using lottie-web's `lottie_light_canvas` build. In the per-frame
  cost bench it was cheapest of svg/canvas/html in every run: 24-layer 1.5 vs 2.5 vs 3.0 ms/frame,
  60-layer 6.8 vs 10.9 vs 13.5. Raw 20-sticker page fps was 6.3 vs 4.8 vs 1.0. Canvas is also the
  only renderer that can run off the DOM (in a worker) or snapshot a frame. html was worst on
  every measure. The "light" build has no expression engine, so it has no `eval`. That matters
  because the server CSP is `script-src 'self'`, and the full `lottie.js` build does contain an
  `eval`.
- 2026-10-01 **Rendering runs in a worker pool, not on the page thread.** Raw lottie at 20
  stickers saturated the main thread (cpu 0.99, 29 long tasks in 6 s, page fps 5–6). A
  main-thread renderer with a frame budget kept the page at 60 fps but held stickers to 7–11 fps.
  Workers are sized at ⌊cores/2⌋−1, clamped to 1..4. Each worker runs lottie light canvas into
  an `OffscreenCanvas` and returns `transferToImageBitmap()` bitmaps (zero-copy).
  - lottie needs only a small DOM surface, which I measured in Bun with a logging shim:
    `createElement('canvas')`, `body`, `getElementsBy*`, `readyState`, and `window.Worker`.
    `worker/domShim.ts` provides exactly that, plus `_isProxy`, the flag lottie's own worker
    build uses.
  - lottie's official `lottie_worker` build is unusable here: it spawns a `blob:` worker (blocked
    by CSP) and is the full build, with `eval`.
  - Workers are Vite module workers (`new URL(..., import.meta.url)`), which are same-origin and
    therefore CSP-safe.
  - Fallback: if `Worker`, `OffscreenCanvas` or `transferToImageBitmap` is missing, or the worker
    does not boot within 5 s, the main-thread engine (`mainThreadEngine.ts`) takes over under the
    same `StickerEngine` contract.
- 2026-10-01 **Each sticker key is pinned to one worker**, the least loaded at first load. The
  document is parsed once there, and lottie completes it in place once (`__complete`). All units
  of that key reuse the same parsed object. On the page side, `refCountedCache` refcounts parse
  handles (64 idle kept, then LRU `unload`) and poster object URLs (256 idle, then revoked).
- 2026-10-01 **Render groups share frames.** A group is (key, pixel size, clock). Looping
  autoplay copies of one sticker share one render and blit it to every canvas. Measured result:
  20 copies ran at 60 fps with page cpu 0.20. Play-once and replay views get a private group
  with their own clock.
- 2026-10-01 **One budgeted rAF ticker** (`frameTicker.ts`) drives all groups: 8 ms budget per
  frame, round-robin, and it stops completely when nothing plays. Clocks are time-based, so
  dropped draws never slow an animation down. The fps cap is 60 for ≤4 playing groups and 30
  above that, which halves the work. With the worker engine the ticker only posts requests.
- 2026-10-01 **Frames are requested one stride ahead for async engines** (`RenderUnit.pipelined`).
  Without this, the worker round trip pushed each group to 3 ticks per frame (~20 fps). The
  visible cost is a constant one-frame phase lead.
- 2026-10-01 The **concurrency cap counts render groups, not views**, with 24 as the default.
  The target is 20 distinct stickers plus headroom. Groups already playing keep their slot
  (stability), and the rest go to whichever became visible longest ago. Over-cap views show the
  static first frame. Measured: 60 distinct → 24 animate.
- 2026-10-01 The **first-frame static** is a PNG rendered on one reused snapshot canvas and
  serialized one at a time. On the main thread that is a `canvas`; in each worker it is an
  `OffscreenCanvas`. It shows as `<img>` while a view is loading-complete but not live: off the
  cap, reduced motion, before admission, or after its unit is released. The pre-snapshot
  placeholder is `poster` or a `--tg-skeleton` box.
- 2026-10-01 Pausing and releasing:
  - Off-screen: an IntersectionObserver with a 100px margin. Paused units are released after
    10 s, but never while the tab is hidden, so returning to the tab is not a rebuild.
  - Hidden tab: `visibilitychange` pauses everything.
  - `prefers-reduced-motion`: no units at all, and live views drop back to the still.
- 2026-10-01 Parse and inflate run in the worker, off the page thread. Decode is not
  parallelized further, because the ~1–5 ms per sticker on first sight is not the bottleneck.
- 2026-10-01 Test fixtures are synthetic, generated by the deterministic `fixtures/syntheticLottie.ts`
  with a seed and layers/vertices knobs, rather than copyrighted Telegram stickers. They mimic the
  TGS cost profile: 512², 60 fps, 3 s, and N shape layers, each a morphing 12-vertex bezier path
  with an animated transform and fill, plus a stroke on every third layer. Size: 24 layers ≈
  15 KB gz / 66 KB JSON, which is a typical sticker; 60 layers ≈ 37 KB gz, which is heavy but
  within the 64 KB spec.
- 2026-10-01 The default benchmark raster mode is software (plain headless). The optional
  `BENCH_GPU=1` mode puts SwiftShader in the GPU process, and I measured it as *slower* for the
  worker path (page fps 8.5), because every worker's raster then funnels into one emulated-GPU
  thread. Real GPUs do not behave like that. Software raster is the conservative case.

## Benchmark

Run it with `cd packages/web && node src/features/sticker/renderer/bench/measure.mjs [--quick] [--json f] [--only name] [--shots dir]`.
The script does a production Vite build of `bench/index.html`, serves it with `vite preview`,
and drives headless Chromium via Playwright (`$PLAYWRIGHT_MODULE`, default
`/tmp/pw/node_modules/playwright/index.mjs`). Viewport is 1280×900, stickers are 160 CSS px,
and the page shows 20 distinct synthetic stickers served as `.tgs` object URLs.

Metrics:

- **fps / p95 / drop / long**: rAF sampling in the page, plus `longtask` PerformanceObserver.
- **cpu / js**: busy fraction of one core on the page thread, from CDP `Performance.getMetrics`
  (TaskDuration or ScriptDuration, divided by wall time).
- **sticker-fps**: manager draws ÷ running groups ÷ seconds.
- `cpuOnly` scenarios (off-screen, hidden, reduced motion, idle) skip the rAF sampler, because
  the sampler itself would keep the page rendering.

**Host caveat:** the host was shared with other agents during every run, at load average 23–30
on 16 cores (about 2× oversubscribed). Absolute numbers are pessimistic, and sticker-fps varies
20–30 from run to run.

**Gates (in `measure.mjs` THRESHOLDS) and their justification:**

- `managed-20-onscreen` requires page fps ≥ 50 and p95 ≤ 25 ms. That means the page never janks:
  scrolling and typing matter more than any sticker, and this is the hard requirement. It also
  requires sticker fps ≥ 20, which is two-thirds of the 30 fps cap Telegram-class clients use
  for many simultaneous stickers, and holds even on this oversubscribed host. On an idle machine
  it reaches the cap of 30 (one run here did). Finally it requires page cpu ≤ 0.5, which proves
  the rendering really is off the page thread.
- `managed-20-offscreen`, `-hidden-tab` and `-reduced-motion` require cpu ≤ 0.02. That is the
  card's "off-screen CPU ≈ 0", judged against the 0.001 idle baseline. All three measured 0.000.

**Bundle.** The shipping app does not render stickers yet: TG-303 and the message bubble will
mount `<AnimatedSticker>`. `check_web_bundle.py` is therefore unchanged at 140049 gz out of
500000. Measured chunk sizes:

| chunk | gzip | when it loads |
| --- | --- | --- |
| eager renderer (`AnimatedSticker` + manager + ticker + policy) | ~5.2 KB | on import |
| `workerEngine` | 0.9 KB | lazy |
| `renderWorker` (lottie light canvas + pako inflate + core tgs) | 67.3 KB | lazy, worker |
| `mainThreadEngine` (lottie light canvas + pako) | 56.1 KB | lazy, fallback only |
| full `lottie` | 77.1 KB | bench only, never shipped |

Once integrated, the bundle script (which counts every asset) should grow by about 130 KB gz, to
about 270 KB of the 500 KB budget. A browser downloads either the worker chunk or the fallback,
never both.

## Residual risk

- All numbers come from a shared, about 2× oversubscribed host with software raster. Sticker fps
  varied 20–30 between identical runs. The lead should re-run
  `measure.mjs --only managed-20-onscreen` on a quiet machine before treating the numbers as
  final.
- HiDPI (dpr 2) costs 4× the raster. In software mode it measured 10–18 sticker fps. If real
  devices show the same, cap sticker raster at 1.5× (`MAX_PIXEL_RATIO` in `pageSignals.ts`).
- The worker DOM shim depends on lottie-web 5.13 internals. A lottie upgrade must re-run the
  bench: the worker engine throws, and `engine=worker` makes that loud in the bench.
  Luma track mattes (`tt` 3/4) degrade in the worker, as they do in lottie's own worker build.
- Tap-to-play is a click on a `role=img` span with no keyboard path. TG-303 is expected to wrap
  stickers in its own buttons.
- Synthetic fixtures approximate the cost of real stickers. That has not been validated against
  real TGS files, which were not downloaded because of copyright.
