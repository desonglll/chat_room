## Decisions

- 2026-10-01 Emoji: a pure-JS SHA-1 `digest` is installed as `crypto.subtle` only when it is missing.
  I did not patch or fork `emoji-picker-element`. database.js uses exactly one secure-only API:
  `crypto.subtle.digest('SHA-1')` in `jsonChecksum`, reached only when the data response has no
  ETag. IndexedDB and `btoa` work over http. Ours has no ETag (`src/web.rs::emoji_data_zh`).
  **Suggested lead follow-up** (outside this card): give `/emoji-data-zh.json` a build-time ETag.
  Then the picker skips the checksum and the full re-download on every check.
- 2026-10-01 Voice without a microphone: `<input type=file accept="audio/*" capture>` opens the
  system recorder over http. The file is decoded with `decodeAudioData` on a 16 kHz
  `OfflineAudioContext`. That resamples while decoding, runs faster than real time, and is
  allowed in insecure contexts. Decoding gives the duration and the 100-bar waveform. Ogg,
  WebM and MP4/M4A files are sent unchanged. Anything else the browser decodes (MP3 from Xiaomi
  recorders, AAC/ADTS, WAV, FLAC …) is re-encoded as 16 kHz mono 16-bit WAV, and the server now
  accepts WAV. I picked WAV over teaching the server MP3, because WAV duration is a header read
  (about 30 lines) while MP3 needs Xing/VBR parsing. One WAV conversion also covers every
  decodable input. A file the browser cannot decode (e.g. AMR) is refused with «无法识别该录音格式»,
  because it would not play for anyone either.
- 2026-10-01 Round video without a camera: `accept="video/*" capture="user"`. A file that fits the
  server's limits (MP4/WebM, ≤ 16 MiB, ≤ 61 s) is sent as a round video unchanged, with a
  best-effort 96 px JPEG thumbnail. **Anything else is sent as a regular video message** through
  the existing chunked `uploadAttachment`, with the notice «视频超过 16 MB 或 60 秒，已作为普通视频发送».
  I did not re-encode in the page through canvas + MediaRecorder. That needs the file's sound
  played back. After a file picker closes, mobile browsers (iOS Safari especially) may refuse
  playback with sound, and a muted element feeds silence into a MediaElementSource. A phone's
  1080p clip passes 16 MiB after about 8 s, so long clips do take the regular path.
- 2026-10-01 Gesture in capture mode: a tap still toggles mic ↔ camera. Press-hold-release, or
  Enter/Space, opens the picker. A file picker needs a user activation. On touch screens that
  means `pointerup`, not `pointerdown`, so "hold to start" cannot open it the way it starts live
  recording. Labels are unchanged («按住录制…»). A 4 s secondary line says why the system app
  opened: «通过 HTTP 访问时将使用系统录音机/相机».
- 2026-10-01 Location without GPS: the dialog keeps the reason as a red secondary line. HTTPS is
  named when `isSecureContext === false`, which is checked before asking, because insecure
  pages keep `navigator.geolocation` but always answer PERMISSION_DENIED, which read as the
  wrong «未获得定位权限». Below it is Telegram's picker: the pin is fixed at the centre and the map
  moves under it, and a tap pans that spot to the pin. «发送所选位置» sends a static location.
  Live location needs the device position and is not offered there; a line says so. The start
  view is 30°N 110°E, zoom 4 (China), because the UI is Chinese-first. Leaflet is lazy-loaded
  only on this path.
- 2026-10-01 Browser check used the server's **embedded** production bundle opened via the LAN
  IP, not `vite preview`. The private `CARGO_TARGET_DIR` guarantees the embedded bundle is this
  worktree's. `vite.config.ts` hard-codes the proxy target to :3000. This is also the real
  production path, with the service worker.
- 2026-10-01 `NotFoundError` now maps to `nodevice` («没有找到麦克风/摄像头») instead of the generic
  `device` («…不可用»). Two existing recorder tests asserted the old mapping and were updated.

## Residual risk

- Real phones were not tested. Headless Chromium on a LAN IP reproduces the insecure context
  exactly, but not the capture UIs. iOS Safari ignores `capture` for `audio/*` and shows a Files
  picker (Voice Memos m4a works through it). Android opens the recorder app.
- An AMR-in-3GP recording (some Huawei recorders) is refused as unreadable. Browsers cannot play
  AMR, so sending it would only produce a broken bubble.
- An iPhone HEVC `.mov` that fits the limits is sent as a round video unchanged; Android peers may
  not decode HEVC.
- The picker's start view assumes users are in China; there is no place search.
