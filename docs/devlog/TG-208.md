## Audit (what was actually duplicated)

Messages were already single-path before this task: WS send, `GET /api/chats/:id/messages`,
search, pins, files all key on `messages.room_id` and authorize with `has_chat_permission`,
whatever the chat type. The duplication was elsewhere:

1. **Provisioning** — `direct_conversations::store::start_direct_conversation` carried its own
   copy of the `INSERT INTO chats / chat_roles / chat_role_permissions / chat_members` SQL,
   parallel to `chats::provisioning::create_chat_with_owner`.
2. **Type discrimination by side table** — `is_direct_chat` / `direct_room_ids` asked
   `direct_conversations` "is this private?" in 9 call sites, although `chats.chat_type`
   has said so since TG-004. `/api/conversations` derived `kind` the same way.
3. **Listing** — `/api/chats` filtered private chats out, so a client had to fetch private
   chats from `/api/conversations` and groups from `/api/chats`: two data paths.
4. **Presentation** — the peer-as-title rule lived only inside the conversations SQL, and
   `GET /api/chats/:id` reached it by running the whole conversation-list query.

## What changed

- `src/direct_conversations/` is now `mod.rs` + `index.rs`: `chat_for_pair`, `record_pair`
  (index statements, executor-generic so they join the caller's transaction) and
  `AppState::private_chat_peers(viewer)` (chat id → peer profile + viewer's remark).
  No handler, no chat/role/member/message SQL.
- `src/chats/provisioning.rs`: the four statements (`insert_chat_row`, `insert_system_role`,
  `grant_role_permission`, `upsert_active_member`) are executor-generic functions; group
  creation and private-chat creation both call them.
- `src/chats/private_chats.rs` (new): `open_private_chat` (friendship lock + block check +
  index lookup + provisioning, one transaction), `is_private_chat` (reads `chat_type` from
  the chat cache), `present_private_chats` / `PrivateChatPeer::present` (peer-as-title rule).
- `src/chats/private_chat_handlers.rs` (new): `POST /api/direct-chats`, moved verbatim from
  `direct_conversations::handlers`, same request/response.
- `src/chats/query_handlers.rs`: `/api/chats` lists private chats (canonical dialect only),
  `/discover` and `GET /:id` decide by `chat_type`.
- `reject_direct_chat` → `reject_private_chat` (by `chat_type`), used by membership,
  governance and lifecycle handlers; 404 behaviour unchanged.
- `src/conversations/`: `kind` and the title/avatar/description CASEs now key on
  `chats.chat_type = 'private'`; new `chat_type` field on `ConversationSummary`.

## Decisions

- 2026-10-01 `/api/rooms` keeps hiding private chats, only `/api/chats` shows them, because the
  frozen Vue / PySide6 / ratatui clients render `/api/rooms` + `/api/conversations` side by
  side and would otherwise list each private chat twice. `ApiDialect` already distinguishes
  the two mounts, so this costs one `if`.
- 2026-10-01 "Is this chat private?" is answered by `chats.chat_type`, never by the index,
  because `CONTEXT.md` makes Chat Type the authoritative shape and TG-004 backfilled it for
  every `direct_conversations` row. The index only maps pairs ↔ chat ids.
- 2026-10-01 Statement helpers are generic over `sqlx::Executor` (one statement each) rather
  than duplicated per adapter or shared as SQL string constants, because the private-chat
  transaction must run index writes and chat provisioning atomically, and inside `with_pool!`
  both arms instantiate the same generic call. `knowledge/store.rs` is the precedent for
  `DB: sqlx::Database` bounds.
- 2026-10-01 No `peer` field was added to `Chat`: `Chat` is built with explicit struct
  literals in ~8 files outside this card (ai, push, knowledge, tests), so a new field is a
  cross-module change. The peer's identity stays available from `/api/conversations[].peer`
  and from WS `auth_ok.participants`. If the React client needs it on `/api/chats`, that is a
  follow-up for the lead to assign (see Residual risk).
- 2026-10-01 `GET /api/chats/:id/members` stays 404 on a private chat (it is the
  `members.review` roster-admin surface, not a member-visible list); unchanged behaviour.
- 2026-10-01 The `/api/chats?title=` filter now applies to the *presented* title, so a private
  chat is found by its peer's name rather than its internal `direct-<uuid>` placeholder.
- 2026-10-01 `realtime/ws.rs` still titles `auth_ok.room_name` via `conversation_summary`;
  left alone because it is outside this card and already applies the same rule.
