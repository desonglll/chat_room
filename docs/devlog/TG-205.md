## Frozen interface

### Schema (`20261101000006_add_chat_invite_links`)

- `chat_invite_links(id, room_id → chats ON DELETE CASCADE, token UNIQUE, creator_user_id →
  users ON DELETE SET NULL, title '', expires_at NULL, usage_limit NULL CHECK > 0,
  usage_count ≥ 0, requires_approval, is_primary, revoked_at NULL, created_at)`;
  `CHECK NOT (requires_approval AND usage_limit IS NOT NULL)`.
- `chat_invite_links_primary_idx`: unique `(room_id) WHERE is_primary AND revoked_at IS NULL`
  — at most one live primary per chat.
- `chat_members.invite_link_id → chat_invite_links ON DELETE SET NULL` (+ index
  `(invite_link_id, status)`): which link admitted or queued a member.

### HTTP

Management (canonical `/api/chats/:id` only — not on the `/api/rooms` alias). Gate
("link manager"): `members.invite` decided by `authorize_chat_action` **and** role owner/admin
(or creator / system administrator). Another administrator's non-primary link additionally
needs `members.promote`; the primary link belongs to the chat (any link manager).

| Method | Path | Answer |
| --- | --- | --- |
| GET | `/invite-links` | `InviteLinksView {links[], can_review, can_manage_others}`; issues the primary link on first read |
| POST | `/invite-links` | `InviteLinkRequest {title ≤32, expires_at future \| null, usage_limit 1–99999 \| null, requires_approval}` → 201 `InviteLink`; 400 invalid (limit + approval = 400) |
| PUT | `/invite-links/:link_id` | same body, replaces settings, token unchanged → `InviteLink`; 409 revoked or primary |
| POST | `/invite-links/:link_id/revoke` | → revoked `InviteLink`; revoking the primary issues a new primary atomically |
| POST | `/invite-links/primary` | "替换链接": revoke live primary + issue new one atomically → new `InviteLink` |
| DELETE | `/invite-links/:link_id` | 204; 409 while the link is live |
| GET | `/invite-links/:link_id/members` | `InviteLinkMember[]` active members it admitted, newest first, ≤200 |
| GET | `/invite-links/:link_id/requests` | `InviteLinkMember[]` pending requests it queued |

`InviteLink {id, chat_id, token, title, creator_id, creator_name, expires_at, usage_limit,
usage_count, requires_approval, is_primary, revoked_at, created_at, pending_count, state}`,
`state ∈ active | expired | limit_reached | revoked`, computed at read time from the clock.
`InviteLinkMember {user_id, username, display_name, avatar_emoji, status, requested_at,
joined_at}`.

Link holder (session required):

| Method | Path | Answer |
| --- | --- | --- |
| GET | `/api/invite-links/:token` | `InvitePreview {title, description, avatar_emoji, chat_type, member_count, requires_approval, membership_status, chat_id}` (`chat_id` only once an active member) |
| POST | `/api/invite-links/:token/join` | 200 `{status:"active", chat_id}` (joined or already a member) · 202 `{status:"pending", chat_id:null}` |

Refusals carry `{"error": reason}`: 404 `not_found`, 410 `expired` / `limit_reached` /
`revoked`, 403 `banned`, 423 `locked`.

Approval links reuse the existing queue: the joiner becomes `chat_members.status='pending'`
(with `invite_link_id`), the existing notification trigger fires, and the existing
`PATCH /api/chats/:id/members/:user_id {action: approve|reject}` settles it; an approval
counts as one use of the link.

Audit events (no token): `room.invite_link.created|edited|revoked|deleted|replaced`, target
`invite_link`.

## Decisions

- 2026-10-01 There was no token-based invite mechanism to migrate: the existing "invite" is the
  direct add (`POST /invitations`, `members.invite`, TG-505 `group_invites` privacy) and the
  queue is `chat_members.status='pending'`. Both stay untouched; links are a new table plus a
  nullable `chat_members.invite_link_id`, and approval links write into the same queue so the
  existing approve/reject action, notification trigger and pending counts keep working.
- 2026-10-01 The management right is `members.invite` **held by an owner/admin**, not
  `members.invite` alone, because `members.invite` is also a member-toggleable default
  ("添加成员"); in Telegram ordinary members with "add users" do not manage the chat's links.
  The key the brief calls `chat.invite_users` is TG-201's `members.invite`.
- 2026-10-01 The usage limit is enforced by one conditional `UPDATE … usage_count + 1 WHERE …
  usage_count < usage_limit` inside the join transaction, followed by the membership upsert
  `… ON CONFLICT DO UPDATE … WHERE status <> 'active'`; zero rows from the upsert rolls the
  increment back (an existing member never consumes a use, even under concurrent joins by the
  same account). PostgreSQL's row lock + READ COMMITTED re-check and SQLite's writer lock make
  it exact; the concurrency test proves 40 joiners at limit 5 → exactly 5 on both.
- 2026-10-01 A limit and an approval flag exclude each other (CHECK + 400), as in Telegram;
  otherwise approving a request would need its own conditional increment.
- 2026-10-01 An additional link dies with its creator's management right, checked at use time
  (read-time re-authorization): dismissing or removing an admin kills the links they issued
  without a sweeper. The primary link belongs to the chat and survives its creator.
- 2026-10-01 The primary link is issued lazily on the first `GET /invite-links` by a link
  manager (idempotent through the partial unique index), not at chat creation, so no existing
  creation path or migration backfill had to change.
- 2026-10-01 Token = 32 bytes from two v4 UUIDs (OS CSPRNG) as base64url, 43 chars; stored in
  plain text because administrators copy it again (Telegram does the same); never logged, only
  returned to link managers. Malformed tokens are rejected before SQL.
- 2026-10-01 `expires_at` is truncated to whole seconds on write: SQLite compares the stored
  RFC 3339 text, which is order-correct only at one precision.
- 2026-10-01 The preview withholds `chat_id` until the viewer is an active member (the preview
  has no use for it; TG-206 will decide public id exposure).
- 2026-10-01 Link routes are canonical-only; the frozen clients behind `/api/rooms` predate them.
- 2026-10-01 TG-505's `group_invites` privacy rule still gates only direct adds; a link is the
  joiner's own action, so it is not consulted (unchanged `invite_member`).
- 2026-10-01 UI: the entry checks `GET /permissions` (side-effect free) rather than the list,
  which would issue a primary link merely by opening chat info. Confirmations for revoke /
  replace are inline, not modal dialogs. `/joinchat/:token` rather than `/+token`: a
  react-router segment cannot carry a literal `+` prefix before a parameter.

## Residual risk

- `/joinchat/:token` sits behind `RequireSession`; an anonymous visitor is redirected to
  `/login` and the token is lost (LoginPage does not keep a return path — not this card's file).
- The primary link is issued lazily; a chat whose managers never open the page has none, and
  the chat header offers no "share link" shortcut yet.
- `invite_link_members` returns at most 200 rows (no paging); fine for per-link stats of
  ordinary groups, not for a primary link of a 200 000-member supergroup.
- A pending request queued by an approval link keeps `invite_link_id` if the link is later
  revoked; approving it still counts against (and is listed under) the revoked link, which is
  what Telegram shows too.
