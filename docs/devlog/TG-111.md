## Frozen interface

- `storage::open_memory_database(&AttachmentStore) -> Result<SqlitePool>`: signature
  unchanged. New guarantee: the database survives any pooled-connection replacement for as
  long as the pool is alive; each call is a separate, isolated database. Consumers:
  `AppState::new()` / `new_with_config()` (tests and throwaway dev servers only; the server
  binary opens a file or PostgreSQL).
- No HTTP, WebSocket, schema, or migration change.

## Decisions

- 2026-10-01 In-memory DB is a uniquely named shared-cache memory database
  (`file:chat-room-memory-<uuid>?mode=memory&cache=shared`) plus a detached
  **anchor** connection, instead of file-backed temp SQLite, because it fixes every
  `AppState::new()` suite at the source with no temp-file cleanup, and keeps tests fast.
  A private `:memory:` DB lives exactly as long as its one connection, so any sqlx discard
  (aborted forwarder, failed on-release ping) swapped in an empty DB.
- 2026-10-01 `mode=memory` goes in the URI, NOT sqlx's `.in_memory(true)`: that sets the
  `SQLITE_OPEN_MEMORY` open flag, and `VACUUM INTO <path>` then creates its target as an
  in-memory database too, so `admin_backup_test::backup_endpoints_require_admin_and_support_sqlite_exports`
  failed deterministically (500: the dump file never reached disk). Found by the first full
  run; fixed; guarded by `memory_database_never_touches_the_working_directory` (URI must not
  be taken as a literal filename) and by the backup test itself.
- 2026-10-01 The anchor is held by a spawned task that awaits `pool.close_event()`, not a
  field on `AppState`, because `src/state*.rs` is lead-owned and `close_event` does not
  hold the pool (sqlx `PoolInner::drop` fires it), so the anchor never extends the pool's
  life and closes when the last pool handle drops. If the runtime ends first (end of a
  `#[tokio::test]`), the task and anchor drop with it.
- 2026-10-01 Pool stays at `max_connections(1)`: the anchor is idle, so shared-cache
  table locks never contend in steady state; during churn sqlx's unlock-notify handles
  SQLITE_LOCKED.
- 2026-10-01 Rate-limit test: window 2 s → 600 s instead of an injectable clock, because
  the Redis adapter is INCR + EXPIRE on first hit (window starts at the first request, no
  bucket boundary), so a long window is fully deterministic; isolation already comes from a
  per-test UUID key prefix. Strengthened instead of weakened: the test now reads Redis and
  asserts both the IP and account counters are 3 (attempts from both instances), proving the
  429 came from shared state and not a local fallback, then DELs the keys.
  `src/security/rate_limits.rs` untouched.
- 2026-10-01 Reverted TG-505's file-backed workaround in `tests/privacy_support/mod.rs`
  to `AppState::new()`: the regression test reproduces the exact failure on the old code
  and passes on the new; the privacy suites then ran 20x clean on the in-memory DB.

## Residual risk

- `PoolCloseEvent` only fires on an explicit `pool.close()`; if a pool is merely dropped, the anchor
  task lives until its runtime shuts down. Harmless for tests (one runtime per test) and for the
  in-memory dev server (one pool per process), but it is not a general-purpose pattern.
