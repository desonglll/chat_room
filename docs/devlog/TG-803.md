## Frozen interface

- `GET /api/chats/:id/files?kind=` gains `media` (photo + video, no GIF/sticker/round video/voice),
  `document` (everything else that is not voice/round video/sticker/GIF — music included),
  `voice` (voice + round video), `gif` (`media_kind = 'gif'` or `image/gif`). Existing
  `all|image|video|file` unchanged; anything else → 400.
- `GET /api/chats/:id/links?before=<cursor>&limit=1..100` → `{ items: [{ message_id, position, url,
  sender_id, sender, created_at }], next?: "<message_id>:<position>" }`, newest first. Same gate as
  `/files` (active member via `can_read_chat`, chat password header); recalled messages excluded;
  malformed / foreign cursor → 400.
- Tables `message_links (message_id, position) PK, room_id, url, created_at` and
  `chat_link_index_state (room_id PK, indexed_created_at, indexed_message_id, edits_seen_at)`,
  both cascading from `messages` / `chats`.

## Decisions

- 2026-10-01 **Backfill strategy: lazy, per chat, on read.** The link index is a projection; it is
  brought up to date when the «链接» tab is read: (1) messages edited since `edits_seen_at` that the
  cursor already passed are re-extracted (delete + insert), (2) messages after the cursor are
  extracted in batches of 500, at most 20 batches per request. Existing history is therefore
  backfilled on first read (a chat with >10k messages finishes over a few reads; the newest page is
  only complete once the cursor has caught up — acceptable for a history tab, and the cost is paid
  once). Chosen over write-path hooks because there are many send paths (text, album, poll,
  forward, scheduled, voice…) and a missed hook would silently lose links; chosen over a
  migration-time SQL backfill because URL extraction is not portable SQL.
- 2026-10-01 Each batch writes its links and advances the cursor in one transaction; inserts are
  `ON CONFLICT DO NOTHING` and the cursor upsert only moves forward, so concurrent readers can at
  worst redo a batch.
- 2026-10-01 Hidden `text_link` entity targets are indexed after the visible URLs (Telegram's tab
  shows both). Max 20 links per message; URL length ≤ 2048; http(s) with a host only.
- 2026-10-01 The extractor stops at full-width Chinese punctuation (stricter than TG-408's
  `first_url`, which only trims it) because Chinese text rarely puts a space after a link.
- 2026-10-01 Kind predicates are static SQL fragments chosen by a closed `match`; nothing the client
  sends reaches the SQL text. `media_kind` is checked before MIME so voice is never a "file" and a
  sticker never a "photo".
- 2026-10-01 Client: the tabs call their own server kind; the TG-106 `filteredSource` client-side
  narrowing (bounded 4 raw pages per load) is deleted with its test — every page is now a full page.
- 2026-10-01 Member pagination: already server cursor-paged since TG-201 (`memberPageSource`);
  verified, no change. TG-106 leftovers verified already done on main: `WorkspaceShell` mounts
  `<InfoPane />` unconditionally, the chat header toggles it (`toggleChatInfo`), and the old panel
  styles are gone from `styles/shell.css` (149 lines, no `.tg-shell__info`).

## Residual risk

- First read of the link tab in a very large chat does up to 10k message extractions inside the
  request (bounded, but a few hundred ms on SQLite).
- An edit that happens while a refresh runs between its edit pass and its commit is caught on the
  next refresh, not the current one (`edits_seen_at` is taken at refresh start).
- `/files?kind=document` includes music; Telegram has a separate «音乐» tab. Not on the card.
