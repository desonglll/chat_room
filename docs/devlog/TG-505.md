## Frozen interface

HTTP (both under `/api/users/me/privacy`, bearer required, 401 otherwise):

- `GET /api/users/me/privacy` → `{ rules: PrivacyRuleView[] }`, always five entries in the
  order `last_seen, profile_photo, forwards, group_invites, voice_messages`.
- `PUT /api/users/me/privacy/:key` body `{ tier, allow_user_ids?: uuid[], deny_user_ids?: uuid[] }`
  → `PrivacyRuleView`. Replaces the tier and both lists atomically. 400 for an unknown key,
  unknown tier, unknown account id (whole write rolled back), or > 1000 exceptions. The
  owner's own id is dropped; an id in both lists is stored as deny.
- `PrivacyRuleView = { key, tier: 'everybody'|'contacts'|'nobody', allow_users: UserSummary[], deny_users: UserSummary[] }`
  (`UserSummary` = existing `{ id, username, avatar_emoji, display_name }`).

Behaviour on existing read paths:

- WS `auth_ok.statuses`: per viewer. Exact viewers get `online` / `offline{last_seen}` /
  `empty` (never seen); everyone else gets `recently|within_week|within_month|long_ago`.
- WS `auth_ok.members`, `presence.members`, `system.members`: connected accounts whose exact
  presence the viewer may not see are removed. `user_status` frames about such an account
  are not delivered to that viewer at all.
- `GET /api/users/:id/avatar`: optional bearer; refused viewer → 404 (same as "no avatar").
  Anonymous only when tier = everybody, no deny exceptions, and the owner blocks nobody.
  `Cache-Control: private, max-age=300` with a bearer, `public, max-age=300` without
  (was `public, max-age=31536000, immutable`).
- `POST /api/messages/forward` and `POST /api/favorites/:id/forward`: when the author's
  `forwards` rule refuses the forwarder, `forwarded_from.sender` (and `room_name` for a
  direct-chat source, which is the author's name) is stored as `隐藏的账号`
  (`chat_room::accounts::privacy::HIDDEN_FORWARD_LABEL`).
- `POST /api/chats/:id/invitations`: 403 when the invitee's `group_invites` rule refuses the inviter.
- `AppState::voice_message_allowed(sender, recipient) -> Result<bool>`: TG-401 must call
  it before accepting a voice message in a private chat (no voice messages exist yet).

Rust: `chat_room::accounts::privacy::{PrivacyKey, PrivacyTier, decide, PrivacyFacts,
obscured_status, LastSeenRecord, HIDDEN_FORWARD_LABEL}`, `AppState::privacy_allows`,
`AppState::privacy_settings`, `AppState::privacy_rule`, `AppState::last_seen_record`.

Frontend: `@tg/core` exports `PRIVACY_KEYS`, `PRIVACY_TIERS`, `PrivacyKey`, `PrivacyTier`,
`PrivacyUser`, `PrivacyRule`, `PrivacySettings`, `PrivacyRuleWrite`, `privacyRuleWrite`,
`createPrivacyApi(client, token)`. `packages/web/src/features/settings/privacy` exports
`PrivacySettingsPage({ api?, initialRules?, initialKey?, onBack? })`.

Schema: `user_privacy_rules(user_id, privacy_key, tier, updated_at, PK(user_id, privacy_key))`,
`user_privacy_exceptions(user_id, privacy_key, target_user_id, effect, created_at,
PK(user_id, privacy_key, target_user_id), CHECK(user_id <> target_user_id))`,
`user_last_seen(user_id PK, last_seen_at, prior_seen_day)`. All cascade from `users`.

## Decisions

- 2026-10-01 Decision order is self → owner blocked viewer → exception (deny/allow) → tier,
  because Telegram treats a block as stronger than any list and exceptions as stronger than
  the tier. An id sent in both lists is stored as deny (fail closed) rather than rejected,
  so a racing UI can never produce a 400 that loses the whole edit.
- 2026-10-01 "Contacts" = accepted friendships, the only contact relation in the product;
  it is mutual, unlike Telegram's one-directional contacts.
- 2026-10-01 Phone-number dimension skipped: accounts have no phone numbers. The DB CHECK
  rejects `phone_number` so nobody adds it by accident.
- 2026-10-01 Obscured last-seen is a function of UTC days only: today and the day of the
  latest activity strictly *before* today (`prior_seen_day` column keeps it once today has
  activity). Computing it from the exact time lets a poller recover the time from the moment
  the tier flips; computing it from today's activity lets a poller see the exact moment the
  owner comes online. Cost: an account active only today reads "long ago" to obscured
  viewers until midnight (includes brand-new accounts and, once, every account after the
  upgrade). Thresholds: ≤3 days recently, ≤7 within week, ≤30 within month.
- 2026-10-01 Hidden viewers get no live `user_status` frame and no connected-member entry
  for the owner, not a bucket frame: the frame's arrival time is itself the leak.
  Telegram also shows "last seen recently" rather than "online" to such viewers.
- 2026-10-01 Reciprocity: exact presence requires both the owner's rule to admit the viewer
  and the viewer's rule to admit the owner (Telegram).
- 2026-10-01 Live sockets cache the viewer's privacy context for 15 s (`PRESENCE_RULES_TTL`)
  instead of querying per frame, because a Presence frame fans out to every connection of
  the chat on each connect/disconnect; rule changes reach open sockets within 15 s.
- 2026-10-01 last_seen persisted on WS connect, disconnect, and every heartbeat but at most
  once per 60 s per connection, in a separate `user_last_seen` table (not a `users` column)
  so no existing `SELECT ... FROM users` changes and ownership stays in this task.
- 2026-10-01 Forwards: Telegram keeps the name and drops the account link; forwards here
  carry only a name, so the name is what the rule withholds (`隐藏的账号`). Evaluated
  against the forwarder at write time (the forward is a snapshot, like the name was).
- 2026-10-01 Avatar privacy is enforced on the image endpoint, not by rewriting every
  `avatar_emoji` URL projection (sender snapshots, member lists, search …): the URL is an
  identifier, the bytes are the photo. Anonymous requests are admitted only when no signed-in
  viewer could be refused, otherwise dropping one's bearer would bypass the rule.

- 2026-10-01 Build directory: per the lead's Hazard-2 notice, all recorded cargo results
  come from the private `CARGO_TARGET_DIR=/home/mike/workspace/.cargo-target/tg-505`
  (`CARGO_BUILD_JOBS=6`, dev/test debug info off). Delete that directory after merge.
  Earlier, while still on the shared dir, clippy linked the test crates against another
  worktree's `chat_room` rmeta (fingerprint dep-info held the other worktree's paths, so
  `touch` could not invalidate it); `cargo clean -p chat_room` on the shared dir fixed it
  once and removed ~46 GiB of chat_room artifacts other worktrees then had to rebuild.

- 2026-10-01 (post-merge) `hidden_viewers_receive_no_live_presence_of_the_owner` failed
  deterministically on merged main (`ecd8e78`): a test-ordering assumption, not a product
  bug. The owner's `user_status` online frame is broadcast after `auth_ok` (behind history
  replay) and the offline frame after the disconnect bookkeeping, but the test broadcast its
  marker right after `open_chat` / `close_and_settle` returned, so the marker could overtake
  the frame; with main's heavier replay (TG-302 sticker columns) it always did. The fix: the
  test first waits (5 s frame timeout) for the admitted viewer to receive the owner's
  online/offline frame, and only then broadcasts the marker. Because the chat channel is a
  single ordered broadcast, the hidden viewer's stream would then hold that same frame before
  the marker, so the "never delivered" assertion is no longer vacuous. Presence emission itself
  was never broken: the admitted viewer always receives the frame, which the wait proves.

- 2026-10-01 (post-merge 2) `privacy_matrix_test::sqlite_…` failed ~1 in 4 with a 500 on
  `PUT /api/users/me/privacy/last_seen`. Captured server error (temporary eprintln, since
  removed): `no such table: sessions` — the whole database had vanished. Root cause is
  **harness-specific**: `AppState::new()` is `:memory:` behind a one-connection pool
  (`src/storage.rs::open_memory_database`). Closing a WebSocket aborts its forwarder task;
  if the abort lands while the forwarder holds the connection mid-query (message polling,
  or TG-505's presence-rule reload triggered by the Presence frame every disconnect
  broadcasts), sqlx discards that connection and the pool opens a new one — a fresh, empty
  in-memory database. The PUT was just the first request to hit it. Production cannot lose
  data this way: file SQLite (3-connection WAL pool) and PostgreSQL reopen the same
  database. It is not write contention (no "database is locked"; busy_timeout irrelevant)
  and not the 60 s last-seen writer. Fix: `tests/privacy_support::start_server` now runs on a
  scratch file-backed SQLite (`AppState::open`), removed on drop. Every other suite that
  uses `AppState::new()` + WebSockets carries the same latent hazard (TG-208 reported it);
  a lead-level fix would be to keep an anchor connection to a named shared-cache memory
  database in `open_memory_database`, which is outside this card.

## Residual risk

- `avatar_emoji` still carries the avatar URL everywhere; a refused viewer learns that a
  photo exists (and its version), not the photo. The legacy Vue client loads avatars with
  anonymous `<img>`, so restricted owners' photos no longer show there even to admitted
  viewers; the React client does not render avatar images yet — when it does, it must fetch
  with the bearer (blob URL), not a bare `<img src>`.
- Poke (`src/realtime/inbound.rs`) only succeeds for connected targets and broadcasts a
  `poke:` system frame — an online oracle for accounts in the same chat. Left untouched
  (out of card scope); lead should decide whether poke should respect `last_seen`.
- Typing and sent messages reveal activity by nature (Telegram also shows them).
- Rule changes reach already-open sockets up to 15 s late.
- `/api/users/search` results and `GET /api/users/:id` are unchanged (no presence in them).
