## Frozen interface

- `ComposerSessionApi.sendMessage(text, { silent?, noLinkPreview?, entities? })` and `SendMessageOptions.entities?: MessageEntity[]`. The entities' offsets refer to the already-trimmed text. The session puts them on the `message` frame and on the optimistic row only when non-empty, so the wire is unchanged for plain text.
- `ComposerController.insertCustomEmoji(selection, { id, emoji }) → { text, caret } | null`. Returns null while editing (the host then inserts the plain fallback character).
- `ComposerInputHandle.insertCustom(emoji)`.
- `createOptimisticMessage` input gains `entities?`.
- `messageStore.applyEdit` replaces `entities` with `frame.entities ?? []`. This is a behaviour change: stale ranges no longer survive an edit.
- `compareInstants` breaks millisecond ties on the sub-millisecond fraction (µs/ns).
- New component `features/composer/ComposerEmojiTab.tsx`. The media panel's «表情» tab now has «标准 | 自定义» segments.

## Decisions

- 2026-10-01 The entity draft lives in the non-React `composerController`, not in `Composer.tsx` via `useEntityDraft`, because every text change already funnels through `controller.input` and the controller is what the existing harness tests drive end to end over a real `createChatSession`. The hook would have needed a second sync point in the view.
- 2026-10-01 Custom emoji are refused in edit mode (null → plain fallback character inserted), not supported, because the `edit` path sends `content` only. Making edits carry entities is a separate change with its own server round-trip test.
- 2026-10-01 Scheduled messages do not carry entities: `schedulePayload` stays text-only. The emoji goes out as its plain fallback character. The scheduled API has no entities field, and adding one is a server change outside this card.
- 2026-10-01 The inner tab is labelled «标准» (en "Standard"), not «表情», because the outer media-panel tab is already «表情». Two tabs with one name are ambiguous for screen readers and for `getByRole`.
- 2026-10-01 Changed `Permissions-Policy` `geolocation=()` → `geolocation=(self)` in `src/security/headers.rs` (outside the card). Running the E2E against the real server's headers (not `vite preview`) showed every location share failing with PERMISSION_DENIED: Chromium reports "Geolocation has been disabled in this document by permissions policy". TG-401 had pinned `geolocation=()` on purpose; TG-407 later shipped browser-geolocation sharing without revisiting it, so production could never share a location. `(self)` matches camera/microphone: own pages only, no frames (CSP `frame-ancestors 'none'` already). `tests/voice_messages_test.rs` now pins `geolocation=(self)`.
- 2026-10-01 The E2E runs against this worktree's own embedded bundle (private `CARGO_TARGET_DIR` → `build.rs` embeds this worktree's `packages/web/dist`, service worker on), not `vite preview`. The vite proxy is hard-wired to :3000, and the embed is the production path anyway.

## Residual risk

- Cloud drafts are text-only. A draft restored on another device holds the fallback character without its entity, so it sends as a plain emoji. Telegram syncs draft entities; ours does not.
- Editing a message that has custom emoji from the web drops them server-side: the web `edit` frame sends no entities, and the server (`src/realtime/inbound.rs` edit path) stores and broadcasts exactly the frame's entities. `applyEdit` now mirrors that truth; before this card the client kept showing stale emoji that the server no longer had. The fix is to make the edit path carry entities (follow-up).
