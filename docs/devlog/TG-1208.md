## Frozen interface

- `ChatSession.sendable(): boolean` and `ChatSession.onSendable(handler) → unsubscribe` (new). True while the chat is opening — before the session's first `history_complete`, socket not `failed` — and, once ready, while the socket is `online`. `useChatSession` returns it as `sendable`; `ChatPane` passes `canSend={sendable && slowMode.wait === 0}` (was `connection === 'online' && …`).
- `ChatSession.sendMessage` contract change: while opening, the send is parked (optimistic row in `sending`), returns `true`, and its `message` frame goes out right after the first `history_complete`, in order. Auth failure or `stop()` marks parked rows `failed`. After the session has been ready once, a send while not online is still refused and the row marked `failed` (unchanged).
- `mergeIncomingBroadcast` (core): a confirmed broadcast that is new to the list is inserted before the trailing run of in-flight own sends (`pending:` id AND `delivery_state: 'sending'`); a `failed` row keeps its place. Duplicates and reconciliation are unchanged.
- `deriveChatRowPresence(presence, conversation, currentUserId, peerStatus?)`: `isOnline` is `peerStatus.kind === 'online'` (the privacy-filtered `presenceStore.users[peer]`, the header's source); `undefined` when no status is known.
- `ChatListRowProps.titleAdornment?: ReactNode` (rendered after the title).
- `muteChoicesFor(muted)` exported from `chatInfo/NotificationRow.tsx`.
- `GET /api/chats/:id/members`: with `members.review` unchanged (roster + banned rows); with only `members.ban` → 200 with the banned rows only; neither → 403 (unchanged).
- Core punctuation helpers `quoted`, `parenthetical`, `joinClauses` (keys `c.text.quoted|parenthetical|clauseSeparator`).
- Settings page `account.emoji-status` (设置 › 我的账号 › 表情状态, order 25), registered from `features/customEmoji/register.ts`.

## Decisions

- 2026-10-01 Items (1) and (7) share one root cause: a send before the session's first `history_complete`. (1) `ChatPane` gated the composer on `connection === 'online'`, and `Composer.submit` returns silently when `!canSend` — so Enter while the socket is still `connecting` did nothing and the text stayed. (7) Once `auth_ok` made the socket `online`, the send appended its optimistic row immediately, and every replayed history row arrived later and was appended after it. Fixed in the session (park while opening, flush after the replay), not in the composer, because the session is the one place that knows the replay state and the composer only needs a yes/no gate.
- 2026-10-01 Parked sends still show their optimistic row at once (not deferred to the flush): an invisible message on a slow connection is worse than a clock. To keep that row below the replay, `mergeIncomingBroadcast` inserts confirmed rows before the trailing in-flight sends. This is a core file outside the card; it is the minimal change that makes the ordering hold, and it is right in general (the server has not acknowledged our send, so anything it has already delivered is older). Failed rows are excluded so that new messages do not pile up above a failed send forever.
- 2026-10-01 Only the first opening queues. A chat that was ready and then dropped keeps the old contract (refuse + failed row) because reconnect semantics for offline sends are a larger product decision (Telegram queues them indefinitely) and existing tests pin the refusal.
- 2026-10-01 Item (2) root cause: the chat-list row's dot was «the peer is in this chat's `participants`» — `participants` is the chat roster (`chat_participants`), not the connected set — so an open private chat always showed its peer online, ignoring last-seen privacy, while the header read the privacy-filtered `presence.users[peer]` («离线»/last seen). The row now reads that same status. A status heard in any open chat also shows on rows of closed chats (it is the same per-user value).
- 2026-10-01 Item (6): rather than a new route (a lead-owned `routes.rs` edit), `GET /api/chats/:id/members` serves a ban-only administrator exactly the banned rows. The roster and join requests stay behind `members.review`; authorization is still decided per request at read time.
- 2026-10-01 Item (3): the row reads the conversation's preferences from `chatListStore` (`isConversationMuted`) and writes the PATCH answer back with `withPreferences`, so the choices and the list's mute icon follow at once.
- 2026-10-01 Item (5): the settings page is registered from `customEmoji/register.ts` (the feature's own side-effect module, as `profile/register.ts` does), not `settings/shell/builtinPages.ts` — that file's header says other features must not edit it. The list row and both member lists import `customEmoji/EmojiStatus` directly (as the chat header does), so first paint does not pull the customEmoji barrel; statuses are fetched through the existing batch cache (one request for all rows).
- 2026-10-01 Item (4): three helpers were added next to TG-1204's (`quoted`, `parenthetical`, `joinClauses`) in core's `punctuation.ts`, because the remaining lines needed quotes, a parenthesised aside and a clause separator the existing three did not cover.
