## Frozen interface

### Permission model (docs/tg/architecture.md §4.4)

- Registry `chat_permissions` gains 13 keys (+ `message.pin`, already registered by pins) → 23:
  `message.post`, `message.edit_any`, `message.delete_any`, `message.pin`,
  `message.send_media`, `message.send_sticker`, `message.send_poll`, `message.embed_link`,
  `members.ban`, `members.promote`, `chat.info`, `chat.topics`, `chat.anonymous`, `chat.call`.
  Scopes and Chinese labels: `src/chats/permissions.rs::REGISTRY`.
- Decision order (`AppState::authorize_chat_action`): system admin → creator → step 3 (role
  grant, **or** for an admin appointed with an explicit selection exactly the rows in
  `chat_admin_rights`) → step 4 `chat_member_restrictions` (denies a step-3 grant while
  `until IS NULL OR until > now`; never overrides steps 1–2) → step 5 `ChatType::permits`.
  `message.send_media|send_sticker|send_poll|embed_link` first require `message.send`.
  New variant `ChatAuthorization::RestrictedForMember`.
- **Default permissions = the `member` role's grants** of the 9 member-toggleable keys
  (`permissions::MEMBER_TOGGLEABLE`); baseline `message.edit_own`/`recall_own` always stays.
  New groups default to send + media + sticker + poll + link previews.
- Admin role grants = admin baseline (all sending kinds, own messages) + `DEFAULT_ADMIN_RIGHTS`
  (chat.info, room.settings, message.delete_any, message.pin, members.review/invite/remove/ban,
  chat.topics). Owner role = whole registry.
- Read gate: `AppState::can_read_chat(room, user)` = active membership. Reading is not a key.
- `members.roles` (owner-only) = "may edit/dismiss other administrators".

### HTTP (all under `/api/chats/:id`, and the `/api/rooms` alias)

| Method | Path | Gate | Body → Answer |
| --- | --- | --- | --- |
| GET | `/permissions` | active member | → `ChatPermissionsView {chat_id, chat_type, member_count, default_permissions[], my_permissions[], my_role, registry[{key,scope,label}]}` |
| PUT | `/default-permissions` | `members.ban` | `{permissions[]}` (⊆ member-toggleable, else 400) → `ChatPermissionsView` |
| GET | `/members/page?cursor&limit&filter` | active member (channel: `members.review`) | `filter` = `all` (default, keyset `(joined_at,user_id) DESC`, limit 1–200, default 50) \| `admins` \| `restricted` (whole lists, ≤200) → `{items: ChatMemberEntry[], next_cursor}` |
| GET | `/members/:user_id` | active member | → `ChatMemberEntry` (404 if not active) |
| PUT | `/members/:user_id/admin` | `members.promote`; editing an existing admin needs `members.roles`; non-owners grant only rights they hold | `{permissions[] ⊆ admin-assignable, custom_title ≤16}` → `ChatMemberEntry`; 409 owner/self |
| DELETE | `/members/:user_id/admin` | `members.promote` + `members.roles` | → `ChatMemberEntry` (now `member`) |
| PUT | `/members/:user_id/restrictions` | `members.ban` | `{denied_permissions[] ⊆ member-toggleable, until: RFC3339 \| null}` (replaces; empty lifts; past `until` 400) → `ChatMemberEntry`; 409 owner/admin/self |

`ChatMemberEntry {user_id, username, display_name, avatar_emoji, nickname, role, status,
joined_at, custom_title, admin_rights?, restrictions?[{permission_key, until}]}` —
`admin_rights` only for admins and only when the viewer holds `members.promote` or is the
member; `restrictions` only when the viewer holds `members.ban` or is the member (read-time).
Cursor is opaque (`<unix nanos>.<uuid simple>`).

`PATCH /api/chats/:id` now needs `chat.info` for title/avatar/description-only edits and
`room.settings` when the password or join policy changes.

### WebSocket

- `member_updated {member: ChatMembership}` on appoint / dismiss / restrict and for every
  member whose restriction the sweeper removes.
- `chat_updated {chat}` on default-permission changes and on a supergroup upgrade.

### Rust domain (for TG-202/204/206/207)

- `AppState::apply_chat_capabilities(room, ChatCapabilityChange{username, is_forum,
  slow_mode_seconds}) -> Result<CapabilityOutcome{chat, upgraded}, CapabilityError>` — the
  one place username / forum / slow mode are written; upgrades `group → supergroup` in the
  same transaction; `NotSupported(type)` when the (upgraded) type cannot hold the capability.
- Member-limit upgrade: every domain membership write (`request_chat_membership` in its own
  transaction; approve via `settle_membership_change`).
- `AppState::sweep_expired_chat_restrictions(now)` / `purge_expired_chat_restrictions(now)`
  (clock injected); the sweeper runs every 30 s (`restrictions::ensure_restriction_sweeper`).

### Schema

- `chat_member_restrictions(room_id, user_id, denied_permission_key, until, restricted_by,
  created_at, PK(room_id,user_id,denied_permission_key))` — FKs to chats/users/registry, **not**
  to chat_members (leaving and rejoining keeps a restriction).
- `chat_admin_rights(room_id, user_id, permission_key)` — FK (room_id,user_id) → chat_members
  ON DELETE CASCADE.
- `chat_members.custom_title TEXT NOT NULL DEFAULT ''`.
- Indexes `chat_members_room_joined_idx (room_id, status, joined_at, user_id)`,
  `chat_members_role_idx (role_id, status)`, `chat_member_restrictions_until_idx`.
- `chats.member_count` maintained by triggers on `chat_members` (SQLite row triggers;
  PostgreSQL statement triggers with transition tables). Recounted once by `..02`.

## Decisions

- 2026-10-01 `member_count` is maintained by database triggers rather than by hand in each
  write path, because memberships are also written outside `src/chats` (social/blocks,
  social/friends, push tests, `ON DELETE CASCADE` from `users`) and a trigger is the only
  place that sees all of them, inside the writer's transaction. PostgreSQL uses
  statement-level triggers with transition tables: a row trigger rewriting one `chats` row
  200 000 times in a bulk insert walks an ever-longer HOT chain.
- 2026-10-01 The in-memory chat cache still holds a descriptor copy, so `/api/chats`
  (via `decorate_chats_for_user`, one joined query) and `GET /api/chats/:id`
  (`sync_chat_projection`) read `chat_type`/`member_count` from the row; membership writes in
  `src/chats` also refresh the cache.
- 2026-10-01 Default permissions are the `member` role's grants, not a new column or mask:
  architecture §4.4 says extend the registry, and every inline `chat_role_permissions` guard
  elsewhere (text_store, reactions, stickers/send, favorites …) then honours them for free.
- 2026-10-01 Per-admin rights are a `chat_admin_rights` row set that *replaces* the shared
  `admin` role's grants for that admin, not a personal role: a personal role would need a
  unique name, and `chat_roles.name` is the `role` string every client and ~5 modules compare
  with `'admin'`. The shared admin role keeps the legacy default set so admins appointed via
  the frozen `set_role` action (and every pre-M2 admin) behave exactly as before.
- 2026-10-01 Reads use `can_read_chat` (membership) instead of `message.send`, in
  message history, in-chat search, the chat file list and the forward source check, because
  a restriction or a read-only default would otherwise hide history from the member.
- 2026-10-01 Restrictions are evaluated live (`until > now`), so they lift at `until` without
  the sweeper; the sweeper only deletes rows and emits `member_updated`. Restricting an admin
  is 409 (dismiss first); appointing lifts restrictions (Telegram's behaviour).
- 2026-10-01 Restrictions have no FK to `chat_members`: leaving and rejoining must not shed a
  mute. Admin rights *do* cascade with the membership.
- 2026-10-01 FK column spelling `room_id`, not architecture.md's `chat_id`, per CONTEXT.md
  ("Room") and TG-004's frozen non-rename.
- 2026-10-01 Keyset order is `(joined_at, user_id) DESC` (newest joiner first, Telegram's
  "recent"). SQLite compares the sqlx RFC 3339 text lexicographically, which is order-correct
  for sqlx-written values (`SecondsFormat::AutoSi`); the seeds write the same form.
  `..02` backfills `joined_at` for any active row that lacked one.
- 2026-10-01 Only the owner (key `members.roles`) edits or dismisses another admin; a
  `members.promote` holder may appoint members only and grant only rights they hold. Simpler
  than Telegram's "the admin who promoted may dismiss", which needs a `promoted_by` column.
- 2026-10-01 No HTTP for username / forum / slow mode: those are TG-206 / TG-204 / TG-207.
  They call `apply_chat_capabilities`, which owns the upgrade rule.
- 2026-10-01 The restriction sweeper keeps a static `Weak<AppState>` registry instead of an
  `AtomicBool` on `AppState`, to avoid editing the `state*.rs` hotspot.
- 2026-10-01 UI: the entry is shown to every member of a group/supergroup ("群组权限",
  read-only) and becomes "管理群组" with editors for holders of members.ban/promote/roles.
  The panel is a right `Sheet` over the info column (Telegram's sliding side page).
