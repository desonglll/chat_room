## Frozen interface

### 1. Render seam — `packages/web/src/features/messageList/renderContract.ts`

```ts
export interface MessageRenderContext {
  groupPosition: 'single' | 'first' | 'middle' | 'last' // same sender, consecutive, within a time window
  isOutgoing: boolean
  showAvatar: boolean      // true only on the last message of an incoming group in group chats
  showSenderName: boolean  // true on the first message of an incoming group in group chats
  highlighted: boolean     // jump-to-message flash
  selected: boolean        // selection mode
}
export type RenderMessage = (message: DisplayMessage, ctx: MessageRenderContext) => ReactNode
```

- Every row — `broadcast`, `system`, `upload` — goes through `renderMessage`; `message.type`
  tells them apart. The list draws the date separator, run spacing and the full-width
  highlight band itself (outside `renderMessage`), so a renderer never adds outer margins.
- Grouping rule: same sender (`sender_id`, or display name when null; uploads count as the
  current user), no service row between, same local day, each gap ≤ 5 min
  (`DEFAULT_GROUP_WINDOW_MS`). "Group chat" = `chat_type` `group` | `supergroup`.
- Height rule for renderers: reserve media boxes before load (the default renderer uses a
  fixed 4:3 box) — a late height change of a row ABOVE the viewport is corrected by
  Virtuoso, but a stable height is what keeps the anchor free.
- `useMessageListActions().jumpToMessage(messageId)` (`messageListActions.ts`) is how a
  renderer (reply quote, TG-103) asks the list to jump; the current position becomes the
  "back" point.

### 4. HTTP used (unchanged, both authorize every read)

`GET /api/chats/:id/messages?before=<id>&limit=50` (older pages) and
`GET /api/chats/:id/messages/:message_id/context?limit=100` (jump windows AND newer pages —
there is no `after` cursor; the context of the newest loaded message returns up to 49 newer
ones). Verified against a live server: `before` is **inclusive** of the cursor and pages are
chronological; context returns `limit/2+1` older-including-target then the newer rest.

## Performance budget

Executable in two places; the numbers below are the budgets the scripts enforce.

**Pure** — `bun packages/core/src/domain/messageViewportBenchmark.ts` (exit 1 on breach; also
run by `bun test` with 5× slack as a regression guard). 100k synthetic messages, median.

| metric | budget | measured | why this budget |
| --- | --- | --- | --- |
| `layoutCold100k` full layout, fresh objects | ≤ 120 ms | 58–95 ms | once per chat open; ~1 µs/msg; real windows are ≤ a few thousand rows (< 5 ms) |
| `layoutWarm100k` append through the cache | ≤ 12 ms | 4–5 ms | must fit a 16 ms frame next to React's commit even at the 100k extreme |
| `prependPageInto100k` merge one 50-row page | ≤ 8 ms | 0.7–0.9 ms | half a frame |
| `unreadScan` badge count | ≤ 1 ms | 0.01 ms | runs every render; O(unread) not O(n) |
| `layoutHeapBytesPerMessage` | ≤ 256 B | 122 B | layout must stay small next to the message objects (~410 B synthetic) |

**Browser** — `node packages/web/src/features/messageList/bench/runBrowserBench.mjs [scenario]`
(bundles `bench/harness.tsx` with the REAL `MessageList` + stores and an in-memory fake of the
two endpoints with the server's semantics; headless Chromium 1243, 900×800, production build;
`LATENCY=<ms>` and `ITERATIONS=<n>` env; screenshots to `/tmp/tg-shots/TG-101/`). Frames are
sampled **at paint time** (ResizeObserver after Virtuoso's, see Decisions).

| metric | budget | measured | why |
| --- | --- | --- | --- |
| `prependFinalShiftPx` (25–30 prepends while parked at the top) | 0 px | 0 at latency 0 / 5 / 60 / 200 ms | card acceptance: anchor shift 0 px |
| `prependMaxTransientPx` any painted frame | ≤ 1 px | 0 | sub-pixel rounding only; a 1-frame jump is still a visible jump |
| `prependBlankFrames` viewport not covered by rows | 0 | 0 | a blank frame is a flash |
| `jumpTargetInViewport` jump 50 000 messages back | 0 misses | 0 | card acceptance |
| `returnShiftPx` "back to where you were" | ≤ 1 px | 0 | card acceptance: returns to the original position |
| `followAtBottomPx` / `ownSendBottomPx` | ≤ 2 px | 0 / 0 | follow when at bottom; own send always goes to bottom |
| `noFollowShiftPx` new messages while scrolled up | 0 px | 0 | never move a reader who scrolled away |
| `unreadBadgeError` | 0 | 0 | badge counts exactly the unseen incoming rows |
| `longFramePercent` (> 50 ms) wheel-scrolling a 100k-row list | ≤ 5 % | 0 – 3.3 % (median frame 16.7 ms) | headless on a shared, loaded box (load avg ~15): 50 ms = 3 missed vsyncs is the signal that survives that noise |
| `domRows` mounted rows | ≤ 120 | 21–22 | virtualization actually bounds the DOM |
| `listHeapMB100k` JS heap: list mounted over 100k vs store only | ≤ 24 MB | 7.4–8.5 MB (store alone 43.6 MB) | the list must cost well under the data it shows |

## Decisions

- 2026-09-30 Virtuoso gets `totalCount` + index-based `itemContent`, not `data`, because a
  `data` array of row objects would allocate 100k objects per render; an absolute index maps
  to `all[index - firstItemIndex + hidden]`.
- 2026-09-30 **Hidden lead row**: while more history exists, the oldest loaded message is not
  rendered, because the first visible row's `startsDay`/`groupPosition`/`showSenderName`
  depend on its predecessor; with the predecessor already loaded, a prepend never changes a
  row that is on screen (unit-tested: layout of visible rows identical across prepends).
- 2026-09-30 `firstItemIndex` shift is computed generically (`prependShift`: find the previous
  first row's key in the new row list) instead of "page length", because dedup, the lead
  reveal at chat start, and detached→live joins all change the count differently.
- 2026-09-30 Date separators live INSIDE the `startsDay` row plus a floating pill overlay while
  scrolling, instead of `GroupedVirtuoso`, because CSS sticky cannot cross Virtuoso's item
  wrappers and `groupCounts` + prepend is a second, more fragile anchor mechanism.
- 2026-09-30 `skipAnimationFrameInResizeObserver` on, because with the default rAF-deferred
  measurement the browser bench showed one PAINTED frame per prepend displaced by the whole
  page height (up to 1259 px).
- 2026-09-30 Bottom overscan is widened (+4500 px) while an older page is in flight and 200 ms
  after, because Virtuoso recomputes its range from the scroll event one frame after the
  prepend: at the old scrollTop the range ends above the viewport (measured: blank frames).
  The widening must be in place BEFORE the commit — changing `increaseViewportBy` in the same
  render as `firstItemIndex` broke Virtuoso's compensation (measured 2283 px). Hence the
  controller holds an instant response for one painted frame (`afterPaint`, awaited in
  parallel with the request, so a real round trip pays nothing).
- 2026-09-30 **Prepend anchor guard** (`usePrependAnchor`), because Virtuoso's upward-scroll
  compensation is skipped when its rendered range starts at row 0 both before and after —
  exactly a reader parked at the top — leaving a permanent shift of the page height (measured
  at latency 0: 320–1259 px, intermittent). The guard pins the topmost visible row right
  before the controller prepends and restores it in a ResizeObserver callback (after layout,
  before paint, after Virtuoso's observers); when Virtuoso already compensated the delta is 0.
  It stands down on wheel/touch/key/pointer input and after 600 ms.
- 2026-09-30 "Back to where you were" stores key + pixel offset and restores it through the
  same guard (`pinAt`), because `initialTopMostItemIndex` on a remount positions from
  ESTIMATED heights (measured: landed 240 px off at the bottom clamp).
- 2026-09-30 One FAB, Telegram-style: with a return point it goes back there, otherwise to the
  newest message; badge = unseen incoming rows.
- 2026-09-30 Newer pages in a detached window come from `/context` of the newest loaded
  message, not a new `after` endpoint, because it already exists with authorization and
  `src/chats/**` belongs to TG-208 right now. Cost: up to 51 already-known rows per request.
- 2026-09-30 A detached window that overlaps the live rows JOINS live without a remount
  (rows keep their absolute index), so paging down from a jump into the present is seamless.
- 2026-09-30 Older pages load only after `history_complete`, and the list mounts only then,
  because mounting on the first replayed row and following a 100-row burst opened the chat
  short of the bottom (real-server screenshot). Replayed rows (`motion: 'none'`) follow with
  `auto`, live arrivals with `smooth` (reduced motion → `auto`).
- 2026-09-30 Seen/unread tracking runs in Virtuoso's event handlers, not in effects, because
  an effect re-rendered once per replayed frame and tripped React's nested-update limit
  during the socket's 100-frame replay (observed in the real app).
- 2026-09-30 Controller `dispose()` is reversible (`resume()`), because React StrictMode
  remounts effects on the same memoized controller; a permanent dispose silently dropped every
  page in dev (observed: the same `before=` cursor requested 7 times).
- 2026-09-30 Incremental layout = identity diff (common prefix + suffix) rather than a
  per-message WeakMap cache, because WeakMap set/get cost 23/16 ms per 100k in Bun/JSC.
- 2026-09-30 `mergeMessagePages` checks the overlap by binary search, because the inclusive
  `before` cursor always overlaps and building a 100k id set cost 40–60 ms per page (now < 1 ms).
- 2026-09-30 `reachedStart` trusts the server's `limit/2+1` older formula (verified live);
  guessing low would hide history, guessing high costs one extra empty request.
- 2026-09-30 The default renderer reuses TG-012's `.tg-msg*` classes in `styles/chat.css`
  instead of duplicating bubble CSS, because TG-103 replaces it wholesale anyway.

## Residual risk

1. **Live frames do not reach REST-loaded rows.** `messageStore` applies edits, recalls and
   reactions only to its own timeline; rows this list loaded older than it (`older`) or in a
   detached window keep their fetched state until reopened. Proper fix (outside TG-101's
   paths): add `prependHistory(chatId, messages)` to `messageStore` and let the controller's
   live mode write older pages there (its `older` array then disappears; the anchor math is
   unchanged because it is key-based).
2. The anchor guarantees rest partly on Virtuoso 4.18.16 internals (compensation paths, RO
   timing); the guard corrects whatever it misses before paint, but any `react-virtuoso`
   upgrade must re-run `runBrowserBench.mjs`.
3. Browser numbers come from headless Chromium on a heavily shared machine (load ~15, swap
   full); frame-time figures are indicative, the pixel figures are exact.
4. The guard stands down on wheel/touch/key/pointer; a programmatic scroll by other code within
   600 ms of a prepend would be "corrected" back.
5. `targetMessageId` from `?message=` stays in the URL; re-opening the same chat URL re-jumps
   (intended), but a jump error notice ("消息不存在或已被删除") shows for deleted targets.
