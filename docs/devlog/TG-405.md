## Frozen interface

- `PUT /api/chats/:id/auto-delete` `{ seconds }` — 0, 86400, 604800 or 2592000. Either side of a
  private chat; `chat.info` holders in groups/channels. Broadcasts `chat_updated` and a `system`
  notice («X 将自动删除时间设为 1 天» / «X 关闭了自动删除»).
- `messages.auto_delete_at` (migration `20270101000005`), stamped by a trigger on insert.
- New WS frame `{ "type": "messages_deleted", "message_ids": [...] }` — rows removed for
  everyone, no placeholder. Additive (frozen clients ignore unknown frames, TG-007).

## Decisions

- 2026-10-01 Per-message deadline stamped at insert by a trigger (SQLite `AFTER INSERT` +
  `strftime(..., '+N seconds')`, PostgreSQL `BEFORE INSERT` + `make_interval`), so every insert
  path — text, media, stickers, polls, voice, video notes, albums, forwards, scheduled delivery —
  obeys it without learning a column, and changing/turning off the timer never touches messages
  already sent (Telegram). A chat-level "since" timestamp was rejected: it cannot represent
  messages sent under an earlier, different timer.
- 2026-10-01 Expired messages are hard-deleted (Telegram removes them for everyone) with the
  dependent rows following their `ON DELETE` rules, exactly like TG-204's topic deletion; their
  attachments' orphan state is recomputed afterwards (a forward or favorite may still hold the
  file), so no file is orphaned or lost. Clients drop the rows on `messages_deleted`.
- 2026-10-01 The sweeper runs every 10 s in batches of 500 and drains back to back when behind;
  it is idempotent and resumable because it only acts on rows still present and past due.
- 2026-10-01 The system notice is a live `system` frame, like every other system notice in the
  product today (they are not persisted — pre-existing behaviour, noted by TG-100).
