## Frozen interface

- **Wire**: `Attachment` (Rust `src/models.rs`, TS `packages/core/src/types/message.ts`) gains an optional
  `thumbnail_url: string`. Present only for `image/jpeg|jpg|png|gif|webp`; omitted (not `null`) otherwise,
  so legacy WS frame snapshots and older clients are unchanged. Old cached JSON deserialises (`serde(default)`).
- **HTTP**: `GET /api/attachments/{id}/thumbnail?key={access_key}` → 200 `image/jpeg` (or `image/png`
  when the source has transparency), longest edge ≤ 640 px, `Cache-Control: private, max-age=31536000,
  immutable`, `nosniff`. 404 for: wrong/foreign key, unknown id, recalled message/deleted favourite (same
  rule as the original), non-image, undecodable, source > 32 MiB or > 50 M pixels. 400 without `key`.
- **Web**: `attachmentPreviewUrl(attachment)` / `fallBackToOriginal(attachment)` in
  `features/message/content/attachmentPreview.ts`; `MediaItem.previewUrl` in the viewer.

## Decisions

- `image 0.25.10`, `default-features = false, features = ["jpeg","png","gif","webp"]` (lead-authorised, the
  user chose server-side generation). Pulls zune-jpeg, png, gif, image-webp, moxcms (+ small deps); no rayon,
  no C code.
- **Lazy on first request, cached on disk** rather than at upload completion: one code path covers new
  uploads, albums, favourites and every historical image (no backfill job, no upload-latency cost), and
  uploads via voice/video-note/OSS-direct need no hook. The first viewer pays one render (~100 ms for a
  4000×3000 JPEG in a debug build's blocking pool).
- **Authorisation = the original's**: the handler calls `attachment_metadata(id, key)` on every request,
  *before* touching the cache, so a cached file never outlives its original's visibility (tested: recall →
  404 even when cached). Capability-key model, same as `/api/attachments/:id?key=` (an `<img>` cannot send
  the session header).
- Cache in `<attachments root>/.thumbnails/<id>` — local even with OSS (a projection; loss = re-render).
  Top-level dot dir, so `backup/files.rs` skips it exactly like `.staging` and restores ignore it. Written to a
  temp name then renamed, so a concurrent reader never sees half a file.
- Hostile input: declared dimensions checked before any pixel is decoded (50 M px cap) **and**
  `image::Limits { max_alloc: 256 MiB }`; the decoder's `Limits` error maps to the same `TooLarge`. Decoding
  runs in `spawn_blocking` behind a global 2-permit semaphore. SVG is never offered (not raster).
- 640 px long edge: bubbles are ≤ ~320 CSS px, so 640 is sharp at 2x; a 591 KB 4000×3000 JPEG → ~20 KB.
  JPEG q80, PNG only when the image has alpha (a transparent PNG must not turn black).
- **GIF**: the server renders frame 1 (for clients that cannot animate), but the web keeps showing the
  original GIF — its motion is the content. Rule lives in `attachmentPreviewUrl`.
- **Viewer**: thumbnail first, original swapped in. The stage renders the original transparent
  (`data-loading`) over a `object-fit: contain` preview layer that fills the box; the preview is removed on
  the original's `load`. Two consequences fixed in `useViewerMotion.ts`:
  1. the open flight used the bubble image's natural size to compute its landing box — now a server
     thumbnail's size is treated as aspect-only, so the flight lands where the preview fills (no jump);
  2. the flight waited for `decode()` of the **original** before revealing the stage, which on a slow phone
     would hold it mid-air for the whole download — it now waits for the preview layer when there is one.
  `findThumbnail` joins on `previewUrl` (what the bubble shows), so fly-in/fly-out still find the bubble.
- If the thumbnail cannot be served (404), bubble/album/info tiles fall back to the original once
  (`BubbleImage.fallbackSrc`, `fallBackToOriginal`) rather than showing "image unavailable".

## Residual risk

- Thumbnails are cached per server instance (local disk). Several instances behind OSS each render once.
- Orphaned cache files when an attachment row is deleted are not swept (they are unreachable: every request
  re-authorises). A sweep can be added to the existing staging cleanup if disk matters.
- The first open of a never-viewed large photo costs one decode on the server (bounded by the semaphore).
