### HTTP — login (unauthenticated)

| Route | Body | Result |
| --- | --- | --- |
| `POST /api/users/login` | unchanged `{username, password}` | **no 2FA**: unchanged `200 AuthSession`. **2FA on + password right**: `428 Precondition Required` with `TwoFactorChallenge` `{error:"two_factor_required", pending_token, hint, has_recovery_email, expires_at}` |
| `POST /api/users/login/two-factor` | `{pending_token, password}` | `200 AuthSession` · `401` wrong 2FA password · `410` pending token unknown/expired/exhausted (restart at stage 1) · `429` |
| `POST /api/users/login/two-factor/recovery` | `{pending_token}` | `202 {email_pattern, expires_at}` code mailed to the *verified* recovery email · `409` no recovery email · `410` · `429` · `503` no mail transport |
| `POST /api/users/login/two-factor/recovery/confirm` | `{pending_token, code}` | `200 AuthSession` — 2FA is **removed**, every other session of the account is terminated · `401` wrong code · `410` · `429` |

A pending token is a random UUID, stored only as SHA-256, lives 5 minutes, allows 5 wrong
2FA passwords, and is **not** a session (every bearer route rejects it). Recovery requires a
pending token, i.e. the account password has already been proven; the email code only
replaces the forgotten second factor.

### HTTP — settings (bearer session)

| Route | Body | Result |
| --- | --- | --- |
| `GET /api/users/me/two-factor` | — | `200 TwoFactorStatus {enabled, hint, recovery_email: string\|null, pending_recovery_email: string\|null}` |
| `POST /api/users/me/two-factor` | `{account_password, password, hint}` | enable → `200 TwoFactorStatus`; **terminates every other session (D-010)** · `401` wrong account password · `409` already on · `400` · `429` |
| `PUT /api/users/me/two-factor` | `{current_password, new_password?, hint?}` | change → `200 TwoFactorStatus` (sessions kept) · `401` · `404` not on · `429` |
| `DELETE /api/users/me/two-factor` | `{current_password}` | disable → `204` · `401` · `404` · `429` |
| `POST /api/users/me/two-factor/recovery-email` | `{current_password, email}` | `202 {expires_at}` verification code mailed · `401` · `404` · `503` |
| `POST /api/users/me/two-factor/recovery-email/confirm` | `{code}` | `200 TwoFactorStatus` · `401` wrong code · `410` nothing pending · `429` |

Limits: 2FA password ≤ 256 chars and ≥ 1; hint ≤ 64 chars and must not contain the password;
email ≤ 254 chars; codes are 6 digits, 15 minutes, 5 attempts.

- 2026-10-01 Base is `fa1b1aa`, not the `8ba40e5` named in the assignment: `tg-worktree.sh new`
  branches from current `main`, which had gained one board-only docs commit. No code differs.
- 2026-10-01 A 2FA login answers **`428 Precondition Required`** with a JSON challenge instead of
  `200` with a different shape, because every frozen client (Vue `web/`, ratatui, PySide6)
  parses a `2xx` as `AuthSession`; a non-2xx they already render as "登录失败：428". `401` and
  `403` were rejected because the Vue client maps them to "用户名或密码错误" / "邀请码无效",
  which would be false. **Frozen clients cannot log in to 2FA accounts** — by design; they
  keep working for every account without 2FA (pinned by
  `accounts_without_two_factor_keep_the_frozen_login_response`).
- 2026-10-01 D-010 applied: enabling 2FA ends every other session in the same transaction as the
  insert; the recovery reset ends *all* earlier sessions (the new one is created afterwards).
  Changing the 2FA password/hint and disabling 2FA keep sessions — the user already proved
  the second factor, and D-010 only speaks about enabling.
- 2026-10-01 Enabling requires the **account** password as well, because under D-010 a stolen
  bearer token that could enable 2FA would lock the real owner out of every device.
- 2026-10-01 Recovery requires a pending token (account password already proven) and a code
  mailed to a *verified* address; the reset code has its own `purpose='reset'` row, so an
  email-verification code can never be replayed as a reset code. The reset **removes** 2FA
  (Telegram's behaviour) rather than setting a new password in the same request.
- 2026-10-01 Pending tokens are stored as SHA-256 only and are single-use (`DELETE … RETURNING`
  consumes them atomically, so two racing correct submissions cannot mint two sessions).
  Attempt counters are reserved with `UPDATE … attempts < max RETURNING` *before* argon2.
- 2026-10-01 Mailed codes are argon2-hashed with the existing `hash_password`, not SHA-256: a
  6-digit space is brute-forced offline in microseconds under a fast hash.
- 2026-10-01 Mail delivery is a process-wide `RecoveryMailer` slot (`install_recovery_mailer`)
  rather than an `AppState` field, so no shared state file (`src/state*.rs`, lead-owned) had to
  change. Default `UnconfiguredMailer` → `503`. **Production mail delivery is not configured;
  nothing in the server installs a transport.** `MemoryMailer` is the log-free test outbox.
  Nothing logs a code; `RecoveryMail`'s `Debug` redacts it.
- 2026-10-01 Rate limiting: two new `AuthAction`s (`TwoFactor`, `TwoFactorRecovery`) through
  `accounts::auth_limits::require_auth_capacity`, keyed by user id + client IP. That needs two
  enum variants in `src/security/rate_limits.rs` (outside the card) — reusing `VerifyPassword`
  would have shared a bucket with an unrelated endpoint.
- 2026-10-01 Web CSS lives beside the features (`features/auth/twoFactorLogin.css`,
  `features/settings/security/security.css`) and is pulled in by two `@import` lines in
  `styles/index.css`, keeping the "components never import CSS" rule.
- 2026-10-01 Cargo runs switched mid-task from the shared target dir to
  `/home/mike/workspace/.cargo-target/tg-506` (lead notice, Hazard 2); every cargo result in

## Residual risk

- Frozen clients (Vue `web/`, ratatui, PySide6) cannot complete a 2FA login; they show a
  generic "登录失败：428". Intended; retire with M6.
- The mailer slot is process-wide: two `AppState`s in one process share one transport (only
  relevant to tests; each TG-506 test binary installs one outbox and uses unique addresses).
- An account without a recovery email that forgets its 2FA password has no self-service path
  (Telegram's 7-day wait reset is out of scope); only an operator deleting the
  `two_factor_credentials` row helps.
- There is no endpoint to remove a recovery email without disabling 2FA; it can only be replaced.
- Stage one proves the account password to whoever holds it (the `428` reveals it was right) —
  inherent to two-step login and identical to Telegram; stage one stays under the `login` limit.
