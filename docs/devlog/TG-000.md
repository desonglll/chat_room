## Frozen interface

This task is a pure refactor of file layout. **No public interface changes.** Every symbol
that was reachable as `crate::config::X`, `chat_room::config::X`, `crate::ai::X` or
`crate::knowledge::X` before is still reachable under exactly the same path, via
re-exports from the parent module. Downstream tasks can ignore the split entirely.

## Decisions

- 2026-09-30 拆分 `src/config.rs` 的办法是**把校验下沉到拥有该字段的配置类型上**，而不是新建一个

  `BackupConfig::validate` / `WebPushConfig::validate` 已经是仓库既有约定，`AppConfig::validate`

## 为什么红色的 main 没被发现

这是任务卡要求回答的部分。事实先列，结论在后。可在仓库内核实的：

1. **`main` 不是这个仓库的默认分支，`master` 是。** `git remote show` 的
   `remotes/origin/HEAD -> origin/master`，而 `origin/master` 停在 `80c167e`，与 `origin/main`
   的 `a16f422` 无关。后果是：GitHub 的仓库首页、Actions 页面的默认视图、以及任何 README 状态
   徽章描述的都是 `master`。`main` 上的一次红色运行确实存在，但它不在任何人第一眼会看到的位置。
   分支保护的设置入口也是围绕默认分支组织的，`main` 恰好是没人被提示去保护的那一条。
2. **workflow 对 `main` 只有事后触发，没有事前门禁。** `.github/workflows/ci-cd.yml:4-7` 的触发器
   是 `push: branches: [main]` 加 `pull_request:`。`push` 触发的运行在提交**已经落到分支上之后**
   才报告，它在物理上无法阻止任何东西。文件里唯一的事前门禁是 `pull_request`，而 `a16f422`
   的提交信息是 `update.`——和它前面的 `7acf7c3 update.`、`fc25980 update.`、`09ffdb1 update.`
   一样，是直推，不是 PR。没有 PR，`pull_request` 触发器一次都不会点火。
3. **仓库里没有任何「保护即代码」。** `.github/` 下只有 `ci-cd.yml` 一个文件：没有 `CODEOWNERS`，
   没有 PR 模板，没有 `merge_group:` 触发器（即没在用 merge queue），没有 ruleset 文件。
   真正的分支保护是 GitHub 服务端设置，本机没有 `gh`（`command not found`），无法读取。
   但对第 2 条来说它也是无关的：保护规则约束的是 PR 流程，而这个提交没走 PR。
   **直推能成功本身就说明** `main` 要么没开保护，要么推的人有 bypass 权限。
4. **本地没有任何 hook。** `git config core.hooksPath` 为空，`$GIT_COMMON_DIR/hooks/` 下除了
   `.sample` 什么都没有。也就是说 `check_file_sizes.py` 在推送前**没有任何机会**运行。
   仓库确实提供了 `scripts/tg-worktree.sh check`，但它是自愿调用的，没有东西强制它。
5. **开发者跑「显而易见的那几条命令」看到的是绿的。** `a16f422` 上 `cargo fmt`、`cargo clippy`、
   `cargo test` 全绿，唯一的红灯来自一个 Python 审计脚本。除非有人专门去跑它，否则本机没有红色信号。
6. **这道门禁的形状让静默失败成为常态。** `check_file_sizes.py` 不只在超过绝对上限时失败，
   还在**超过记录基线**（第 73 行）和**基线过期**（第 77 行）时失败。于是它会因为「给一个 430 行
   的文件加了 20 行」这种局部无害的改动变红，也会在一次**正当的拆分之后**因为第二个理由
   （基线过期）再变红一次。一道在日常编辑上就会响的警报，会训练人默认它是红的——这正是
   roadmap 预判的 `FND-001` 复发机制。

**结论**：不是「通知没送到」，是**结构上没有任何东西能阻止红色提交进入 `main`**。
`main` 上的 CI 是一个事后的报告器，而它的报告还挂在一条不是默认分支的分支上。

**给集成负责人的建议**（`.github/**` 与仓库设置都不在本任务的 Allowed paths，我没有改）：

- 把默认分支改成 `main`（或者退役 `master`）。在那之前，`main` 上任何红灯都不会被人第一眼看到。
- 给 `main` 开分支保护：`Require a pull request before merging` +
  `Require status checks to pass`，把 `Quality gates` 这个 job 设为必需检查。只有这样
  `pull_request` 触发器才真正成为门禁，`push` 触发器才只是冗余确认。
- 加一个 `pre-push` hook（或让 `scripts/tg-worktree.sh check` 挂上去），至少跑两条快的
  Python 门禁：`check_file_sizes.py` 与 `check_migration_parity.py`。它们不需要编译，
  秒级完成，足以让这一类红灯永远到不了远端。
- 把 `on: push` 的分支过滤放宽到 agent 分支（`agent/**`），否则并行期间每条任务分支都要靠
  owner 自己记得跑门禁。

## Residual risk

- **`AppConfig::validate` 的校验顺序变了。** 委派之后的顺序是 uploads → attachments →
  realtime → auth → security → web_push → observability → backup → admin → redis →
  work_queue → database → ai → vector_store。原来 `ai.standard_extra_body` 的对象类型检查在
  redis/work_queue 之后、database 之前，`admin.usernames` 的非空检查也和 admin 的保留期检查
  隔着好几段，而 `max_upload_bytes()` / `chunk_size_bytes()` 的溢出检查原来在**最后**、现在在
  `uploads.validate()` 里最先跑。单个错误的消息文本一字未改，`src/config/tests.rs` 的 11 个
  测试全过；但如果**一份配置同时有两处错误**，报出来的是哪一条可能和 `a16f422` 不同。
  审阅者该怀疑的就是这一点。没有测试覆盖「多错并存时报哪一条」，我也没有新增——那会把一个
  实现细节钉死成契约。
- **`src/config/environment/value.rs` 是一个共享的强制转换模块，天生有变成倾倒场的引力。**
  它现在只有 6 个函数、45 行，文件头写明了边界。下一个往 `environment/` 加段的 agent 如果
  把「不属于单字段赋值」的东西塞进去，这条约束就失效了。审阅 `environment/` 的改动时看一眼这个文件。
- **`web/src/chat.css` 的豁免依赖 TG-602 真的会删掉 `web/`。** 如果 TG-602 被推迟或缩小范围，
  这个 355 行的文件就会无限期带着豁免存在。脚本的 stale-baseline 检查只在文件**被删除**时
  才会报警，文件一直留着的话不会有任何提示。
- **`main` 依然没有任何事前门禁。** 本任务把代码修绿了，但没有（也无权）修那个让红色提交能进
  `main` 的机制。见「为什么红色的 main 没被发现」一节的建议清单。下一次同类事故的概率没有下降。
