## Frozen interface

Everything below is the contract TG-303 / TG-304 / TG-306 build on. It only grows.

### Storage model

| Table | Key | Notes |
| --- | --- | --- |
| `sticker_sets` | `id` | `short_name` UNIQUE, stored lowercase (`[a-z][a-z0-9_]{0,63}`); `title` 1–64 chars; `set_type` `regular` \| `custom_emoji`; `owner_id` nullable (`SET NULL` on account delete — sets outlive their creator) |
| `stickers` | `id` | `set_id` → sets (CASCADE); `position`; `emoji` (primary); `format` `webp`\|`tgs`\|`webm`; `mime_type`; `width`/`height`; `duration_ms` (NULL for webp); `size_bytes`; `content_hash`; `storage_key` (= SHA-256 hex, same content-addressed object space as attachments); `access_key` (catalogue capability); `removed_at` (soft delete — messages keep resolving the row) |
| `sticker_emojis` | `(sticker_id, emoji)` | 1–20 emoji per sticker, indexed by `emoji` for search |
| `user_sticker_state` | `user_id` | `revision` bumps on every library write; the row lock serialises one account's library writes on both adapters |
| `user_sticker_sets` | `(user_id, set_id)` | `position` (ascending = top first), `archived_at`, `installed_at` |
| `user_recent_stickers` | `(user_id, sticker_id)` | `used_at`; capped at 20 per account |
| `user_favorite_stickers` | `(user_id, sticker_id)` | `created_at`; capped at 5 per account, oldest evicted |
| `custom_emoji` | `sticker_id` | one row per sticker of a `custom_emoji` set: `set_id`, `emoji`, `created_at`. TG-304 owns everything above the table (`20261201000003`) |
| `messages.media_kind` | — | nullable TEXT. NULL = unclassified legacy/plain message (text, or attachment classified by its mime). TG-302 writes only `'sticker'`; M4 owns the other values listed in architecture.md §4.5 |
| `messages.sticker_id` | — | nullable → `stickers(id)` `ON DELETE SET NULL` |

### Format limits (server-side, by content sniffing — the client MIME is ignored)

| Format | MIME | File cap | Geometry | Time |
| --- | --- | --- | --- | --- |
| `webp` (static) | `image/webp` | 512 KiB | regular: both sides ≤ 512 and one side = 512; custom emoji: 100×100. Animated WebP rejected | — |
| `tgs` (gzip Lottie) | `application/x-tgsticker` | 64 KiB compressed, 1 MiB inflated | Lottie `w` = `h` = 512 | `fr` ≤ 60, `(op − ip) / fr` ≤ 3 s |
| `webm` | `video/webm` | 256 KiB | as webp | VP9 only (`V_VP9`), no audio track, duration ≤ 3 s, ≤ 30 fps when declared |

### HTTP (all bearer-authenticated except the capability file URL)

| Method + path | Body | Response |
| --- | --- | --- |
| `POST /api/sticker-sets` | `{short_name, title, set_type?}` | 201 `StickerSet`; 409 `short_name_taken`; 400 codes below |
| `GET /api/sticker-sets/:short_name` | — | 200 `StickerSet` (case-insensitive short name) |
| `POST /api/sticker-sets/:short_name/stickers` | multipart `file`, `emoji` (space-separated, 1–20) | 201 `Sticker`; 403 not owner; 400 `{error}` |
| `DELETE /api/sticker-sets/:short_name/stickers/:sticker_id` | — | 204; 403 not owner |
| `GET /api/stickers/installed` | — | 200 `InstalledStickerSets` |
| `PUT /api/stickers/installed` | `{set_ids: [uuid]}` reorder | 200 `InstalledStickerSets` |
| `PUT /api/stickers/installed/:set_id` | — | install (or un-archive) at the top; idempotent |
| `PATCH /api/stickers/installed/:set_id` | `{archived: bool}` | 200 `InstalledStickerSets`; 404 not installed |
| `DELETE /api/stickers/installed/:set_id` | — | 200 `InstalledStickerSets` |
| `GET /api/stickers/recent` | — | 200 `[Sticker]`, most recent first, ≤ 20 |
| `DELETE /api/stickers/recent/:sticker_id` | — | 204 |
| `GET /api/stickers/favorites` | — | 200 `[Sticker]`, newest first, ≤ 5 |
| `PUT` / `DELETE /api/stickers/favorites/:sticker_id` | — | 204 |
| `GET /api/stickers/search?emoji=😀` | — | 200 `[Sticker]` from the caller's non-archived installed sets, set order then sticker order, ≤ 50 |
| `GET /api/stickers/:sticker_id/file?key=<access_key>` | — | the file; capability URL exactly like `/api/attachments/:id?key=` |
| `POST /api/chats/:id/sticker-messages` | `{sticker_id, reply_to?, client_message_id?}` | 201 `StoredMessage` (200 when `client_message_id` replays an existing send) |

Rejection codes (`400 {"error": code}`): `unsupported_format`, `file_too_large`, `invalid_dimensions`, `animated_webp`, `invalid_gzip`, `invalid_json`, `invalid_lottie`, `too_long`, `frame_rate_too_high`, `invalid_webm`, `unsupported_codec`, `audio_not_allowed`, `invalid_emoji`, `invalid_short_name`, `invalid_title`, `set_full`, `sticker_not_found`.

### JSON shapes

```jsonc
// Sticker
{ "id": "uuid", "set_id": "uuid", "emoji": "😀", "emojis": ["😀","😃"],
  "format": "webp|tgs|webm", "mime_type": "image/webp", "width": 512, "height": 512,
  "duration_ms": null, "size_bytes": 1234,
  "file_url": "/api/stickers/<id>/file?key=<uuid>" }
// StickerSet
{ "id": "uuid", "short_name": "cats", "title": "Cats", "set_type": "regular|custom_emoji",
  "owner_id": "uuid|null", "stickers": [Sticker], "installed": true, "archived": false,
  "created_at": "…", "updated_at": "…" }
// InstalledStickerSets — sets ordered top first; archived sets are included with archived: true
{ "revision": 7, "sets": [StickerSet] }
```

### Sticker message wire shape (history `StoredMessage` and WS `broadcast`)

A sticker message is an ordinary attachment message plus two optional fields, both
omitted (not `null`) on every other message so frozen byte-for-byte snapshots are unchanged:

```jsonc
{ "type": "broadcast", "message_id": "…", "content": "",
  "attachment": { "id": "…", "file_name": "sticker.tgs", "mime_type": "application/x-tgsticker",
                  "size_bytes": 1234, "download_url": "/api/attachments/<id>?key=<k>",
                  "is_sensitive": false },
  "media_kind": "sticker",
  "sticker": { "sticker_id": "uuid", "set_id": "uuid", "set_short_name": "cats",
               "emoji": "😀", "format": "tgs", "width": 512, "height": 512 },
  … every other broadcast field unchanged … }
```

Render from `attachment.download_url` (per-message capability, same authorization as any
attachment); use `sticker.set_short_name` for "view pack". A client that ignores the new
fields (Vue, PySide6, ratatui) still shows the file as an attachment. `sticker` is absent
when the message is recalled for this viewer (mirrors attachment redaction).

## Decisions

- 2026-10-01 Sticker messages carry a **per-message attachment row** pointing at the sticker's content-addressed object, instead of a message → sticker file link, because it makes the file's authorization literally the attachment code path (capability key issued only inside the chat's history), keeps frozen clients rendering the file, and lets recall/favorite/forward behave as for any attachment.
- 2026-10-01 Set catalogue files use their own capability key (`stickers.access_key`), issued only through bearer-authenticated set endpoints: sets are public by short name (Telegram semantics), so the catalogue is not chat-scoped — the chat-scoped copy is the message attachment.
- 2026-10-01 `messages.media_kind` is nullable and not backfilled, because classifying existing attachments (photo/video/document) is M4's decision; NULL keeps today's meaning.
- 2026-10-01 Library writes serialise on an upsert of `user_sticker_state` as the first statement of the transaction, because it takes a row lock on PostgreSQL and the write lock on SQLite before any read — one mechanism for both adapters, no advisory locks, and the revision doubles as a client sync hint.
- 2026-10-01 Sticker enrichment hooks into `attach_message_reactions` (the single post-load step every history/search/replay/live path already calls) so no loader in `src/messages/store.rs` (at its 457-line baseline) grows.
- 2026-10-01 The orphan-attachment sweep (`src/admin/metrics.rs` purge re-check, `src/attachments/content.rs` recompute) now also counts a live sticker as a reference, because a sticker message shares its object with the set catalogue: without it, recalling every message that used a sticker and running the purge deleted the set's file. Edits are line-count neutral (both files sit at their size baseline).
- 2026-10-01 `StoredMessage` gained `Default` and the three existing struct literals use `..Default::default()` instead of `reactions: Vec::new()`, so adding the two optional fields grew neither `src/messages/store.rs` nor `src/attachments/content.rs` past their baselines.
- 2026-10-01 Built and tested with a private `CARGO_TARGET_DIR=/home/mike/workspace/chat_room/target-tg-302` (agent-protocol §1 exception), because in the shared dir the `chat_room` lib artifact of another worktree (tg-208) was linked into this worktree's tests — the fingerprint does not distinguish worktrees, so tests saw a crate without `stickers`. Delete that directory after merge.
- 2026-10-01 No new dependency: `flate2` (gzip), `serde_json` (Lottie header) and a ~150-line EBML walker cover the three formats; nothing is decoded.
- 2026-10-01 Sticker send checks `message.send` (the attachment rule) through `authorize_upload`, which I made `pub(crate)` instead of copying it. TG-201 should add `message.send_sticker` to the registry and to `src/stickers/handlers/messages.rs` when it lands.

## Residual risk

- Forwarding a sticker message (`forward_message`, `src/messages/store.rs`) copies the attachment but not `media_kind`/`sticker_id`, so a forwarded sticker renders as a plain image/file attachment. Fix belongs to whoever next edits the forward path (store.rs is at its size baseline).
- The chat file browser (`/api/chats/:id/files`) lists sticker messages as files.
- A sticker object that was uploaded but never sent, then removed from its set, has no `attachments` row, so the orphan sweep never considers it: it leaks (same as a failed attachment metadata write today).
- Sets are public by short name to any signed-in account; there is no private set. Matches Telegram; a product decision if that should change.
- WebM validation trusts container metadata (`Duration`, `DefaultDuration`, pixel size); a file lying in its header is not caught because nothing is decoded. Same for TGS `op/fr`. Clients should still cap playback.
- The shared `CARGO_TARGET_DIR` links another worktree's `chat_room` lib into tests (see Decisions); other agents may be testing stale code without noticing.
