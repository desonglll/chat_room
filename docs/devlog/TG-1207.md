- `MessageCacheLookup` gains `Bypass` (read the database, do not populate).

## Root causes (diagnosed before coding)

### 1. "AI off but the knowledge index calls embeddings and retries 401 forever"

Not reproducible with the committed `chat-room.toml` (port 18207, sqlite, default config): zero
embedding traffic, zero 401 lines. Evidence for the real cause:

- `src/main.rs:92` runs `dotenvy::dotenv()`. The main checkout has a local, untracked `.env`
  (the user's) containing `CHAT_ROOM_AI_ENABLED=true`, `CHAT_ROOM_VECTOR_ENABLED=true`,
  `CHAT_ROOM_RERANK_ENABLED=true` (only key names and these booleans were read; no secrets).
  TG-1201 started its server from the main checkout, so `[ai] enabled = false` in the TOML was
  overridden. AI was on in that process.
- The vector index is switched by `[vector_store].enabled` alone, independently of `[ai]`.
  (`src/knowledge/mod.rs` `MessageIndex::connect`). With the TOML's `[ai] enabled = false` and
  only the vector flag on, the indexer would still run. Its only consumers are AI context
  retrieval (`src/ai_threads/context.rs`) and the admin reindex (`src/admin/services.rs`).
- The worker (`src/knowledge/worker.rs`) treats every failure as retryable:
  `retry_index_job` backs off exponentially, capped at 300 s, with no attempt limit and no
  error classification. A rejected credential (HTTP 401/403) therefore retries every job
  forever, and every new message adds a job. That is the observed endless 401 log.

### 2. "Default Redis makes every request stall about 2.5 s"

Redis on this machine answers PING in about 1 ms now. Authenticated requests take 2–5 ms with
Redis on, so the stall only appears while Redis is slow (it was, during TG-1201's run, with
five agents compiling). The code path explains the 2.5 s exactly:

- Each `RedisCache` command has its own `tokio::time::timeout(command_timeout = 500 ms)` and
  there is no breaker. A slow Redis makes every call wait the full 500 ms.
- One authenticated history request makes up to five sequential Redis calls:
  `session_user` → `get_session` (500 ms) → DB → `set_session` on miss (500 ms);
  `message_history` → version `GET` (500 ms) → page `GET` (500 ms) → `set_message_history`
  (500 ms). About 2.5 s, repeated on every request.
- The auth rate limiter does the same through its own timeout.
- Latent correctness bug in the same path: a timed-out invalidation `INCR` lets the old page
  stay servable for its TTL.

## Decisions

- 2026-10-01 Breaker inside `RedisCache` rather than shorter timeouts. Any timeout still
  costs its full length once per call. The breaker bounds the cost to one timeout per 5 s
  cooldown regardless of how many calls a request makes.
- 2026-10-01 While open, reads report a miss and writes report success (`Ok`), instead of
  an `Err`. Otherwise every request logs warnings for the whole outage. The breaker logs
  once per transition. Session deletes skipped during an outage are safe: `session_user`
  checks the database row on every request.
- 2026-10-01 After any failure, history pages are not read from Redis until the breaker is
  closed and one `message_ttl_secs` has passed since the failure. Reads go to the database
  and overwrite the page. This closes the lost-invalidation staleness window, including the
  pre-existing one without the breaker.
- 2026-10-01 The rate limiter shares the cache's breaker via `run()`. A bypass uses its
  existing local fallback.
- 2026-10-01 Not changing the user's `.env`. It is their local file, outside the repo.
  Reported to the lead instead.

## Residual risk

- While the breaker is open (≤ 5 s per failure) the auth rate limiter uses its per-process local
  window. With several server replicas, limits are per replica during that window. This is the
  existing fallback behaviour, now entered faster.
- Cooldown is a constant (`breaker::OPEN_COOLDOWN` = 5 s), not configurable. Deliberate: no config
  surface change; revisit if operators need it.
