## Frozen interface

### Database (20270101000004)

- `scheduled_messages(id PK, room_id → chats ON DELETE CASCADE, sender_id → users ON DELETE
  CASCADE, content, entities TEXT JSON default '[]', reply_to_id → messages ON DELETE SET NULL,
  silent BOOL, scheduled_at, created_at, updated_at)`; indexes on `(scheduled_at)` and
  `(room_id, sender_id, scheduled_at)`.
- `messages.silent BOOLEAN NOT NULL DEFAULT FALSE`.
- Triggers rewritten (both adapters): `notifications_reply_insert` fires only
  `WHEN reply_to_id IS NOT NULL AND NOT silent`; the mention notification (SQLite trigger body,
  PostgreSQL `record_mention_notification()`) adds `AND NOT messages.silent`. Mentions are still
  recorded in `message_mentions` for silent messages; only the notification (and hence the push
  job) is skipped.

### HTTP (canonical `/api/chats` prefix only; not on `/api/rooms`)

| Method | Path | Body | Answer |
| --- | --- | --- | --- |
| GET | `/api/chats/{id}/scheduled-messages` | – | 200 `ScheduledMessage[]` (caller's own, soonest first); 404 non-member |
| POST | `/api/chats/{id}/scheduled-messages` | `{content, scheduled_at, entities?, reply_to?, silent?}` | 201 `ScheduledMessage`; 400 bad date/text; 403 no send right; 404 non-member; 409 ≥100 pending |
| PATCH | `/api/chats/{id}/scheduled-messages/{sid}` | `{content?, entities?, scheduled_at?, silent?}` | 200 `ScheduledMessage`; 404 not the caller's / delivered |
| DELETE | `/api/chats/{id}/scheduled-messages/{sid}` | – | 204; 404 |
| POST | `/api/chats/{id}/scheduled-messages/{sid}/send-now` | – | 200 `StoredMessage` (id = sid); 404 already delivered; 503 queue saturated |

`ScheduledMessage = {id, chat_id, content, entities? (omitted when empty), reply_to, silent,
scheduled_at, created_at, updated_at}`. Dates must be `> now` and `≤ now + 366 days`.

### Wire (additive, optional)

- `StoredMessage.silent` and `broadcast.silent`: `true` for silent messages, **omitted** otherwise
  (`skip_serializing_if = Not::not`), so every frozen snapshot is byte-identical.
- Client `message` frame: optional `silent: true`.
- The delivered message's id **equals** the scheduled id; clients drop a list entry when a
  broadcast with that id arrives.

## Decisions

- 2026-10-01 Scheduled messages live in their own table and are INSERTed into `messages` only at
  delivery, instead of `messages.scheduled_at` + filters, because every read path (history,
  search, global search, unread counts, chat-list previews, notifications, catch-up, knowledge
  index, the TG-502 unarchive trigger, reply triggers) would otherwise need a new filter and one
  missed filter is a leak. With a separate table invisibility is structural, and the TG-502
  trigger cannot fire before delivery. (The card text says `messages.scheduled_at`; the lead's
  brief preferred this design.)
- 2026-10-01 Delivery = one transaction: `DELETE FROM scheduled_messages WHERE id` first, then
  `INSERT INTO messages` with the **same id**. The DELETE takes SQLite's write lock / PG's row
  lock, so a concurrent deliverer (another instance, «send now» racing the scheduler) consumes
  nothing and inserts nothing — exactly once without a claim column. Reusing the id also lets the
  client match the broadcast to the list entry.
- 2026-10-01 The delivered `created_at` is the delivery instant, not `scheduled_at`: the realtime
  pollers read `messages` by a `(created_at, id)` cursor; back-dating a late delivery (after
  downtime) would put it behind every connected cursor and it would never be broadcast live.
- 2026-10-01 Dispatcher: a 1 s poll of the indexed `scheduled_at` range, started from
  `build_app_with_web` like the other background workers; the list of started states is a
  process-wide `Vec<Weak<AppState>>` in the module (same pattern as TG-406's poll broadcaster) to
  stay out of `src/state*.rs`. It holds only a `Weak`, so it ends with its state. Each delivery
  takes a `work_queue().message()` permit and ticks are skipped during maintenance. No edit to
  `src/work_queue.rs` was needed.
- 2026-10-01 Delivery re-authorizes: `message.send` or (channel) `message.post` via
  `has_chat_permission` (the full chat-type decision), plus an active-membership + chat-not-deleted
  guard inside the INSERT. An author who lost the right has the row **discarded** (not retried
  forever); logged at info without the body.
- 2026-10-01 Silent = `messages.silent` + trigger conditions, not an app-side filter, because
  reply notifications are produced by a DB trigger and Web Push jobs by a trigger on
  `notifications`; stopping the notification row stops the push with no change in
  `src/notifications` or `src/push_notifications`. Silent messages still count as unread and still
  unarchive (Telegram: silent only mutes the alert).
- 2026-10-01 Scheduled messages are text (+ custom-emoji entities, reply). Media/sticker/poll
  scheduling is left out (see Residual risk); the composer only offers «定时发送» with a text
  draft and no forward.
- 2026-10-01 Date picker is a native `<input type="datetime-local">` (through `TextField`) plus
  three quick picks — accessible on desktop and mobile, no new dependency.
- 2026-10-01 Both dialogs are `React.lazy` chunks (≈1.5 kB + 1.2 kB gzip) so the main bundle only
  gains the composer glue.

## Residual risk

- Scheduling media, stickers, polls or forwards is not supported (text + entities + reply only).
- The client only drops a delivered entry when its broadcast reaches an open chat; for a closed
  chat the list refreshes when the dialog opens or the chat is reopened.
- A second server instance's in-memory chat cache is not refreshed by another instance's
  delivery (pre-existing multi-instance behaviour; the delivery itself is exactly once, tested on
  both adapters with two live instances).
- The dispatcher polls every second; a tick after an outage delivers up to 50 due rows per tick,
  so a very large backlog drains at ~50 messages/s.
- The 100-per-chat limit is a count-then-insert check; concurrent creates can overshoot by a few.
