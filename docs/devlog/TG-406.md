## Frozen interface

### Storage (migration `20270101000006_add_polls`, SQLite + PostgreSQL)

- `polls(message_id PK → messages ON DELETE CASCADE, room_id → chats, creator_id → users SET NULL,
  question, public_voters, multiple_choice, quiz, correct_option, explanation, revision,
  closed_at, created_at)`; CHECK: a quiz has a `correct_option` and is single-choice.
- `poll_options(message_id → polls, position, text)`, PK `(message_id, position)`.
- `poll_votes(message_id, position, user_id → users, voted_at)`, PK `(message_id, user_id,
  position)`, FK `(message_id, position) → poll_options`. Index `(message_id, position, voted_at DESC)`.
- Counts are never stored: always `COUNT(*)` over `poll_votes`.
- **A message is a poll exactly when a `polls` row exists for it.** Nothing depends on TG-302's
  `messages.media_kind`; the lead may later set `media_kind = 'poll'` for these messages, but no
  TG-406 code reads it.

### Wire

- `PollState` (Rust `src/realtime/payloads.rs`, TS `packages/core/src/types/realtime.ts`) —
  TG-007 fields unchanged (`id, question, closed, total_voters, options[{text, voters}]`);
  **additive, omitted at default**: `public_voters`, `multiple_choice`, `quiz`,
  `correct_option` (index), `explanation`, `chosen` (index list), `revision` (monotonic).
  `id` = the poll message's id. A TG-007-shaped payload still parses (test
  `tests/poll_frame_snapshot_test.rs`).
- Privacy rules of a snapshot:
  - chat-wide (`poll_updated`): no `chosen`; quiz answer only once `closed`;
  - per-viewer (history, `broadcast.poll`, REST): `chosen` present (`[]` = not voted); quiz
    answer revealed once the viewer answered or the poll closed;
  - **no snapshot ever contains a voter id.** Voters are listed only by the endpoint below.
- `StoredMessage.poll?` and `broadcast.poll?` — optional, omitted for non-poll messages, never
  set on a recalled message. `content` of a poll message is the question (search, previews,
  notifications see text).
- `poll_updated { message_id, poll }` — aggregated: at most one per poll per
  `POLL_BROADCAST_WINDOW` (250 ms), always reflecting every vote committed before it began.

### HTTP (`src/messages/polls/handlers.rs`, OpenAPI-registered)

| Method | Path | Body / query | Answers |
| --- | --- | --- | --- |
| POST | `/api/chats/:id/polls` | `{question, options[], public_voters?, multiple_choice?, quiz?, correct_option?, explanation?, reply_to?, client_message_id?}` | 201 `StoredMessage` with `poll` |
| GET | `/api/polls/:message_id` | — | `PollState` (viewer) |
| POST | `/api/polls/:message_id/votes` | `{options: number[]}` | `PollState` (viewer) |
| DELETE | `/api/polls/:message_id/votes` | — | `PollState` (viewer) |
| POST | `/api/polls/:message_id/close` | — | `PollState` (viewer) |
| GET | `/api/polls/:message_id/voters` | `?option=&limit=&offset=` | `{option, total, voters[{user_id, username, display_name, avatar_emoji, voted_at}]}` |

Errors: 400 malformed/invalid ballot; 401 no session; 403 no send permission / not author-or-admin
on close / anonymous voter list; 404 no such poll **or not an active member** (existence never
leaks); 409 closed poll, or a quiz answer change/retraction. Limits: question 1–300, 2–10 options
of 1–100, explanation ≤200 (Telegram's). Creation needs `message.send` (or `message.post` in a
channel); voting/reading needs active membership only (channel subscribers vote, as in Telegram);
closing needs authorship or `message.pin` (admins/owner; the chat creator shortcut applies).

## Decisions

- 2026-10-01 Poll keyed by `message_id` (no separate poll id) because the message row already
  owns chat, sender, order, recall and history; forwarding/recall need no extra mapping, and it
  keeps us independent of TG-302's `media_kind` as the lead asked.
- 2026-10-01 Counts computed from `poll_votes`, never denormalised, because a stored counter is
  exactly what concurrent votes corrupt; 4 indexed queries per history page is cheap.
- 2026-10-01 Every mutation transaction starts with `UPDATE polls SET revision = revision + 1`
  because that first write serialises all writers of one poll on both adapters (SQLite takes the
  write lock before any read, so no busy-snapshot upgrade; PostgreSQL row-locks under READ
  COMMITTED and later statements see the winner's commit). Proven by
  `tests/poll_concurrency_test.rs` on both.
- 2026-10-01 Poll snapshots attach **after** the Redis history cache (`message_history`), so
  cached pages hold no counts and 1000 votes never invalidate the cache.
- 2026-10-01 Coalescing state is a process-wide `LazyLock<Mutex<HashSet<message_id>>>` in
  `polls/broadcast.rs`, not an `AppState` field, because `state*.rs` is a lead-owned hotspot and
  message ids are globally unique (multiple `AppState`s in one test process cannot collide).
  Delivery is in-process like every other `AppState::broadcast`.
- 2026-10-01 Viewer-specific data never travels chat-wide: `poll_updated` omits `chosen` and the
  unrevealed quiz answer; the viewer's own responses carry them. The client merges with
  "absent = unknown, keep" (`mergePollState`) and drops snapshots with an older `revision`.
- 2026-10-01 Non-members get 404 on every poll endpoint (not 403) so poll existence does not leak
  across the chat boundary; the anonymous voter list is 403 because anonymity is public info.
- 2026-10-01 Forwarding copies the poll (question, options, mode, quiz answer) as a new open poll
  with no votes, owned by the forwarder — the card's "Telegram forward copies as a new poll".
- 2026-10-01 `forward_message` moved from `src/messages/store.rs` to new
  `src/messages/forward_store.rs` because store.rs sat at its size baseline (457) and the poll
  copy needed the forward to become a transaction. Body otherwise verbatim.
- 2026-10-01 Bars scale by share of all voters (not relative to the leader); single-choice
  percentages use largest remainder so they sum to 100; multiple-choice rounds per option.
- 2026-10-01 Results show only after the viewer voted or the poll closed (Telegram). The
  «结束投票» footer action is shown to the poll's author only — the client does not know chat
  roles; admins can close through the API (a later menu entry can expose it).
- 2026-10-01 The voter-list dialog is `lazy()`-loaded (1.3 kB chunk); the bubble body is in the
  main chunk (it must render in history without a flash).

## Residual risk

- Editing a poll message through the WS `edit` frame changes `content` but not the question
  (the renderer shows `poll.question`). Telegram forbids editing polls; blocking it belongs in
  `src/messages/actions.rs` (not this card).
- `poll_updated` is in-process like every `AppState::broadcast`: a multi-node deployment would
  miss frames from other nodes (same as reactions/edits today).
- A voter's *other* devices learn counts live but not their own `chosen` until reload (frames are
  chat-wide by design).
- The coalescing flush reads the poll with a fresh query per window; under heavy SQLite write
  contention flushes may space out beyond 250 ms (observed: 7 frames over 5 s for 1000 votes) —
  that only lowers the broadcast count further.
- A flush that races a recall may broadcast one last snapshot of a just-recalled poll (question
  and counts only, no voters); clients already hide recalled messages.
