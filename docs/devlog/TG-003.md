### The build-output contract between `packages/web` and `build.rs`

This is what TG-012 (React app shell) and TG-602 (delete `web/`) depend on. It is a
three-sided contract: `packages/web` produces, `build.rs` stages, `src/web.rs` embeds.

**1. How `build.rs` invokes the web build.** Exactly one command, run with cwd
`packages/web`:

```
bun run build -- --outDir <OUT_DIR>/web --emptyOutDir
```

`@tg/web`'s `build` script is `tsc --noEmit && vite build`; bun appends the passthrough
args to the end of that shell string, so the flags land on `vite build`. Two consequences
`packages/web` must preserve:

- `build` must keep `vite build` as its **last** command, or the flags go to the wrong
  process. Prepending more steps is safe; appending one is not.
- `vite.config.ts`'s `build.outDir` is overridden on every Cargo build. The value in the
  config file only matters for a bare `bun run -F '@tg/web' build`.

Dependency install: `build.rs` runs a root `bun install --frozen-lockfile` (cwd = repo
root, the bun workspace root) when `packages/web/node_modules/.bin/vite` is missing. That
path is the sentinel — measured, not assumed: bun 1.3.14 puts `vite` in
`packages/web/node_modules/.bin`, **not** in the root `node_modules/.bin`, which after a
root install holds only `prettier`, `tsc`, `tsserver`.

**2. What must exist in `<OUT_DIR>/web` after the build.** `src/web.rs` embeds these by
fixed path with `include_str!` / `include_bytes!`, so a missing one is a **compile error**,
not a 404:

| Path in `<OUT_DIR>/web` | Produced by |
| --- | --- |
| `index.html` | `packages/web/index.html` via vite |
| `assets/*` | vite (flat directory, hashed names, enumerated at build time) |
| `favicon.svg` | staged from `web/public/` by `build.rs` |
| `icons/icon-sprite.svg` | staged from `web/public/` by `build.rs` |
| `brand/echo-gate.svg` | staged from `web/public/` by `build.rs` |
| `emoji-data-zh.json` | staged from `web/public/` by `build.rs` |
| `theme-bootstrap.js` | staged from `web/public/` by `build.rs` |
| `manifest.webmanifest` | staged from `web/public/` by `build.rs` |
| `pwa-192.png` | staged from `web/public/` by `build.rs` |
| `pwa-512.png` | staged from `web/public/` by `build.rs` |
| `sw.js` | synthesized by `build.rs` (self-unregistering stub) |

**3. The staging precedence rule, which is how TG-012 and TG-602 take these over.**
`build.rs` stages a legacy file only **if that path does not already exist** in
`<OUT_DIR>/web` after vite has run. So creating `packages/web/public/favicon.svg` (vite
copies `publicDir` into `outDir`) silently and automatically wins over
`web/public/favicon.svg`; no `build.rs` change is needed. Same for `packages/web/public/sw.js`
or a real service-worker-emitting plugin in `packages/web/vite.config.ts`.

**TG-602 cannot delete `web/public/` until all nine staged paths are served from
`packages/web`.** `build.rs` panics with the exact missing path if one is absent. The
honest completion order is: TG-012 adds `packages/web/public/**` → `build.rs`'s
`LEGACY_PUBLIC_ASSETS` list becomes dead → TG-602 deletes the list and `web/`.

**4. The asset manifest.** `build.rs` writes `<OUT_DIR>/web_assets.rs` containing
`const GENERATED_ASSETS: &[(&str, &str, &[u8])]` — one entry per **regular file** directly
inside `<OUT_DIR>/web/assets`, sorted by name, as `(file name, content type, include_bytes!)`.
Content type is `text/css; charset=utf-8` for `.css`, `text/javascript; charset=utf-8` for
`.js`, `application/octet-stream` otherwise. Subdirectories under `assets/` are skipped
(they would otherwise become an `include_bytes!` on a directory, i.e. a compile error), so
**`packages/web` must not configure nested asset output** without adding manifest support
first. Vite 8's default `assets/[name]-[hash][extname]` is flat and satisfies this.

**5. Not part of the contract.** `web/` is no longer read by the Rust build except for the
eight files under `web/public/`. `cd web && bun install && bun run dev|build` keeps working
on its own `web/bun.lock` and is not compiled into the binary any more.

### The one that changed the shape of the task

- 2026-09-30 **`build.rs` stages eight files out of `web/public/` and synthesizes `sw.js`,
  instead of only repointing the build directory.** Repointing alone does not compile.
  `src/web.rs` lines 9–18 embed ten fixed paths with `include_str!`/`include_bytes!`:
  `index.html`, `favicon.svg`, `icons/icon-sprite.svg`, `brand/echo-gate.svg`,
  `emoji-data-zh.json`, `theme-bootstrap.js`, `manifest.webmanifest`, `sw.js`, `pwa-192.png`,
  `pwa-512.png`. `packages/web` produces only `index.html` and `assets/`; the other nine came
  from `web/public/` via vite's `publicDir` (eight of them) and from the
  `echo-gate-service-worker` plugin in `web/vite.config.ts` (`sw.js`). A missing one is a
  **compile error**, not a 404. The three ways out were: (a) edit `src/web.rs` — outside
  allowed paths and reserved to the integration lead; (b) add `packages/web/public/**` —
  outside allowed paths, TG-012's territory; (c) stage them from `build.rs`, which this task
  owns. Chose (c). It keeps the repointing inside one file and the staging rule (below) makes
  TG-012's takeover a pure addition.
- 2026-09-30 Staging **never overwrites a file vite already emitted** — it copies only when
  the destination is absent after `--emptyOutDir`. So the moment TG-012 creates
  `packages/web/public/favicon.svg`, vite's copy wins and `build.rs` needs no edit. The
  alternative (copy unconditionally, or pass `--publicDir ../../web/public` on the CLI) would
  have made `web/public` silently outrank `packages/web/public` forever, i.e. a trap for the
  next task. Precedence was chosen to point at the future, not the past.
- 2026-09-30 `sw.js` is a **generated self-unregistering stub**, not a copy of the Vue
  worker. The Vue worker precached that client's `assets/app.js`, `assets/app.css` and chunk
  URLs, which no longer exist; embedding it would pin returning browsers to 404s. It is also
  not obtainable without building `web/`, which is the thing this task removes from the Rust
  build. The stub calls `skipWaiting()`, deletes every cache and `unregister()`s, so a browser
  that already installed the Vue worker is actively cleaned up rather than left in control. It
  is replaced automatically once `packages/web` emits its own `sw.js` (same precedence rule).
  Deliberately no `client.navigate()` — the next navigation is already clean, and forcing a
  reload from an activating worker is how reload loops start.

### Invoking the workspace build

- 2026-09-30 The install sentinel is **`packages/web/node_modules/.bin/vite`**, not the root
  `node_modules/.bin/vite`. Measured, not assumed: after `bun install` at the workspace root
  on bun 1.3.14, root `node_modules/.bin` contains only `prettier`, `tsc`, `tsserver`; `vite`
  is in the member's own `.bin`. Using the root path as the sentinel would have re-run
  `bun install` on every single Cargo build.
- 2026-09-30 `bun install --frozen-lockfile` runs **once at the repository root** with no
  `current_dir`, because the crate root is the bun workspace root and one root install
  populates all three members. The old code had `current_dir("web")`; a per-package install in
  a bun workspace is not a thing.
- 2026-09-30 Kept the `bun run build -- --outDir <abs> --emptyOutDir` invocation form rather
  than calling `packages/web/node_modules/.bin/vite` directly. Verified by running it that bun
  appends passthrough args to the end of the script string, so `tsc --noEmit && vite build`
  becomes `tsc --noEmit && vite build --outDir "…" --emptyOutDir` — the type-check stays in
  the Cargo build, which is where a broken client should fail. The cost is recorded in
  `Frozen interface`: `vite build` must remain the last command in that script.
- 2026-09-30 `rerun-if-changed` lists **specific subpaths** of each package
  (`package.json`, `tsconfig.json`, `src`, …), not the package directories, because
  `packages/web` contains `node_modules` and Cargo walks a watched directory recursively.
  `packages/web/public` is emitted **only if it exists**: Cargo re-runs a build script
  unconditionally when a watched path is missing, so listing it now would rebuild the client
  on every `cargo check`. Consequence to accept: the first `cargo build` after TG-012 creates
  that directory needs a `touch build.rs`. Noted in `Residual risk`.

### Salvaged from the archived `master` branch

Integration lead pointed at `archive/master-2026-09-30`, commit `c24a2f1 feat: split web and
API containers with legacy postgres support`, which solved a more general version of this
problem with cargo features (`--features react|vue|api-only`).

- 2026-09-30 **Did not adopt feature-based client selection.** Three reasons, in order of
  weight:
  1. It cannot be landed from this task. `[features] default/vue/react/api-only` lives in
     `Cargo.toml`, which is in this task's explicit *do not touch* list and is
     integration-lead-exclusive under `agent-protocol.md` §3.1. A `build.rs` that reads
     `CARGO_FEATURE_REACT` while `Cargo.toml` declares no features is a dead branch that can
     never execute — strictly worse than a hardcoded path, because it reads as working.
  2. The `--all-features` landmine has no in-scope fix, and the archive did not fix it
     either. `AGENTS.md` and `agent-protocol.md` §2.4 both prescribe
     `cargo clippy --all-targets --all-features` and `cargo test --all-targets --all-features`.
     The archived assert is `react + vue + api-only <= 1`, so `--all-features` (= 3) trips it.
     Checked what `c24a2f1` actually did about that: nothing — it changed CI to
     `cargo test --locked --all-targets` plus a separate `cargo check --locked --features
     api-only`, i.e. it *avoided* `--all-features` rather than making it green. Reproducing
     that needs `.github/workflows/**`, outside this task's allowed paths. TG-000 currently
     relies on "the crate declares zero features, so `--all-features` is byte-identical to the
     default build"; this task does not invalidate that.
  3. The benefit does not survive contact with `main`. `--features vue` re-embeds a client
     that `docs/tg/README.md` locks as deleted and TG-602 removes; it buys optionality nobody
     asked for at the price of a permanently two-branch build script. The card's actual
     requirement — `web/` stays *independently runnable* — is satisfied and verified without
     any feature.
- 2026-09-30 **`api-only` is acceptable to drop now because the capability already exists at
  runtime on `main`.** `src/main.rs:22` declares `--no-web` and `src/main.rs:145` feeds
  `web_enabled` into `build_app_with_web`, so an API-only deployment is one CLI flag today. The
  only thing `--features api-only` adds over `--no-web` is *not paying the bun build and not
  embedding the bundle bytes* — a build-time and binary-size optimization, not a capability.
  And it cannot work against `main`'s `src/web.rs` anyway: the archived
  `generate_api_only_assets()` writes `index.html` plus an empty manifest, which leaves
  `main`'s nine other `include_*!` paths unresolved. Making it work requires porting the
  archived `src/web.rs` shape (see the integration note below), which is a `src/**` change and
  a separate task.
- 2026-09-30 **Adopted two things from `c24a2f1`'s `generate_asset_manifest`, because they are
  strictly better and live entirely inside `build.rs`:** the recursive walk of `assets/`
  (`collect_asset_names`) and the full `content_type()` extension table. The previous flat
  `read_dir` would have turned a nested asset directory into `include_bytes!` on a directory —
  a compile error with no usable message — and the previous two-arm match served every `.css`
  and `.js` correctly but every `.svg`, `.png` and `.woff2` in `assets/` as
  `application/octet-stream`. TG-012 adds exactly those. Verified `/assets/*path` in
  `src/lib.rs:327` captures the whole remainder, so a relative key like `sub/x.js` resolves.
- 2026-09-30 **Did not adopt the archive's manifest key format.** `c24a2f1` keyed
  `GENERATED_ASSETS` by path relative to the whole output directory (`assets/index-x.js`,
  `favicon.svg`) because its `src/web.rs` served *everything* through the manifest. `main`'s
  `web::bundled_asset` compares the key against the `/assets/*path` remainder, so keys must be
  relative to `assets/`. Copying the archive's format here would have produced a build that
  compiles and 404s every asset at runtime. This is the one place the archive is actively
  wrong for `main`.

### Dockerfile and `.dockerignore`

- 2026-09-30 The COPY list preserves the manifest-before-source split, so the layer order is
  now: `package.json` + `bun.lock` + `tsconfig.base.json` + the three `packages/*/package.json`
  → `bun install --frozen-lockfile` → `src` + `packages` + `web/public`. A source-only change
  still reuses the cached install layer, which is the property the old `web/…` list had.
- 2026-09-30 `COPY packages ./packages` copies whole package directories rather than
  enumerating `src`/`test`/`tsconfig.json` per package, because an enumerated list silently
  drops any directory a later task adds. That is only safe with `.dockerignore` excluding the
  build products, which is why `node_modules`, `packages/*/node_modules` and `packages/*/dist`
  were added. Without those entries the host's `node_modules` would both bloat the build
  context and overwrite the container's freshly installed one. `.dockerignore` is listed in
  this task's allowed paths precisely for this.
- 2026-09-30 `packages/core` and `packages/ui` are copied even though only `packages/web` is
  built, because `@tg/web`'s `build` runs `tsc --noEmit` first and that resolves `@tg/core` and
  `@tg/ui` as TypeScript source (TG-002 froze source consumption, no `dist`).
- 2026-09-30 `COPY web/public ./web/public` stays, and `web/src` / `web/index.html` /
  `web/vite.config.ts` / `web/bun.lock` are gone. That is the whole point of the task: the Vue
  client no longer participates in the image build, but the eight files `src/web.rs` still
  embeds do. When `web/public` can go, so can this line and `LEGACY_PUBLIC_ASSETS` together.
- 2026-09-30 **Image verification is deferred to `.github/workflows/ci-cd.yml`'s `image` job,
  by integration-lead direction mid-task; the local `docker build` was cancelled after ~50
  minutes in the `cargo build --locked --release` stage.** Recorded because the roadmap card
  still lists "`docker build` 成功" under Acceptance and TG-001 deferred its own image check to
  this task — a later reader will otherwise conclude the check was skipped silently. The
  reasoning given: that job uses buildx with `push: false` and GitHub Actions caching, carries
  no `if:` guard so it runs on `agent/**` pushes, and a local build shares no cache with it
  while competing for the same disk as the shared Cargo build directory. The consequence I own
  is `Dockerfile review` below — the COPY list is reasoned line by line instead of being
  demonstrated, and `Residual risk` names the three specific ways it can still be wrong. The
  local build did get far enough to prove the base images resolve and the context is accepted;
  it proves nothing about the COPY list.
- 2026-09-30 Three separate `COPY packages/<name>/package.json ./packages/<name>/` lines rather
  than one `COPY packages/*/package.json ./packages/`. Docker resolves a glob source against a
  directory destination by basename, so all three would land as `./packages/package.json` and
  the last would win. This is a correctness constraint, not formatting.
- 2026-09-30 Left `web/src` and the other `web/` sources **in** the build context rather than
  adding them to `.dockerignore`. They are no longer COPYed, so they cost context transfer
  only; excluding some of `web/` while `web/public` must stay would have made the ignore file
  harder to read than the saving is worth. TG-602 deletes the directory outright.

## Dockerfile review

Image verification is deferred to CI, so the COPY list has to be reviewable by reading. Here
is every line of the `source` stage and why it is there. Nothing else in the file changed —
the `ENV CARGO_TARGET_DIR=/app/target` block, the `builder` stage, the `postgres:17-bookworm`
runtime, the user/volume/healthcheck setup and the entrypoint are untouched.

Before (Vue) → after (workspace):

| Line | Before | After |
| --- | --- | --- |
| manifests | `COPY web/package.json web/bun.lock web/tsconfig.json web/vite.config.ts ./web/` | `COPY package.json bun.lock tsconfig.base.json ./` + `COPY packages/{core,ui,web}/package.json` into each package dir |
| install | `RUN … cd web && bun install --frozen-lockfile` | `RUN … bun install --frozen-lockfile` (at `/app`) |
| sources | `COPY src ./src` + `web/index.html` + `web/public` + `web/src` | `COPY src ./src` + `COPY packages ./packages` + `COPY web/public ./web/public` |

Line by line, after:

- `COPY package.json bun.lock tsconfig.base.json ./` — `package.json` declares
  `workspaces: ["packages/*"]`; `bun.lock` is the root lockfile TG-002 committed;
  `tsconfig.base.json` is what every package's `tsconfig.json` extends, and `@tg/web`'s
  `build` starts with `tsc --noEmit`, so a missing base config fails the build, not just the
  typecheck. `web/bun.lock` and `web/tsconfig.json` are **gone**, which is the point of the
  task: the Vue client's dependency graph (PrimeVue, cytoscape, vue-router, …) is no longer
  installed to build the server.
- `COPY packages/core/package.json ./packages/core/` and the same for `ui` and `web` — bun
  needs every workspace member's manifest present before `bun install` will resolve a
  workspace, and `--frozen-lockfile` compares them against `bun.lock`. Three separate COPY
  lines rather than one glob because `COPY packages/*/package.json ./packages/` flattens all
  three onto one destination path and the last one wins — a known Docker COPY footgun, not a
  style preference.
- `RUN --mount=type=cache,id=chatroom-bun,… bun install --frozen-lockfile` — **one** install at
  the workspace root, no `cd`. The bun install cache mount id is unchanged, so the warm cache
  from previous builds still applies. **This is the layer whose caching matters**, and it is
  still preceded only by manifests, so it is invalidated by a dependency change and not by a
  source change — the exact property the old file had.
- `COPY src ./src` — unchanged, and still after the install layer.
- `COPY packages ./packages` — whole package directories. Needed for `packages/web` because
  `build.rs` builds it; needed for `packages/core` and `packages/ui` because TG-002 froze them
  as **TypeScript source** with `exports` pointing at `.ts` and no build step, so `@tg/web`'s
  `tsc --noEmit` resolves into their `src/`. Whole-dir rather than an enumerated
  `src`/`test`/`tsconfig.json` list so that a directory a later task adds is not silently
  dropped; that is only safe because `.dockerignore` now excludes `packages/*/node_modules` and
  `packages/*/dist`. It re-copies the three `package.json` files with identical content, which
  is harmless.
- `COPY web/public ./web/public` — the eight files `src/web.rs` embeds by fixed path and
  `build.rs` stages (`favicon.svg`, `icons/icon-sprite.svg`, `brand/echo-gate.svg`,
  `emoji-data-zh.json`, `theme-bootstrap.js`, `manifest.webmanifest`, `pwa-192.png`,
  `pwa-512.png`). `web/src`, `web/index.html`, `web/vite.config.ts` and `web/bun.lock` are no
  longer copied at all. This line and `LEGACY_PUBLIC_ASSETS` in `build.rs` disappear together
  once `packages/web/public/**` exists.

Layer-caching property, stated so it can be checked: the only `RUN` that installs dependencies
is preceded exclusively by `Cargo.toml`, `Cargo.lock`, `build.rs`, `migrations*`, and the four
bun manifest files. Editing anything under `src/`, `packages/*/src`, or `web/public` cannot
invalidate it.

`.dockerignore` is not in the roadmap card's `Allowed paths` (`build.rs`, `Dockerfile`,

### For the integration lead / TG-602: what is worth keeping from `archive/master-2026-09-30`

The tag is the only remaining copy. Four things there are worth more than the feature flags:

1. **`src/web.rs`'s shape.** On that branch `src/web.rs` had **one** fixed embed

2. **`--features api-only` + a separate nginx frontend image.** `git show

- **The nine staged files are a hidden coupling between a deleted-scheduled directory and the
  Rust build.** `build.rs` will keep reading `web/public/` until TG-012 provides
  `packages/web/public/**`. Deleting `web/public` before then fails the build with a clear
  panic naming the missing file, but it fails. The precedence rule makes the fix additive; it
  does not make the coupling go away. Item 1 of the salvage list is what actually removes it.
- **The generated `sw.js` is a behaviour change nobody has exercised in a browser.** It was
  fetched over HTTP and its bytes verified, but "a browser that already has the Vue service
  worker installed gets cleanly unregistered" is reasoned, not observed — there is no browser
  automation in this environment and no previously-installed worker to test against. The
  failure mode if the reasoning is wrong is a returning user seeing stale Vue assets until a
  hard reload. A reviewer with a browser should load the old client once, then the new one.
- **`packages/web/public` is watched only once it exists.** The first `cargo build` after
  TG-012 creates that directory will not notice it; `touch build.rs` is needed once. This is a
  deliberate trade against Cargo re-running the build script on every `cargo check` (which is
  what listing a missing path does). It is a papercut that will be reported as "my public file
  is not being embedded".
- **`tsc --noEmit` now runs inside every `cargo build` that touches the client.** That is
  intentional — a type error should fail the Rust build — but it means Cargo build times are
  coupled to `packages/core` and `packages/ui` compile health, and a red typecheck in a
  package this task does not own will look like a `build.rs` failure. The panic message says
  `React web build failed`, which is honest but not specific.
- **The richer `content_type()` table is unexercised.** `packages/web` currently emits one
  `.js` file and nothing else into `assets/`, so only the `Some("js")` arm has ever run in this
  repo. The table is copied verbatim from `c24a2f1`, where it did run, minus `pdf` (nothing

  branch is currently dead. A reviewer should not read "the page loads" as coverage of either.
- **`bun install --frozen-lockfile` inside `build.rs` means `cargo build` can reach the
  network** on a machine without `packages/web/node_modules`. That was already true of the old
  code; the sentinel path changed, the property did not. Worth knowing for an offline build.
- **The `Dockerfile` change is unverified — this is the biggest thing to distrust in this
  branch.** No image was produced (see `Verification`). Every claim about it is reasoning over
  the file, not observation. The specific ways it could still be wrong, in descending
  likelihood:
