## Frozen interface

### Semantics

- `ChatType::effective_permission`: in a channel, a request for `message.send` is decided as
  `message.post` (prerequisites included). Every send path — WS `message`/`typing`/`poke`,
  attachments (multipart + chunked), stickers, polls (`message.send_poll`), forwards, favorite
  forwards — therefore needs `message.post` in a channel, and the content kinds
  (`send_media`/`send_sticker`/`send_poll`/`embed_link`) depend on `message.post` there.
- Channel role grants (`channels::system_role_grants`): owner = registry; admin =
  `ADMIN_BASELINE` + `CHANNEL_ADMIN_RIGHTS` (post, edit_any, delete_any, pin, chat.info,
  room.settings, members.review/invite/remove/ban); subscriber (`member` role) = **nothing**.
- Moderation keys now enforced (WS `edit` / `recall`, `chats::message_moderation`): own message
  → `message.edit_own` (+ `message.send`) / `message.recall_own`; someone else's →
  `message.edit_any` / `message.delete_any`. A moderator edit never revives a recalled message.
  Poll creation → `message.send_poll`; closing someone else's poll → `message.pin` **or**
  `message.edit_any`.
- Reactions: in a channel every subscriber may react (`AppState::may_react`); elsewhere
  reacting still needs `message.send`.
- A channel post's frozen `sender` is the channel title (`resolve_display_name`).
- A channel is quiet: `chat_participants` = staff (owner + admins); no `system` join/leave,
  `presence`, `user_status` or `read_receipt` frames; `auth_ok.read_receipts` = the viewer's
  own cursor; `auth_ok.members` = connected staff.

### HTTP (canonical `/api/chats` only; not on the `/api/rooms` alias)

| Method | Path | Gate | Body → Answer |
| --- | --- | --- | --- |
| POST | `/api/chats` | session | + `chat_type: "group" \| "channel"` (default group; others 400), `signatures_enabled?: bool` (channel only) → `Chat` |
| POST | `/:id/subscription` | session; not banned; password if any (`{password}` body optional) | → 200 `ChatMembership` (active) / 202 (approval channel); 404 not a channel; 403 banned |
| DELETE | `/:id/subscription` | session | → 204; 409 owner; 404 not a channel |
| PATCH | `/:id/channel` | `chat.info` | `{signatures_enabled}` → `Chat`; broadcasts `chat_updated` |
| POST | `/:id/message-views` | subscriber of a channel | `{message_ids: uuid[1..=100]}` → `{views: [{message_id, views}]}` (counts as stored now; unknown/recalled ids dropped); 400 empty/>100; 404 not a channel or not a reader |

### WebSocket

- `broadcast` gains two optional fields (omitted when absent, snapshots unchanged):
  `views: i64` (channel posts only) and `post_author: string` (signed posts only).
- `message_views_updated {views: [{message_id, views}]}` (frame shape frozen by TG-007): at
  most one per channel per `VIEW_BROADCAST_WINDOW` (500 ms), listing every post that gained
  views in that window with its new total.

### Schema (`20261101000003_add_channel_posts`)

- `messages.views_count INTEGER/BIGINT NOT NULL DEFAULT 0`, `messages.post_author TEXT NULL`.
- `message_views(message_id → messages ON DELETE CASCADE, user_id → users ON DELETE CASCADE,
  viewed_at, PK(message_id, user_id))`, index `message_views_user_idx(user_id)`.
- Trigger `messages_channel_post_author` (SQLite AFTER INSERT row trigger; PostgreSQL BEFORE
  INSERT function) fills `post_author` = nickname › display name › username of the sender for
  every insert into a channel whose `signatures_enabled` is on.

## Decisions

- 2026-10-01 Subscribers keep a `chat_members` row (role `member`, which in a channel holds no
  key) instead of a separate subscription table. Reason: every read gate (`can_read_chat`,
  chat list, unread counts, mute in `chat_members.muted_until`, notifications, search, files,
  forward source, WS join) authorizes on `chat_members`; a second table would have to be taught
  to each of them, each a chance to leak. What is actually O(N) at 200k is the fan-out of a
  join, not the row: the roster in `system`/`presence` frames, a `read_receipt` per read, and
  every cursor in `auth_ok`. Those are removed for channels (`chats::channels` module docs).
  TG-201 already measured the roster paging and the `member_count` triggers at 200k.
- 2026-10-01 `message.send` is *decided as* `message.post` in a channel
  (`ChatType::effective_permission`), rather than teaching each send path about channels.
  Reason: ~10 paths ask for `message.send` or a kind that depends on it, and TG-401 (voice),
  TG-404 (scheduled), TG-305 (GIF) are adding more in parallel; they inherit the rule for free.
  The TG-201 follow-up (channel admins cannot send media) is fixed by the same line.
- 2026-10-01 Views are counted once per account and post (`message_views` rows) and applied in
  batches: the report endpoint only enqueues; one flush per chat per 500 ms window writes all
  pairs in one transaction (`INSERT … ON CONFLICT DO NOTHING RETURNING`) and sends one frame.
  Reason: the card's broadcast bound, and one transaction instead of one per viewer. A crash
  loses at most one window of views; counter and rows never disagree.
- 2026-10-01 Views are reported over REST (`POST /message-views`), not a new WS client frame.
  Reason: keeps the frozen client-frame set untouched and the handler in this task's files; it
  mirrors Telegram's `messages.getMessagesViews(increment)`.
- 2026-10-01 `post_author` is written by a database trigger, not by each insert path. Reason:
  seven insert paths exist today (text, attachment, chunked upload, sticker, poll, forward,
  favorite forward) and three parallel tasks add more; the trigger sees them all.
- 2026-10-01 A channel post's `sender` is frozen as the channel title. Reason: Telegram shows
  posts in the channel's name; the author is only visible through the signature.
- 2026-10-01 Reactions in a channel are allowed for every subscriber ("react if allowed" =
  an active, unbanned subscriber). A per-channel reaction switch is not in the card.
- 2026-10-01 Own-message recall now needs `message.recall_own` instead of `message.send`, so a
  muted member can still delete their own message (Telegram behaviour); own edits still need
  `message.send` as before.
