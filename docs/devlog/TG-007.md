## Frozen interface

TG-008 (drafts), TG-011 (`packages/core` WS client), TG-107 (typing/presence UI), and M2+
build on this section. The `ChatMessage` enum moved from `src/models.rs` to
`src/realtime/frames.rs` with its payload types in `src/realtime/payloads.rs`; both are
re-exported from `crate::models`, so every existing `use crate::models::ChatMessage` keeps
working and `crate::models` remains the import path of record.

### 1. Extended `typing` frame

```jsonc
// client → server (and rebroadcast server → client with user_id/username filled)
{ "type": "typing", "content": "draft preview…", "action": "recording_voice",
  "user_id": "…", "username": "…" }
```

- `action` ∈ `typing` | `recording_voice` | `recording_video_note` | `uploading_photo` |
  `uploading_video` | `uploading_document` | `uploading_voice` | `choosing_sticker` |
  `choosing_location` | `cancel` (Rust: `TypingAction`).
- `action` is **optional on input, always present on output**. A frame without it (every
  pre-TG-007 client) means `typing`.
- A server-side **unknown** `action` string deserialises to `typing`
  (`#[serde(from = "String")]`), so a newer client never gets its typing frame dropped by an
  older server. Client implementations (TG-011) MUST mirror this: unknown `action` → `typing`.
- Legacy clear semantics kept: empty `content` with `action: "typing"` still means "stopped
  typing" (the frozen Vue client both sends and renders that). New clients SHOULD send
  `action: "cancel"`. Server-initiated clears (message sent, connection closed) are emitted as
  `content: ""` + `action: "cancel"`.

### 2. Presence: per-user status

`ChatMember` (`{user_id, username, avatar_emoji}`) and the `presence` frame
(`{members, participants}`) are **unchanged** — see Decisions for why per-user `last_seen`
is a sibling frame rather than a new field on those (state.rs ownership + Telegram parity:
`updateUserStatus` is its own update there too). Clients MUST NOT assume any relative order
between `presence`, `system` and `user_status` frames.

New frame, server → client:

```jsonc
{ "type": "user_status", "user_id": "…", "status": { "kind": "online" } }
{ "type": "user_status", "user_id": "…",
  "status": { "kind": "offline", "last_seen": "2026-09-30T12:00:00Z" } }
```

`status.kind` ∈ `online` | `offline` (with `last_seen`) | `recently` | `within_week` |
`within_month` | `long_ago` | `empty` (Rust: `UserStatus`). The five non-online/offline kinds
are the **privacy tiers** — they are Telegram's obscured statuses and are placeholders until
TG-505 implements the real per-viewer privacy rules. `empty` = "no information".

Live behaviour as of this task (all emitted from `src/realtime/ws.rs`):

- first connection of an account to a chat → broadcast `online` (after the join
  `system` / `presence` frame);
- last connection of an account closes → broadcast `offline` with `last_seen = now` (before
  the trailing `presence` frame);
- `auth_ok` gains `statuses`: one entry per active participant — `online` for currently
  connected accounts, `empty` for the rest (no persistence yet; a DB-backed last_seen is
  TG-505/M5 work).

```jsonc
{ "type": "auth_ok", "room_name": "…", "members": […], "participants": […],
  "read_receipts": […],
  "statuses": [ { "user_id": "…", "status": { "kind": "online" } },
                { "user_id": "…", "status": { "kind": "empty" } } ] }
```

### 3. New frame skeletons (shape + broadcast path only; business logic in later milestones)

All server → client. A client frame carrying one of these types is ignored by the server
(the existing `_ => {}` in `src/realtime/inbound.rs`), like every other server-only frame.

| frame | shape | filled by |
| --- | --- | --- |
| `chat_updated` | `{ "chat": <Chat descriptor — same JSON as GET /api/chats/:id, never password_hash/access_hash> }` | M2 (TG-201/202) |
| `member_updated` | `{ "member": <ChatMembership: user_id, username, avatar_emoji, nickname, role, status, requested_at, joined_at> }` | M2 (TG-201) |
| `topic_updated` | `{ "topic": { "id", "title", "icon_emoji", "closed": bool, "pinned": bool } }` | M2 (TG-204) |
| `message_views_updated` | `{ "views": [ { "message_id", "views": int }, … ] }` — **batched**, one frame carries many ids | M2 (TG-202) |
| `poll_updated` | `{ "message_id", "poll": { "id", "question", "closed": bool, "total_voters": int, "options": [ { "text", "voters": int }, … ] } }` | M4 |
| `draft_updated` | `{ "user_id", "text", "reply_to_message_id": uuid\|null, "topic_id": uuid\|null, "updated_at" }` | TG-008 |

Rust payload types: `TopicSummary`, `MessageViewCount`, `PollState`, `PollOption` in
`src/realtime/payloads.rs`. Later milestones extend these **additively only** (new optional
fields); the tags and existing fields above are frozen.

**Broadcast paths.** Every variant travels the existing pipeline
(`AppState::broadcast` → `ChatEvent::Message` → per-connection forwarder in
`src/realtime/outbound.rs` → socket), verified end-to-end by
`tests/ws_frame_broadcast_test.rs`. One frame has routing logic in the transport:
`draft_updated` carries `user_id` and the forwarder (`frame_visible_to` in
`src/realtime/protocol.rs`) delivers it **only to that user's own connections** — TG-008
broadcasts a draft on the chat channel and the transport keeps it private to the drafting
account. Everything else is chat-wide.

### 4. Compatibility contract for the frozen clients

- The server **ignores** unknown inbound frame types (parse failure → frame dropped,
  connection stays up). Pinned by `tests/ws_frame_broadcast_test.rs`.
- ratatui CLI: unknown server frames decode to a catch-all `Unknown` variant and are
  silently ignored (see Decisions — the one behavioural change in `src/bin/`).
- Old Vue client: extended `typing` / `auth_ok` are safe (extra JSON keys ignored), but an
  unknown frame **type** falls through `handleMessage` into the system-message branch and
  renders an empty bubble — patch under "Integration patch required" fixes it; with live
  `user_status` emission this patch is **required at merge time**, not optional.

### 5. What did NOT change (frozen non-changes)

`auth_ok.room_name` keeps its name (frozen client data, CONTEXT.md "Room");
`ForwardedFrom.room_name`; `/ws/:room_id` path; the `presence` frame and `ChatMember`;
every pre-TG-007 frame keeps its exact serialisation — pinned byte-for-byte by
`tests/ws_frame_snapshot_legacy_test.rs`. This was the one deliberate breaking window;
**from here on the WS protocol only grows** (new frames, new optional fields), it does not
change shape again.

## Decisions

- 2026-09-30 **Per-user status is a new `user_status` frame plus `auth_ok.statuses`, not new
  fields on `presence` / `ChatMember`.** Three reasons. (1) Ownership and greenness: the
  `presence` variant is constructed in `src/state.rs` (`publish_member_profile`) and
  `ChatMember` is built literally in `src/state.rs` and `src/chats/participants.rs` — all
  integration-lead-owned; any field added to either would not compile without editing files
  this task must not touch, leaving the branch red until a patch is applied. (2) Telegram
  parity: Telegram's own protocol delivers status as its own update (`updateUserStatus`), not
  embedded in member lists. (3) 只增不改: TG-505 can change what `status` contains per viewer
  without ever touching the member snapshot again. The frozen interface explicitly forbids
  clients from assuming relative order of `presence` and `user_status` frames.
- 2026-09-30 **The `ChatMessage` enum moved to `src/realtime/frames.rs`, re-exported from
  `crate::models`.** The frame changes belong to the realtime module (this task's ownership),
  `models.rs` would have crossed the 350-line warning with the seven new variants, and
  TG-004 set the same precedent with `chats::models`. No import site changed.
- 2026-09-30 **Added a `cancel` typing action beyond the card's nine.** Without it a granular
  state (`recording_voice`…) could only be cleared by the legacy empty-`content` convention,
  which TG-107's UI should not have to depend on. Legacy semantics kept in parallel: empty
  `content` + default action still means "stopped" because the frozen Vue client sends and
  renders exactly that. Server-initiated clears (message sent, disconnect) emit `cancel`.
- 2026-09-30 **Unknown `action` strings deserialise to `typing`
  (`#[serde(from = "String")]`)** instead of failing the frame: serde's `#[serde(other)]` is
  not available on plain string enums, and dropping a whole typing frame because a newer
  client added an action would be the worst outcome. The roundtrip test pins that the
  `From<String>` table agrees with the serialised names for all ten actions.
- 2026-09-30 **`draft_updated` routing lives in the transport, not in a new channel.** The
  frame carries `user_id` and the per-connection forwarder (`frame_visible_to`,
  `src/realtime/protocol.rs`) drops it for every other account. The alternative — per-user
  channels — is `state.rs` surgery this task must not do. Cost accepted and documented: the
  draft text transits (but is never delivered through) other connections' forwarder tasks
  in-process. TG-008 just calls `AppState::broadcast`.
- 2026-09-30 **New frames are emitted live only where the card demands live behaviour**
  (typing actions, `user_status` on connect/disconnect, `auth_ok.statuses`); the six
  skeletons have no trigger yet — their broadcast path is proven by
  `tests/ws_frame_broadcast_test.rs` driving `AppState::broadcast` directly. `auth_ok.statuses`
  reports `online`/`empty` only: without a migration (card: none) there is no persisted
  last-seen for offline users, and inventing one in memory would produce values that lie
  across restarts. `offline.last_seen` is real because it is stamped at disconnect time.
- 2026-09-30 **`user_status` ordering: `online` after the join `system`/`presence` frame,
  `offline` before the trailing `presence` frame.** Chosen to keep the existing
  strict-order test assertions (and any frozen-client assumption shaped like them) valid;
  the frozen interface declares the relative order unspecified so nobody new may rely on it.
- 2026-09-30 **`src/bin/client_chat_protocol.rs` got one behavioural change** (listed here
  because bin edits are otherwise compilation-only): a `#[serde(other)] Unknown` variant on
  its `ServerMessage`, ignored by `emit_server_event`. Measured before the change: every
  unknown frame kind produced `ChatEvent::Error("unknown variant `user_status`…")` — an error
  line in the TUI per frame, and worse, `connect()` aborts outright if one arrives during the
  auth loop. That fails the card's acceptance ("旧客户端对未知帧优雅忽略"), and with live
  `user_status` emission it would happen on every peer connect. Behaviour for every known
  frame is byte-identical; `src/bin/client_chat.rs` and the rest of the CLI are untouched.
- 2026-09-30 **`ws.rs` split: history replay moved to `src/realtime/history_replay.rs`.**
  `ws.rs` was at 345 lines, five under the gate, before this task added anything. The replay
  block was the one self-contained concern; behaviour unchanged (same sends, same
  `member_disconnected` on failure, same cursor result).
- 2026-09-30 **`chat_updated` embeds the full REST `Chat` descriptor** rather than a slimmer
  ad-hoc shape: `Chat`'s serialisation already never emits `password_hash`/`access_hash`
  (pinned by `chat_updated_carries_the_rest_descriptor_and_never_the_hashes`), clients get one
  descriptor shape to parse everywhere, and M2 gains fields by growing `Chat` — additively —
  instead of re-breaking the frame. `member_updated` reuses `ChatMembership` for the same
  reason.
- 2026-09-30 **Fixed a pre-existing `cargo fmt` failure in `tests/integration/web_client.rs`
  (4 lines, chain wrap).** Verified by stashing this task's changes: the base commit d12aae2
  itself fails `cargo fmt --all -- --check` on that one file (introduced by f044c5d). The file
  is inside my `tests/**` grant and the fmt gate cannot pass without it; noting it here so the
  lead knows the hunk is unrelated to frames and that main's fmt gate was red at base.
- 2026-09-30 **Existing tests were adapted at their `next_json`/`read_json` helpers, not at
  each assertion.** Live `user_status` frames interleave with the sequences five test files
  assert strictly. Each file's frame-reader now skips `user_status` exactly like it already
  skips `history_complete` (one changed line per file, no baseline growth); dedicated
  `user_status` coverage lives in `tests/ws_frame_broadcast_test.rs` instead. Files:
  `attachment_test.rs`, `chat_features_test.rs`, `chat_management_test.rs`,
  `integration_test.rs` (helper shared by `tests/integration/*`).

## Residual risk

- **The Vue patch is required, not optional, once this merges.** Until it is applied, every
  peer connect/disconnect paints an empty system bubble in an open Vue chat. Measured, small,
  cosmetic — but user-visible in the reference client.
- **`auth_ok.statuses` reports `empty` for every offline participant.** There is no persisted
  last-seen (card: no migration), so TG-107's chat-header "last seen …" copy can only be
  rendered for users seen disconnecting during the session. TG-505 (or an M5 sibling) must add
  the `users.last_seen_at` column and replace `initial_statuses`'s `Empty` branch; the frame
  shape already carries whatever it produces.
- **`user_status` is emitted per chat channel, not per account globally.** A user in two
  chats produces independent status frames per chat, and `last_seen` stamps the moment the
  last connection *to that chat* closed. Telegram's status is global per user; when M5 builds
  the real presence system it should emit from a per-user source instead — additively, same
  frame.
- **Draft privacy relies on one transport filter.** `frame_visible_to` in
  `src/realtime/protocol.rs` is the only thing keeping a `draft_updated` broadcast out of
  other users' sockets; `tests/ws_frame_routing_test.rs::draft_updated_reaches_only_the_
  drafting_accounts_connections` pins it. If TG-008 ever bypasses `ChatEvent::Message` (e.g.
  a direct `send_json`), that guarantee silently disappears — keep drafts on
  `AppState::broadcast`.
- **The skeleton payload shapes are my best forward-guess of M2/M4 needs** (TopicSummary,
  PollState, MessageViewCount fields). They are deliberately minimal; if M2 needs a different
  *field meaning* (not a new field), that is a frame break this task was supposed to have
  prevented — review them now, not in M2.
- **The CLI's typing indicator display was not visually captured** during the live drive (the
  tmux capture raced the 6-second typing window; the probe log proves the frames reached and
  left the server correctly, and the CLI's typing rendering path is untouched pre-existing
  code). TG-107 owns typing UI anyway.
- **The PySide6 desktop client was traced, not driven.** `apply_event` ignores unknown kinds
  by construction; the card scoped live verification to the Vue and ratatui clients.
