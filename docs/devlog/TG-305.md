## Frozen interface

### HTTP (all JSON, bearer session; errors `{ "error": code }`)

| Route | Answer |
| --- | --- |
| `GET /api/gifs/saved` | `SavedGif[]`, most recently used first |
| `POST /api/gifs/saved` `{ message_id }` | `201 SavedGif` (new) / `200 SavedGif` (already saved, moved to the front). `404 message_not_found` when the caller cannot read the message (nonexistent, recalled, deleted chat, not an active member — indistinguishable on purpose); `400 not_a_gif`; `400 gif_unavailable` (legacy non-content-addressed object) |
| `DELETE /api/gifs/saved/:id` | `204`; `404 saved_gif_not_found` unless it is the caller's |
| `GET /api/gifs/saved/:id/file?key=` | the saved copy, capability-keyed (no bearer), `Range` supported (206), `private, immutable` |
| `GET /api/gifs/recent?limit=` | `RecentGif[]` (≤ 60), newest first, one per content hash, from chats where the caller is an active member; password chats and sensitive attachments excluded |
| `POST /api/chats/:id/gif-messages` `{ saved_gif_id \| message_id, reply_to?, client_message_id? }` | `201 StoredMessage` (`media_kind: "gif"`), `200` on a `client_message_id` replay; `400 exactly_one_source`; `404 saved_gif_not_found` / `message_not_found`; `403` without `message.send` |
| `POST /api/chats/:id/gif-messages/upload?reply_to=&client_message_id=` body = raw file | same answers; `400 unsupported_format / invalid_file / invalid_dimensions / unsupported_codec / audio_not_allowed / too_long / empty_file`; `413` over 10 MiB |

`SavedGif = { id, mime_type, size_bytes, width|null, height|null, duration_ms|null, file_url, saved_at, used_at }`
`RecentGif = { message_id, room_id, mime_type, size_bytes, width|null, height|null, duration_ms|null, file_url, created_at }` — `file_url` is the message attachment's own `download_url`.

A GIF message on the wire is an ordinary attachment message with `media_kind: "gif"` (TG-302's column/field; no new wire field). Accepted formats: `image/gif`, `video/mp4` (H.264 `avc1`/`avc3`, no sound track), `video/webm` (no audio track); ≤ 10 MiB, ≤ 60 s when stated, sides 1–4096.

### Schema (`20261201000004_add_user_saved_gifs`, SQLite + PostgreSQL)

- `user_saved_gifs(id PK, user_id → users ON DELETE CASCADE, content_hash, storage_key, mime_type, size_bytes, access_key, source_message_id (no FK), saved_at, used_at, UNIQUE(user_id, content_hash))`, indexes `(user_id, used_at DESC)`, `(storage_key)`.
- `animation_metadata(content_hash PK, width, height, duration_ms, created_at)` — geometry the server read from an uploaded header.
- Partial indexes `messages_gif_created_idx ON messages(created_at) WHERE media_kind = 'gif'`, `attachments_gif_mime_idx ON attachments(created_at) WHERE mime_type = 'image/gif'`.
- `user_saved_gifs.storage_key` is a live reference for the attachment orphan sweep (`recompute_attachment_orphan_status` and the purge re-check).

## Decisions

- 2026-10-01 **No server-side transcoding.** `ffmpeg` is installed on this host, but the repository never invokes it, the `Dockerfile` does not ship it, and a process-spawning converter is a new runtime dependency (AGENTS.md: needs lead review). Instead the server accepts the GIF formats browsers play natively: short, silent MP4 (H.264) and WebM "animations" — Telegram's own storage format — plus real `.gif` files. Clients play video GIFs as muted looping inline `<video>` and fall back to `<img>` for `.gif`. If the lead later approves a converter, only `send.rs::store_animation` changes (convert, then store the MP4); the wire and the table already speak MIME types.
- 2026-10-01 **Header-only validation** (`gifs/animation*.rs`): format by magic bytes, never by the client's MIME; MP4 `moov/trak` walk for geometry, `avc1/avc3`, and any `soun` handler → `audio_not_allowed`; WebM EBML walk for `PixelWidth/Height`, duration, and any audio track. "Silent" is enforced as "no audio track", because a GIF always plays muted and sound would be silently lost. No new dependency; fuzzed by truncation in the tests.
- 2026-10-01 **A saved GIF is the account's own reference, like a favorite**: saving requires being able to read the message *now* (live message, live chat, active membership — the same rule as favorites and TG-201's `can_read_chat`, and the membership that reveals the attachment capability through history); afterwards it outlives the source message's recall or the account leaving the chat (Telegram behaviour). It gets its own capability key and file route, so it never piggybacks on a message attachment's key. Unreadable and nonexistent answer the same 404.
- 2026-10-01 **The orphan sweep counts saved GIFs.** Without it a recalled GIF message would let the purge delete an object someone still has saved. Two one-clause edits (`src/attachments/content.rs`, `src/admin/metrics.rs`), written on the existing lines so neither baseline file grows; removing/evicting a saved GIF re-runs `recompute_attachment_orphan_status`. Test: `the_orphan_sweep_keeps_a_saved_gif_until_it_is_removed`.
- 2026-10-01 **Sending is by reference**, like stickers: a new `attachments` row (own capability key) pointing at the same content-addressed object, inserted with the message (`media_kind = 'gif'`) in one transaction under the `message.send` re-check, then cache invalidation + broadcast — the existing attachment path, not a parallel one. Upload uses a raw request body (not multipart) so the core client can send a `Blob` through the injected fetch.
- 2026-10-01 **Recency order**: `used_at` moves a GIF to the front on re-save and on send (Telegram); cap 200 per account, least recently used evicted (and released to the sweep).
- 2026-10-01 **Recent GIFs from chats** skip password chats (their history needs the password on every read; this list would otherwise hand out their capability URLs without it) and sensitive attachments (the panel has no veil). One per content hash. Partial indexes keep the query off a full `messages` scan.
- 2026-10-01 **Geometry**: the server records header geometry per content hash (`animation_metadata`) so the masonry has boxes before any file loads; GIFs that arrived without it (plain attachment `.gif`s) use aspect 1 until the media reports its own (`onAspect` → `gifStore.aspects`). The message wire is unchanged (no width/height) — the bubble sizes to the media like a photo.
- 2026-10-01 **Autoplay policy is a pure state machine** (`playback.ts`): play iff on screen AND (autoplay allowed OR tapped); off screen always pauses; a tap on a playing GIF pauses it and it stays paused when it scrolls back. `autoplayAllowed = !prefers-reduced-motion && !Save-Data`, read live via `useSyncExternalStore`. One shared IntersectionObserver with **no** root margin, so "off screen" means off screen.
- 2026-10-01 **A real `.gif` is not an `<img>` unless it plays**: paused/not autoplaying it is a canvas still drawn from the first frame; removing the `<img>` is the only way to stop a browser decoding an animated image. Video GIFs use `pause()`.
- 2026-10-01 **"保存 GIF" menu row via a new generic extension point** in `features/message/messageMenu.tsx` (`registerMessageMenuItem`), because no message-actions extension existed and the builder is hard-coded. ~20 lines, no behaviour change when nothing is registered (TG-103 menu tests unchanged). The row loads `gifLibrary` lazily. No toast exists in `@tg/ui`, so saving is silent; the GIF tab shows the result.
- 2026-10-01 **Plain `image/gif` attachments render as GIFs too** (priority 25 > image 20), so the autoplay policy also covers GIFs sent through the ordinary attach button; a *sensitive* one is left to the photo kind, which has the veil.
- 2026-10-01 **Panel**: one scroll column, header + masonry per section (已保存的 GIF, 聊天中的 GIF), absolute boxes from `gifPanelLayout`, only cells within viewport ± one screen mounted. The tab is a lazy chunk (`LazyGifTab`), registered from the eager `register.ts`. Sending consumes the composer's reply target (`composerStore.setReplyTarget(chatId, null)`) and closes the panel, like a sticker.
- 2026-10-01 Module layout: `src/stickers/gifs.rs` is the module root the card names; its submodules live in `src/stickers/gifs/` because one file would exceed the 500-line block. `animation.rs` is split into `animation/mp4.rs` and `animation/webm.rs` for the 350-line warning.
- 2026-10-01 Errors reuse `StickerError` (the `src/stickers` domain error; `Invalid(code)` carries the wire string) instead of a second error type.

## Residual risk

- Uploads without a converter: a user with only a large real `.gif` gets it stored as-is (≤ 10 MiB) and played as `<img>`; no GIF→MP4 size win until a converter is approved.
- MP4 validation trusts `mvhd` duration and the first sample entry's codec; a file with a malformed but parseable header may be accepted and simply fail to play (no decode on the server by design).
- Recent GIFs join `messages` → `chat_members` for the caller; partial indexes help, but on a very large deployment with many GIFs in big chats this is the query to watch (it is capped at 180 rows scanned after the index).
- When TG-404 (scheduled messages) lands, if scheduled rows live in `messages` before their send time, `recent_gifs` / `readable_gif_file` must exclude them.
- The "保存 GIF" row gives no feedback (no toast primitive).
- The chat list previews an MP4 GIF as 视频 (it classifies by MIME; not this card's file).
- Safari WebM playback is not verified (Safari plays WebM from 14.1/16 depending on codec); MP4 is the recommended upload format and is what Telegram uses.
