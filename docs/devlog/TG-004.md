## Frozen interface

### 1. The `chats` table as built

SQLite (`migrations/20261001000001-03`); PostgreSQL is identical modulo types
(`TEXT`→`UUID`, `TEXT`→`TIMESTAMPTZ`, `INTEGER`→`BOOLEAN` for the three flags).

```sql
chats (
  id                              TEXT PRIMARY KEY NOT NULL,
  title                           TEXT NOT NULL,              -- was rooms.name
  password_hash                   TEXT NOT NULL DEFAULT '',
  creator_user_id                 TEXT REFERENCES users (id) ON DELETE SET NULL,
  join_policy                     TEXT NOT NULL DEFAULT 'open'
                                    CHECK (join_policy IN ('open', 'approval')),
  avatar_emoji                    TEXT NOT NULL DEFAULT '',
  description                     TEXT NOT NULL DEFAULT '',
  deleted_at                      TEXT,
  created_at                      TEXT NOT NULL,
  locked_at                       TEXT,
  chat_type                       TEXT NOT NULL DEFAULT 'group'
                                    CHECK (chat_type IN ('private','group','supergroup','channel')),
  username                        TEXT,
  access_hash                     TEXT NOT NULL DEFAULT '',
  is_forum                        INTEGER NOT NULL DEFAULT 0,
  linked_chat_id                  TEXT DEFAULT NULL REFERENCES chats (id) ON DELETE SET NULL,
  slow_mode_seconds               INTEGER NOT NULL DEFAULT 0,
  auto_delete_seconds             INTEGER NOT NULL DEFAULT 0,
  signatures_enabled              INTEGER NOT NULL DEFAULT 0,
  history_visible_to_new_members  INTEGER NOT NULL DEFAULT 1,
  member_count                    INTEGER NOT NULL DEFAULT 0   -- projection, not truth
)

CREATE INDEX        chats_created_at_idx       ON chats (created_at, id);
CREATE UNIQUE INDEX chats_title_active_idx     ON chats (title)    WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX chats_username_active_idx  ON chats (username)
    WHERE deleted_at IS NULL AND username IS NOT NULL;
```

`member_count` is seeded in the same transaction that writes the owner's (or the two direct
participants') membership, and backfilled from `chat_members` for pre-existing rows. It is a
projection: the authoritative count is still `COUNT(*)` over `chat_members`.

### 3. `ChatType`

`src/chats/chat_type.rs`:

```rust
pub enum ChatType { Private, Group, Supergroup, Channel }   // serde + SQL: lowercase strings
```

| | `Private` | `Group` | `Supergroup` | `Channel` |
| --- | --- | --- | --- | --- |
| `member_limit()` | `Some(2)` | `Some(200)` | `Some(200_000)` | `None` |
| `allows_public_username()` | false | false | true | true |
| `allows_topics()` | false | false | true | false |
| `allows_slow_mode()` | false | false | true | false |
| `counts_views()` | false | false | false | true |
| `allows_linked_discussion()` | false | false | false | true |
| `history_visibility_is_configurable()` | false | false | true | false |

`permits(permission_key)` is the **intrinsic-constraint layer** of the authorization decision.
It denies what the type cannot do, whatever the role says:

- `Private` denies `members.invite`, `members.remove`, `members.review`, `members.roles`,
  `room.settings`, `room.delete`, `message.post`, `chat.topics`.
- `Group` denies `message.post`, `chat.topics`.
- `Supergroup` denies nothing.
- `Channel` denies `message.send` (channels use `message.post`) and `chat.topics`.

An unknown key is **permitted**: whether a permission exists at all is the `chat_permissions`
registry's decision, and returning `false` here would silently deny every key M2 adds.

`src/chats/supergroup_upgrade.rs`:

```rust
pub enum SupergroupUpgradeTrigger {
    MemberLimitExceeded, PublicUsernameSet, ForumEnabled, SlowModeEnabled,
}
pub struct ChatCapabilityRequest {
    pub member_count: i64, pub has_public_username: bool,
    pub is_forum: bool, pub slow_mode_seconds: i64,
}
pub fn supergroup_upgrade_trigger(ChatType, &ChatCapabilityRequest)
    -> Option<SupergroupUpgradeTrigger>;
impl ChatType { pub const fn upgraded(self, SupergroupUpgradeTrigger) -> Option<ChatType>; }
```

Only a `Group` is ever triggered, and `upgraded()` returns `Some(Supergroup)` for `Group` and
`None` for everything else: the upgrade is one-way and irreversible, as in Telegram. There is
no downgrade path and none may be added. 200 members is *not* over the limit; 201 is.

### 4. Authorization decision order (architecture.md §4.4)

`AppState::authorize_chat_action(room_id, user_id, permission) -> ChatAuthorization`, in
`src/chats/authorization.rs`, evaluated in exactly this order:

1. **system administrator** → `ChatAuthorization::SystemAdministrator`, but **only** for the
   six administrative keys in `SYSTEM_ADMINISTRATOR_PERMISSIONS` (`room.settings`,
   `room.delete`, `members.review`, `members.invite`, `members.remove`, `members.roles`).
   Never a `message.*` key — see Decisions.
2. **chat creator** (`chats.creator_user_id`) → `ChatAuthorization::Creator`
3. **role permission** from `chat_role_permissions` → `RolePermission` / `NoRolePermission`
4. **per-user restriction** — *reserved for M2*. `chat_member_restrictions` belongs here,
   between 3 and 5, and nowhere else: it must be able to override a role grant while still
   being subject to the intrinsic constraint. The insertion point is the end of
   `chat_permission_grant()`.
5. **`chat_type` intrinsic constraint** → `ForbiddenByChatType(ChatType)`. Applies to every
   grant above it, including step 1's: it can only turn an allow into a deny.

`has_chat_permission()` is the boolean wrapper over the same function, and it is what all 16
call sites use — read paths and write paths alike. `has_chat_role_permission()` is step 3 on
its own, exposed so the order stays readable rather than buried in one query.

one route list pointing at one set of handler items, so the alias cannot drift. The alias adds
exactly one layer, `chats::compat::mark_legacy_room_dialect`, which inserts an
`ApiDialect::LegacyRooms` request extension. Removed in M6.

Chat descriptor response body:

```jsonc
{ "id": "…", "chat_type": "group", "title": "…",
  "username": null, "is_forum": false, "linked_chat_id": null,
  "slow_mode_seconds": 0, "auto_delete_seconds": 0, "signatures_enabled": false,
  "history_visible_to_new_members": true, "member_count": 1,
  "has_password": false, "creator_user_id": "…", "join_policy": "open",
  "avatar_emoji": "", "description": "", "membership_status": "active",
  "membership_role": "owner", "unread_count": 0, "created_at": "…",
  "name": "…"   // ONLY on /api/rooms/* and inside /api/conversations; deprecated, gone in M6

```

- `password_hash` and `access_hash` are never serialised.
- `title` is present on both paths. `name` is present on the alias and inside
  `/api/conversations[].group` (which has no alias of its own), and absent from
  `/api/chats/*`.
- Requests accept `title` **and** `name` (`#[serde(alias = "name")]`) on both paths, as does
  the `?title=`/`?name=` filter on `GET /api/chats`. A pre-rename client can POST to
  `/api/chats` and a post-rename client can POST to `/api/rooms`.
- Every other response field keeps its current spelling, including `room_id` on
  `StoredMessage`, `ChatTask`, `ChatPin`, `ChatAiPolicy`, notifications and search results.
  See "Frozen non-rename 1".
- The OpenAPI document served at `/api-docs/openapi.json` is
  `chats::compat::openapi_with_deprecated_chat_alias()`: every `/api/chats*` path item is
  cloned under `/api/rooms*` with `deprecated: true` and a description pointing at the
  canonical path. No handler is annotated twice.

## Decisions

- 2026-09-30 **Renamed `room_ai_policies` → `chat_ai_policies`, which is not on the task
  card's list.** Audited the live schema by applying all 61 SQLite and 50 PostgreSQL migrations
  to scratch databases and listing tables, rather than reading migration files: it is the tenth
  surviving member of the family (`room_ai_policies.room_id` is a PK foreign key to
  `rooms(id)`), created later than the card's list in
  `20260901030002_add_ai_governance.sql`. Leaving it would have made it the only `room_*` table
  in a `chat_*` schema.
- 2026-09-30 **Did not rename `room_participants`.** It does not exist:
  `20260818000018_drop_legacy_room_participants.sql` dropped it, and the PostgreSQL bootstrap
  (`20260818000000_initial.sql`) never created it. `chat_rename_schema_test.rs` asserts the
  rename table is exhaustive and that this is the one member with no new name.
- 2026-09-30 **Renamed tables and indexes, but no `room_id` column.** The card scopes migration
  `..02` to the ten new columns plus `name`→`title`, and D-003 freezes `messages.room_id`.
  Given that freeze, renaming the *sibling* tables' foreign key to `chat_id` would produce two
  spellings for the same reference and force `ON m.room_id = cm.chat_id` joins forever. One
  spelling is the more consistent outcome; it also avoids rewriting ~1,400 `room_id`
  occurrences where the bare form cannot be mechanically attributed to a table. Recorded in
  `CONTEXT.md` and flagged under "Residual risk" as a candidate follow-up card.
- 2026-09-30 **Forced `PRAGMA legacy_alter_table = OFF` at the top of the SQLite rename
  migration instead of trusting the default.** Measured on SQLite 3.51.0: the `sqlite3` CLI
  ships with `legacy_alter_table = 1`, and under it `ALTER TABLE … RENAME TO` reports success
  while leaving `REFERENCES rooms` clauses in other tables and `FROM room_memberships` inside
  the two `notifications_room_join_*` trigger bodies pointing at names that no longer exist.
  With the pragma OFF, SQLite rewrites both. `src/storage.rs` sets `foreign_keys(true)`, the
  other documented precondition. Verified by mutation: flipping that one line to `ON` makes
  `chat_rename_schema_test.rs` fail (migration `..02` then dies with
  `error in trigger notifications_room_join_insert: no such table: main.room_memberships`).
- 2026-09-30 **Recreated the PostgreSQL function `record_room_join_notification()` inside the
  rename migration.** PostgreSQL does not rewrite plpgsql bodies when a table is renamed — the
  body is text resolved at execution time. Checking `pg_proc.prosrc` on a fully migrated
  database showed it is the only function in the schema that names a renamed table. Without
  this, every join request would have failed at runtime while the migration reported success.
  `assert_postgres_foreign_keys_resolve` now scans `pg_proc.prosrc` for the old names so the
  next person who renames a table cannot miss this.
- 2026-09-30 **Kept the trigger names `notifications_room_join_insert` / `_update` and the
  function name `record_room_join_notification`.** They are named after the notification
  `kind` value `room_join_request`, which clients consume, which the database triggers write,
  and which already exists in every stored `notifications` row. Renaming the trigger would need
  a DROP + CREATE duplicating the whole body for no gain.
- 2026-09-30 **PostgreSQL CHECK and foreign-key constraint names were left alone** (so
  `chat_members` still carries `room_memberships_room_id_fkey`). There are forty of them, no
  application code references a constraint by name, and PostgreSQL's own
  `ALTER TABLE … RENAME` does not rename them either. Indexes *were* renamed, because SQLite
  needed an explicit DROP/CREATE for them anyway and keeping the two adapters comparable is
  worth the six lines.
- 2026-09-30 **`access_hash TEXT NOT NULL DEFAULT ''` rather than architecture.md §4.2's
  `NOT NULL` with no default.** `ALTER TABLE … ADD COLUMN … NOT NULL` requires a non-null
  default in both adapters. Migration `..03` backfills every existing row with 64 bits of
  randomness (`lower(hex(randomblob(8)))` on SQLite, `substr(md5(random() || clock_timestamp()
  || id), 1, 16)` on PostgreSQL — pgcrypto is deliberately not made a deployment
  requirement), and both chat-creation paths generate one, so the empty string is unreachable
  in practice. A `CHECK (access_hash <> '')` is deliberately not added: SQLite cannot add a
  CHECK to an existing column without rebuilding the table.
- 2026-09-30 **`/api/chats/*` and `/api/rooms/*` are produced by one function taking the path
  prefix.** The alias cannot drift from the canonical tree because there is no second route
  list to keep in sync — a stronger guarantee than the equivalence test alone.
- 2026-09-30 **Chose an `ApiDialect` request extension over rewriting response JSON.** The
  alias router carries one `from_fn` layer that inserts the marker; the five chat-descriptor
  handlers take it as an extractor and choose between serialising `Chat` and `ChatCompatView`.
  The rejected alternative — middleware renaming JSON keys on the way out — would have had to
  buffer every response body (breaking the SSE endpoint `…/ai/suggest/events` and the
  attachment streams) and could not tell a chat's `title` from a task's `title`.
- 2026-09-30 **`/api/conversations` serves `ChatCompatView` unconditionally.** It embeds the
  same chat descriptor but has no deprecated alias of its own, so path-scoped shaping cannot
  help it, and `web/src` reads `room.name` there. Emitting both `title` and `name` is what keeps
  the Vue, PySide6 and ratatui clients working. Dropping `name` is M6 work, with those clients.
  The conversation row now also carries `chat_type`, `username`, `is_forum` and `member_count`,
  because architecture.md §4.3 makes the sidebar's shape depend on the chat type and M1 should
  not have to fetch each chat to learn it.
- 2026-09-30 **Left the ratatui CLI on `/api/rooms/*`.** It is the acceptance test for the
  alias; pointing it at `/api/chats/*` would have removed the only end-to-end proof. The
  integration tests moved to `/api/chats/*`, and `tests/chat_api_alias_test.rs` covers the
  alias automatically, so both paths have coverage.
- 2026-09-30 **Step 1 of the authorization order grants a system administrator the six
  administrative permissions and never a `message.*` one.** `CONTEXT.md` defines a System
  Administrator as entrusted with deployment-wide **operations** independently of any Chat
  role, and `AGENTS.md` keeps the Chat as the knowledge-isolation boundary. Letting step 1
  grant `message.send` would have silently given every system administrator read access to
  every chat's history through `GET /api/chats/:id/messages`, which is a privacy change nobody
  asked for. The repository's existing pattern agrees: system-admin powers are exposed through
  dedicated `/api/admin/*` endpoints, not by bypassing chat RBAC.
  `chat_authorization_test.rs` pins both halves.
- 2026-09-30 **Permission key values were not renamed** (`room.settings`, `room.delete`). They
  are rows in `chat_permissions` referenced by value from `chat_role_permissions`; renaming
  them is a migration of user data whose only benefit is tidiness, and architecture.md §4.4
  hands the registry expansion (`chat.info`, `chat.topics`, …) to M2. M2 renames them alongside
  the new keys, with the client rewrite, or keeps them — that is M2's call, not M0's.
- 2026-09-30 **Audit `scope`/`target_type`, the `ai-usage` `group_by` value and the
  `NotificationKind` wire name were reverted to `room` after the mechanical rename changed
  them.** `audit_events.scope` has `CHECK (scope IN ('system','room'))`, so the renamed value
  made every audited chat action return 500; `web/src/auditApi.ts` types `scope` as
  `'system' | 'room'` and `web/src/aiGovernanceApi.ts` types `group_by` as `'room' | 'model'`;
  and `NotificationKind::ChatJoinRequest` needs `#[serde(rename = "room_join_request")]`
  because the value is written by database triggers and stored in existing rows. Each of these
  was found by a failing test, not by inspection — which is the argument for having run the
  whole suite against both adapters rather than only compiling.
- 2026-09-30 **The mechanical rename was done by a masking script, not by hand.** `src` and
  `tests` held 3,585 and 1,407 occurrences of `room`. A curated list of tokens that must
  survive was masked, `Room`/`room`/`ROOM` were replaced globally, then the masks were
  restored. The token list is the interesting artefact and it is reproduced in "Frozen
  non-rename 2"; everything else the compiler and the test suite caught.
- 2026-09-30 **Used `export CARGO_TARGET_DIR=/Volumes/Tuo-APFS/workspace/.cargo-target/tg-004`**
  for this task's shell, per agent-protocol.md §1, because the rename forced dozens of full
  rebuilds. **Delete that directory after this branch merges** — measured 21 GB, which is
  slightly over the 20 GB the protocol reserves; the volume still has 596 GB free. Nothing
  in the repository points at it: `.cargo/config.toml` is untouched, so any other shell keeps
  using the shared directory.
- 2026-09-30 **One commit, not three.** The card allows either. Splitting would have produced a
  migrations-only commit whose tree compiles but is red (the Rust still queries `rooms`), and
  the brief requires every commit that reaches `main` to be green. The three cards are
  separable on paper but not in the diff: the same files carry the table rename, the type
  rename and the alias.

## Residual risk

- **`src/lib.rs` is 347 lines, three from a new gate violation.** The next task that adds an
  OpenAPI path or schema will trip `check_file_sizes.py`. The natural fix is to move `ApiDoc`
  into its own module; I did not, because the `#[derive(OpenApi)]` path list resolves
  module-relative and re-pointing ~120 entries is churn this task did not need.
- **The system-administrator step of the authorization order is a policy call I made.**
  Architecture.md §4.4 says "系统管理员 → 创建者 → …" without saying *which* permissions the
  first step grants. I scoped it to the six administrative keys on the grounds quoted in
  Decisions. If the intended reading is broader, `SYSTEM_ADMINISTRATOR_PERMISSIONS` in
  `src/chats/authorization.rs` is the single place to change, and
  `chat_authorization_test.rs::a_system_administrator_administers_a_chat_but_cannot_reach_its_messages`
  is the test that encodes my reading.
- **Step 2 (creator) is new behaviour, not just a refactor.** Before TG-005 a creator with no
  role row had no permissions. It now has all of them, subject to step 5. In practice
  `chats.creator_user_id` is always an active owner (`membership_mutations` reassigns or clears
  it when an owner leaves), so I expect no behaviour change — but a chat whose membership rows
  were deleted out of band would now authorize its creator.
- **`member_count` is only maintained at creation.** Join, leave, remove and ban do *not*
  update it yet; the backfill and the two creation paths are correct, and everything else
  reads `COUNT(*)`. Whoever implements the supergroup upgrade in M2 must make the membership
  transactions maintain it, or the projection will drift. `supergroup_upgrade_trigger` takes
  the count as an argument precisely so it is the caller's job to pass a trustworthy one.
- **`ChatType::permits` hard-codes permission keys as strings.** It has to, because the
  registry is data, but it means adding `chat.topics` to `chat_permissions` in M2 without
  revisiting `permits()` would silently leave it allowed in a `group`. The unit tests name
  every key the function mentions, so a grep for the key finds them.
- **PostgreSQL constraint names still say `room_*`.** Cosmetic and documented, but a future
  agent reading `\d chat_members` will see `room_memberships_room_id_fkey` and may think the
  rename was incomplete.
- **A follow-up card is worth opening for the `room_id` columns.** If M2 ever wants one
  spelling, the migration itself is cheap (`ALTER TABLE … RENAME COLUMN` updates indexes and
  triggers in both adapters); the cost is entirely in attributing ~1,400 bare `room_id`
  occurrences in Rust SQL strings to the right table. It should be its own serial task with
  its own test pass, not a rider on something else.
- **The `/api/admin/room-locks/:room_id` path was left alone** because it is outside TG-006's
  card. It is now the only `/api/*` path that says "room" and is not a deprecated alias.
