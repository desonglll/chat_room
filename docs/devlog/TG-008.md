## Frozen interface

TG-105 (composer, which reads/writes drafts), TG-011 (`packages/core` WS client) and the
chat-list draft preview in M1 build on this section.

### 1. `chat_drafts` table

One draft per (chat, account). SQLite (`migrations/20261001000004_add_chat_drafts.sql`);
PostgreSQL identical modulo types (`TEXT`→`UUID`/`TIMESTAMPTZ`).

```sql
chat_drafts (
  room_id             TEXT NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
  user_id             TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  text                TEXT NOT NULL,
  reply_to_message_id TEXT REFERENCES messages (id) ON DELETE SET NULL,
  topic_id            TEXT,          -- no FK: forum topics land in M2 (TG-204)
  updated_at          TEXT NOT NULL,
  PRIMARY KEY (room_id, user_id)
)
CREATE INDEX chat_drafts_user_idx ON chat_drafts (user_id, updated_at DESC);
```

**The FK column is `room_id`, not the card's `chat_id`** — lead ruling applying TG-004's
frozen-non-rename-1: `room_id` is the one and only spelling of "foreign key to `chats(id)`"
until a dedicated rename task. See Decisions.

### 2. HTTP contract

Both endpoints exist automatically under the deprecated `/api/rooms/:id/draft` alias because
they are rows in the single route list of `src/chats/routes.rs`.

**`PUT /api/chats/:id/draft`** — idempotent save of the caller's own draft.

```jsonc
// request (all fields except text optional)
{ "text": "unsent…", "reply_to_message_id": null, "topic_id": null }
// response 200 — the stored draft, same shape as the frozen draft_updated frame
{ "user_id": "…", "text": "unsent…", "reply_to_message_id": null,
  "topic_id": null, "updated_at": "2026-09-30T12:00:00Z" }
```

- Auth: bearer session + active membership in the chat (401 / 403). 404 unknown chat.
- `text` > 4096 chars → 400 (the server's message limit; a draft that can never be sent is
  refused early). Text is stored verbatim — no trimming: trailing whitespace mid-composition
  is legitimate draft state.
- `reply_to_message_id` must be a non-recalled message of this chat → otherwise 400.
- **Idempotent:** a PUT identical to the stored draft (`text`, `reply_to_message_id`,
  `topic_id` all equal) writes nothing, broadcasts nothing, and returns the stored row with
  its original `updated_at`. Client retries and debounce races cannot spam other devices.
- **Clear:** `text: ""` with no `reply_to_message_id` deletes the row (Telegram parity:
  saving an empty draft clears it) and answers 200 with the cleared state
  (`text: ""`, nulls, fresh `updated_at`). Clearing an already-absent draft is also
  idempotent: nothing broadcast. An empty `text` WITH a reply is a real draft (reply picked,
  no text yet) and is stored.
- Every non-idempotent PUT broadcasts one `draft_updated` frame (frozen by TG-007:
  `{user_id, text, reply_to_message_id, topic_id, updated_at}`) through
  `AppState::broadcast` on the chat channel; the transport (`frame_visible_to`,
  `src/realtime/protocol.rs`) delivers it only to the drafting account's own connections.

**`GET /api/chats/:id/draft`** — the reconnect read path (断线重连后草稿不丢).

- 200 with the draft object above, or 200 with JSON `null` when no draft is stored.
- Same auth as PUT. This is a new endpoint rather than an `auth_ok` field because TG-007
  closed the frame-breaking window (`auth_ok` may not gain fields) — see Decisions.

### 3. `packages/core` (files owned by this task; barrel exports are a lead patch)

```ts
  reply_to_message_id?: string | null; topic_id?: string | null }

```

`DraftFetchLike` is a minimal injected `(url, init) => Promise<{ status, json() }>` — no
platform global is referenced, per architecture.md §2.

`packages/core/src/domain/draftSync.ts` — pure debounce + idempotence, injected clock:

```ts
export function draftsEqual(a: DraftContent, b: DraftContent): boolean
export function createDraftSynchronizer(save, options: { clock: DraftClock; delayMs?: number })
  // .update(chatId, draft)  debounced (default 1500 ms, clamped 1000–2000)
  // .flush(chatId?)         immediate save of pending edits (navigate away / send)
  // .accept(chatId, draft)  remote draft_updated arrived: adopt as last-saved state
  // .pending(chatId)        introspection for tests/UI
```

`update` with content equal to the last saved/accepted state cancels rather than schedules —
the client half of the idempotence contract; the server half makes retries harmless.

## Decisions

- 2026-09-30 **`chat_drafts.room_id`, deviating from the card's `chat_id` column name.**
  Lead ruling on the card correction: TG-004's frozen-non-rename-1 rules that EVERY foreign
  key to `chats(id)` is spelled `room_id` until a dedicated rename task renames them all at
  once (`chat_members.room_id`, `chat_reads.room_id`, …). A lone `chat_drafts.chat_id` would
  introduce a second spelling and force mixed-name joins forever. The HTTP payload and the
  frozen frame carry no chat-id field at all (the chat is the URL path / the WS channel), so
  the wire contract is unaffected by the column spelling.
- 2026-09-30 **Reconnect read path is `GET /api/chats/:id/draft`, not an `auth_ok` field and
  not a field on an existing REST response.** `auth_ok` is frozen — TG-007 closed the one
  breaking window and its devlog forbids new fields. Decorating `/api/conversations` or the
  chat descriptor would put per-viewer mutable state into responses that are cached and
  compared byte-for-byte by the alias tests, and would make every list query pay a join for
  a field only the composer needs. A dedicated GET beside the PUT keeps the resource
  self-contained, gets the `/api/rooms` alias for free from the single route list, and is
  what a client reconnect naturally does anyway (it re-fetches the chat it reopens).
- 2026-09-30 **Idempotence is comparison-then-write in the handler, not `ON CONFLICT` alone.**
  The card demands server-side idempotent writes because clients debounce and retry. A bare
  upsert is idempotent for the row but not for the side effects — every retry would bump
  `updated_at` and re-broadcast to the account's other devices, which is exactly the spam the
  card wants absorbed. Reading the stored row first (PK lookup, one indexed query) lets an
  identical PUT return the stored `updated_at` untouched and skip the broadcast entirely.
  The write itself is still an atomic UPSERT (`ON CONFLICT (room_id, user_id) DO UPDATE`),
  so two racing non-identical PUTs cannot error — last writer wins, each broadcasts its own
  state, and the account's devices converge on the final frame.
- 2026-09-30 **Broadcast strictly via `AppState::broadcast` / `ChatEvent::Message`.**
  TG-007's devlog flags this exact risk: `frame_visible_to` in `src/realtime/protocol.rs` is
  the only thing keeping `draft_updated` out of other accounts' sockets, and it only runs in
  the per-connection forwarder (`src/realtime/outbound.rs`). A direct socket send would
  bypass the privacy guarantee. `tests/ws_draft_routing_test.rs` drives the real HTTP PUT and
  asserts both sides (same-account fan-out, cross-account silence) end-to-end.
- 2026-09-30 **Empty text + no reply deletes the row instead of storing an empty draft.**
  Telegram parity (saving an empty draft is how Telegram clears one), and it keeps
  `chat_drafts` from accumulating a dead row per member per chat. The clear still answers
  200 with the cleared state and still broadcasts (once — clearing an absent draft is a
  no-op), so other devices erase their composer. An empty `text` WITH `reply_to_message_id`
  is deliberately a stored draft: a picked reply target with no text yet is real composer
  state in Telegram.
- 2026-09-30 **`reply_to_message_id` is validated (this chat, not recalled) → 400; `topic_id`
  is stored opaquely.** The reply target is checkable today and a cross-chat reply pointer
  would leak message existence across the authorization boundary. Topics do not exist until
  M2 (TG-204), so there is nothing to validate against and no FK to declare; M2 owns adding
  the constraint if it wants it. Documented in the frozen interface so TG-204 sees it.
- 2026-09-30 **Draft cap = 4096 chars, rejected with 400 rather than truncated.** 4096 is
  `MAX_MESSAGE_CHARS` (`src/realtime/auth.rs`) — a longer draft could never be sent. Silent
  truncation would make devices disagree about the draft's tail; an explicit 400 keeps the
  client's local copy authoritative until it shortens. The client debouncer is unaffected
  (it keeps local state and simply fails the sync).
- 2026-09-30 **GET answers 200 + JSON `null` for "no draft", not 404.** Absence of a draft is
  the normal state, not an error; a 404 would be indistinguishable from a typo'd path for
  clients and would force error-branch handling on every reconnect. `Json(Option<ChatDraft>)`
  keeps one success shape.
- 2026-09-30 **Membership gate is `require_active_member`-style (status == active), no new
  permission key.** A draft is the caller's own composer state, readable and writable only by
  its owner; the chat-type intrinsic layer and role registry govern *sending*, not composing.
  Same gate the pins module uses for direct chats — and direct chats have `chat_members`
  rows, so one gate covers all four chat types.
- 2026-09-30 **`updated_at` is server-stamped, never client-supplied.** Devices' clocks skew;
  the frame consumers (other devices of the same account) use `updated_at` to order frames
  against local edits, so one clock must own it.
- 2026-09-30 **Debounce default 1500 ms, clamped to the card's 1–2 s.** Mid-range so hosts
  passing nothing comply with the card; a host passing an out-of-range value is clamped
  rather than trusted, because the card's range is a product requirement, not a hint.
- 2026-09-30 **Colocated `.test.ts` files in `packages/core/src/`.** The ownership grant is
  "drafts.ts and domain/draft* plus their .test.ts files"; colocating keeps the grant to four
  files and two directories. `bun test` discovers them wherever they live, and the platform
  boundary scanner walks all of `src/` — the tests obey the same no-DOM rules, which is a
  feature: the test double for the clock proves the domain helper needs no real timer.

## Residual risk

- **The idempotence check is read-then-write, not atomic.** Two *concurrent* PUTs from the
  same account can each read the stale row: two identical ones may both broadcast (a
  harmless duplicate frame), two different ones each broadcast their own state while the
  UPSERT makes the last writer win — the account's devices converge on the last *frame*,
  which in a pathological interleaving may not be the last *row*. The next PUT or GET
  resolves it. Serialising via a transaction would buy little: the debounced client makes
  concurrent same-account PUTs rare, and drafts are self-correcting state.
- **`draft_updated` fan-out is in-process only.** `AppState::broadcast` reaches connections
  of this server instance; unlike `broadcast` messages, drafts have no database polling
  fallback in `outbound.rs`. In a multi-instance deployment a device connected to another
  instance misses the live frame and only catches up through the reconnect GET. Same
  limitation as every TG-007 frame; whoever builds multi-instance realtime owns it.
- **`topic_id` is stored opaquely** — no FK, no validation — until topics exist (M2,
  TG-204). A client can park an arbitrary UUID there. Documented in the frozen interface;
  M2 decides whether to backfill-validate.
- **Drafts of soft-deleted chats linger.** `deleted_at` never fires the CASCADE; the rows
  go away when the retention job hard-deletes the chat. Bounded by (members × chats) and
  by the 4096-char cap; the endpoints already 404 on soft-deleted chats via `state.chat()`.
- **404-before-auth mirrors `tasks::task_actor`.** An unauthenticated prober can tell an
  existing chat id from a random one (404 vs 401), like every other chat-scoped endpoint
  that resolves the chat first. Kept consistent with the repository pattern rather than
  fixed piecemeal here.
- **Draft text is user content in a server-stamped row; it is never logged.** The handlers
  log only `sqlx::Error` values (`internal_error`), matching the "do not log private
  message bodies" rule — worth re-checking if anyone adds tracing to this module.
- **Every future migration-adding task is exposed to the stale-embed hazard** until the
  two-line `build.rs` patch lands: an incremental build in the shared target directory can
  link a `chat_room` lib whose `sqlx::migrate!` embed predates the new migration, making
  fresh deployments from that binary silently miss it and migration tests fail with an
  off-by-N applied count. Measured in this task (see "Integration patch required");
  `touch src/storage.rs` is the manual workaround.
